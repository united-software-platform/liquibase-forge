## Репозиторий разработки

Этот репозиторий — место разработки forge, а не целевой проект, и настраивается иначе.

- **Корень принятого состояния.** В `.env` вручную задаётся `FORGE_ACCEPTED_DIR=.forge/db`:
  `make forge-env-sync` дописывает значение `db` из шаблона. Каталог `.forge/` и `/db/` исключены
  `.gitignore`, поэтому проверочные прогоны `/forge` в git не попадают.
- **Что не входит в поставку forge.** `.gitignore`, `db/` и `backlog/` этого репозитория в целевой
  проект не переносятся: поставленный `.gitignore` скрыл бы принятое состояние и след целевого
  проекта. Файлы обмена в `.forge/` скрывает от git собственный `.forge/.gitignore`, который
  создают `forge` и шлюз.

## Отличия от поставки kit'а

Отличия forge в файлах SDD Developer Kit обрамлены строками-маркерами `# >>> liquibase-forge`
и `# <<< liquibase-forge`. Текст между маркерами — копия фрагмента из
[`install/blocks/`](./install/blocks/): тот же фрагмент установщик `install.sh` вносит в целевой
проект. Правка отличия делается в двух местах одной правкой — во фрагменте и между маркерами
файла; расхождение ловит тест `tests/delivery/test_blocks.py`. Текст вне маркеров совпадает
с поставкой kit'а и под forge не правится.

| Файл | Фрагмент | Основание |
|------|----------|-----------|
| [docker-compose.yml](./docker-compose.yml) | [docker-compose.yml](./install/blocks/docker-compose.yml) | Окружение kit'а и инструмент lbfr описаны разными файлами: сервис агента `claude` остаётся в файле kit'а, сервисы инструмента подключаются секцией `include:` из [docker/lbfr/docker-compose.yaml](./docker/lbfr/docker-compose.yaml) |
| [Makefile](./Makefile) | [Makefile](./install/blocks/Makefile) | Раннер исполняет только цели `make`: через них агент без Docker запускает Liquibase и готовит окружение |
| [.env.example](./.env.example) | [env.example](./install/blocks/env.example) | Адреса и учётные данные БД, перечень тестовых БД, корень принятого состояния, версии образов |
| [tools/host-runner/runner.py](./tools/host-runner/runner.py) | [runner.py](./install/blocks/runner.py) | Раннер отказывает целям вне белого списка `ALLOWED_TARGETS`; дополнительного списка из `.env` в kit'е пока нет. Блок — отдельный оператор сразу за присваиванием `ALLOWED_TARGETS`: он расширяет белый список, записан ли тот однострочным или многострочным множеством либо выведен из словаря `TARGET_VARIABLES`, и вносит цели forge в этот словарь без переменных. Словарь, объявленный после `ALLOWED_TARGETS`, блок не видит |
| [.gitignore](./.gitignore) | [gitignore](./install/blocks/gitignore) | Файлы обмена `.forge/` и окружение uv подпроекта `tools/forge/` локальны. Записи `/db/` и `backlog/*` стоят вне маркеров: они нужны только репозиторию разработки |

Контрольные суммы четырёх файлов kit'а расходятся с `.sdd-kit-manifest.json`. Установщик kit'а
слияния не делает и при обновлении перезаписывает эти файлы целиком, стирая блоки forge. Порядок
обновления kit'а: переустановить kit, затем запустить установщик forge — он находит пропавшие
блоки и вносит их заново. После правки белого списка в `runner.py` раннер на хосте
перезапускается: список читается при старте. Требования к поставке kit'а — в спецификации
[sdd-kit-delivery](./openspec/specs/sdd-kit-delivery/spec.md), к установке forge —
в [forge-delivery](./openspec/specs/forge-delivery/spec.md).

## Блок бейджей

Блок бейджей стоит в [`README.md`](./README.md) между заголовком и назначением. Бейдж версии
динамический: номер читается сервисом бейджей из `VERSION`, ручной копии номера в `README.md` нет.

| Бейдж | Источник значения | Режим | Цель ссылки |
|-------|-------------------|-------|-------------|
| `version` | `VERSION` в ветке `main` | `dynamic/regex` | `./VERSION` |
| `license` | статическое значение, носителя нет | — | `./LICENSE` |

Ограничения блока:

- **репозиторий должен быть доступен анонимно** — сервис бейджей читает `VERSION`
  без аутентификации;
- **бейдж показывает версию ветки `main`** — номер в рабочей ветке он покажет только после слияния;
- **перенос версии из `VERSION` ломает бейдж молча** — после правки носителя бейдж
  проверяется глазами.

## Выпуск версии

Номер версии хранится только в `VERSION`: `pyproject.toml` берёт его при сборке, `uv.lock` номера
проекта не держит, установщик пишет его в `forge_version` манифеста. Вручную номер не правится —
его повышает сценарий [`release`](./.github/workflows/release.yml).

Версия выпускается ручным запуском сценария `release` на вкладке Actions репозитория. Ветка
запуска — `main`: из другой ветки сценарий завершается ошибкой, а пока файла сценария нет в `main`,
GitHub ручной запуск не показывает. Единственный ввод — разряд:

| Разряд | Что меняется | Пример |
|--------|--------------|--------|
| `patch` | Последнее число | `1.4.3` → `1.4.4` |
| `minor` | Среднее число, последнее обнуляется | `1.4.3` → `1.5.0` |
| `major` | Первое число, остальные обнуляются | `1.4.3` → `2.0.0` |

Сначала прогон вызывает workflow [`checks`](./.github/workflows/checks.yml) на коммите `main`:
если проверки не пройдены, сценарий завершается ошибкой, и ничего не записывается. Затем гейт
задач выпуска находит на GitHub milestone `vX.Y.Z` нового номера: если его нет либо в нём открыта
задача или PR, сценарий завершается ошибкой с их перечнем, и ничего не записывается. Затем прогон
записывает новый номер в `VERSION`, создаёт релизный коммит по
[GIT-021](./rules/git-rules.md#исключение-для-машинного-релизного-коммита), ставит аннотированный
тег `vX.Y.Z`, публикует коммит и тег ключом развёртывания и создаёт GitHub Release по тегу через
`GITHUB_TOKEN`. По этому релизу установщик без `--ref` находит последнюю версию через `releases/latest`.

Предусловия и сбои:

- **Состав выпуска — milestone `vX.Y.Z` нового номера.** Его заводят до выпуска, в том числе
  для `patch`, и привязывают к нему задачи выпуска. Задачи закрываются строками `Closes #N`
  в PR, слитом в `main` до запуска сценария; задачу, которую не успели сделать, переносят
  в другой milestone явно.
- **Ключ развёртывания `release` с правом записи и секрет Actions `RELEASE_DEPLOY_KEY` заведены**
  (см. [защиту `main`](#защита-main)). Без секрета сценарий завершается ошибкой до записи `VERSION`.
  Если push ключом отклонён, прогон падает на публикации коммита — до тега и релиза.
- **Сбой шага «Публикация релиза» после push тега** доводится вручную той же командой:
  `gh release create vX.Y.Z --verify-tag --title vX.Y.Z --generate-notes`. Повторный запуск
  сценария выпустил бы уже следующую версию.

### Защита main

Ветка `main` защищена ruleset'ом из [`.github/rulesets/main.json`](./.github/rulesets/main.json):
изменения попадают в неё только слиянием PR с зелёным job'ом `checks`, одобрения не требуются,
force-push и удаление ветки запрещены. Обход правил есть только у ключа развёртывания `release`,
которым сценарий публикует релизный коммит и тег; у администраторов обхода нет. Имя обязательной
проверки в файле совпадает с именем job'а в `checks.yml` — это сторожит тест
`tests/release/test_main_ruleset.py`.

Ruleset применяется к GitHub командой владельца после каждой правки файла; повторный запуск
ничего не меняет:

```bash
sh tools/github/apply-ruleset.sh .github/rulesets/main.json
```

| Код | Что значит | Что делается |
|-----|------------|--------------|
| `0` | Ruleset создан или обновлён | Правила проверяются: `gh api repos/{owner}/{repo}/rules/branches/main` |
| `1` | GitHub отклонил запрос | Проверяется право администрирования у `gh` и тело файла по тексту ошибки |
| `2` | Нет аргумента, файл не читается, в нём нет имени или `gh` не определил репозиторий | Команда повторяется из корня репозитория с путём к файлу |

Ключ развёртывания заводится и заменяется одними и теми же командами; закрытая часть остаётся
только в секрете. При замене старый ключ сначала удаляется: `gh repo deploy-key list`, затем
`gh repo deploy-key delete <id>`.

```bash
dir=$(mktemp -d)
ssh-keygen -t ed25519 -N "" -C release -f "$dir/release"
gh repo deploy-key add "$dir/release.pub" --allow-write --title release
gh secret set RELEASE_DEPLOY_KEY < "$dir/release"
rm -rf "$dir"
```

Если GitHub Actions не работает, PR в `main` не слить никому — это цена отказа от обхода
у администраторов. Владелец временно переводит ruleset в `disabled` в настройках репозитория
или через API, а после восстановления Actions возвращает правила командой применения выше.

## Проверки

Проверки запускаются в контейнере агента до отправки изменений, каждая — своей командой:

```bash
uv run pytest                 # модульные и интеграционные тесты
uv run pytest tests/delivery  # установщик, перечень поставки и блоки forge
uv run pytest tests/release   # носитель номера, релизный сценарий и проверки CI
uv run ruff check             # линтер
uv run ruff format --check    # форматирование
uv run mypy src               # типы
sh tools/make-lint/check.sh   # объём секций Makefile
```

Интеграционные тесты помечены маркером `integration`. Без `FORGE_TEST_DB_HOST` или без заданных
`AGENT_RUNNER_URL` и `AGENT_RUNNER_TOKEN` они пропускаются с причиной, а при
`FORGE_REQUIRE_INTEGRATION=1` — падают с той же причиной. Если раннер задан, но
на хосте не запущен, тесты наката и отката падают с `runner_unavailable`: перед прогоном раннер
запускается на хосте. Каждый тест с БД получает на сервере `lbfr-db-test` свою БД `t_<uuid>`
и удаляет её после себя. Тесты шаблонов операций без CLI `backlog` плагина `formular`
пропускаются.

Те же команды прогоняет workflow [`checks`](./.github/workflows/checks.yml) — на каждый PR в `main`,
на push в `main` и первым job'ом сценария `release`. Совпадение перечня выше и шагов workflow
проверяет тест `tests/release/test_checks_workflow.py`: новая проверка добавляется в оба места
одной правкой.

Перед тестами job `checks` поднимает окружение интеграционных тестов скриптом
`tools/ci/integration-env.sh`: сервер `lbfr-db-test`, образ Liquibase и раннер на машине CI
с разовым токеном. Скрипт задаёт `FORGE_REQUIRE_INTEGRATION=1`, поэтому интеграционный тест,
не получивший окружения, в CI падает, а не пропускается. В CI с причиной пропускаются только
тесты шаблонов операций: CLI `backlog` плагина `formular` там нет. При сбое job печатает журнал
раннера и `docker compose logs lbfr-db-test`.
Зелёный `checks` — обязательное условие слияния PR в `main` (см. [защиту `main`](#защита-main)).

Полный перечень целей `make` печатает `make help`.
