## Локальная настройка

Регистрация харнесов локальна и в индекс git не входит: каталоги `.claude/` и `.zcode/` создаёт
сам разработчик под свои инструменты.

1. Правила — плагин tessera. Харнес с маркетплейсами плагинов ставит его из маркетплейса
   `united-software-platform/tessera`; харнес без поддержки плагинов — клон репозитория tessera
   и `scripts/bootstrap.sh <каталог навыков проекта>` в нём.
1. Инструменты — `mise install`, затем `uv sync --frozen`: если mise не доверяет `mise.toml`, он
   называет команду `mise trust mise.toml`. Окружение `.venv` ставит CLI `forge` на `PATH` оболочки
   с активированным mise.
1. Секреты — скопировать `.env.example` в `.env` и заполнить значения.
1. Сервер и среда — `mise run env-up` поднимает демон `postgres` общего набора workspace,
   `mise run forge-env-up` создаёт целевую БД и кладёт драйвер Liquibase, `mise run forge-env-check`
   проверяет среду.
1. Навык `forge` — ссылка в каталоге навыков харнеса на `plugins/forge-plugin/skills/forge`.
1. Навыки OpenSpec разворачивает `openspec init` под выбранные харнесы; каталог `openspec/`
   со спецификациями уже лежит в репозитории:

   ```bash
   mise exec -- openspec init --tools <список-харнесов> --language ru --scope project
   ```

Полный перечень задач окружения печатает `mise tasks`.

## Репозиторий разработки

Этот репозиторий — место разработки forge, а не целевой проект, и настраивается иначе.

- **Принятое состояние вне коммитов.** Корень принятого состояния задаёт `mise.toml`:
  `FORGE_ACCEPTED_DIR=.forge/db`. Каталог `.forge/` и `/db/` исключены `.gitignore`, поэтому
  проверочные прогоны `/forge` в git не попадают.
- **Целевая БД — база на общем экземпляре.** `lbfr_forge` на демоне `postgres` workspace;
  интеграционные тесты создают на нём же базы `t_<идентификатор>` и удаляют их после себя.
  Перечень тестовых БД в `mise.toml` адресует целевую базу и шаблон префикса `t_*`.
- **Секреты — только `.env`.** Значение секции `[env]` файла `mise.toml` перекрывает `.env`,
  поэтому секреты в `mise.toml` не подставляются, а лежат в `.env` по именам из `.env.example`.
- **В поставку не входит.** `.gitignore`, `db/` и `backlog/` этого репозитория в целевой проект
  не переносятся: плагин не меняет в целевом проекте ни одного файла — шаблоны операций
  читаются из плагина. Локальные файлы forge в `.forge/` скрывает от git файл
  `.forge/.gitignore`, который кладёт `forge env up`.

## Блок бейджей

Блок бейджей стоит в [`README.md`](./README.md) между заголовком и назначением. Бейдж версии
динамический: номер читается сервисом бейджей из `VERSION`, ручной копии номера в `README.md` нет.
Бейдж проверок показывает статус последнего прогона сценария
[`checks`](./.github/workflows/checks.yml) в ветке `main`: тесты, линтер, форматирование и типы
идут в нём одним заданием, поэтому бейдж у них один.

| Бейдж | Источник значения | Режим | Цель ссылки |
|-------|-------------------|-------|-------------|
| `version` | `VERSION` в ветке `main` | `dynamic/regex` | `./VERSION` |
| `license` | статическое значение, носителя нет | — | `./LICENSE` |
| `checks` | статус сценария `checks.yml` в ветке `main` | badge GitHub Actions | страница прогонов `checks.yml` в `main` |

Ограничения блока:

- **репозиторий должен быть доступен анонимно** — сервис бейджей читает `VERSION`
  без аутентификации;
- **бейдж показывает версию ветки `main`** — номер в рабочей ветке он покажет только после слияния;
- **перенос версии из `VERSION` ломает бейдж молча** — после правки носителя бейдж
  проверяется глазами;
- **переименование `checks.yml` ломает бейдж проверок** — путь сценария записан в URL бейджа,
  и после переименования бейдж правится той же правкой;
- **бейдж проверок показывает только ветку `main`** — статус PR и рабочих веток виден на странице
  PR, а не в бейдже.

## Выпуск версии

Номер версии хранится только в `VERSION`: `pyproject.toml` берёт его при сборке, `uv.lock` номера
проекта не держит. Вручную номер в `VERSION` не правится — его повышает сценарий
[`release`](./.github/workflows/release.yml).

Номер повторяют манифесты плагина и запись маркетплейса — их разработчик правит сам
в подготовительном изменении `prepare-release-X.Y.Z`, до выпуска. Релизный сценарий сверяет их
с выпускаемым номером и при расхождении завершается ошибкой до любой записи.

Версия выпускается ручным запуском сценария `release` на вкладке Actions репозитория. Ветка
запуска — `main`: из другой ветки сценарий завершается ошибкой, а пока файла сценария нет в `main`,
GitHub ручной запуск не показывает. Единственный ввод — разряд:

| Разряд | Что меняет | Пример |
|--------|------------|--------|
| `patch` | Последнее число | `1.4.3` → `1.4.4` |
| `minor` | Среднее число, последнее обнуляется | `1.4.3` → `1.5.0` |
| `major` | Первое число, остальные обнуляются | `1.4.3` → `2.0.0` |

Сначала прогон вызывает workflow [`checks`](./.github/workflows/checks.yml) на коммите `main`:
если проверки не пройдены, сценарий завершается ошибкой, и ничего не записывается. Затем гейт
задач выпуска находит на GitHub milestone `vX.Y.Z` нового номера: если его нет либо в нём открыта
задача или PR, сценарий завершается ошибкой с их перечнем, и ничего не записывается. Затем прогон
записывает новый номер в `VERSION`, создаёт релизный коммит по `GIT-021`, ставит аннотированный
тег `vX.Y.Z`, публикует коммит и тег ключом развёртывания и создаёт GitHub Release по тегу через
`GITHUB_TOKEN`. По этому тегу CLI ставится в целевой проект изолированным инструментом — путь
установки описан в [`README.md`](./README.md).

Предусловия и сбои:

- **Состав выпуска — milestone `vX.Y.Z` нового номера.** Его заводят до выпуска, в том числе
  для `patch`, и привязывают к нему задачи выпуска. Задачи закрываются строками `Closes #N`
  в PR, слитом в `main` до запуска сценария; задачу, которую не успели сделать, переносят
  в другой milestone явно.
- **Версия плагина — в манифестах до выпуска.** В подготовительном изменении номер вносится
  в оба манифеста плагина и в запись маркетплейса; сценарий их не пишет.
- **Ключ развёртывания `release` с правом записи и секрет Actions `RELEASE_DEPLOY_KEY` заведены**
  (см. [защиту `main`](#защита-main)). Без секрета сценарий завершается ошибкой до записи `VERSION`.
  Если push ключом отклонён, прогон падает на публикации коммита — до тега и релиза.
- **Сбой шага «Публикация релиза» после push тега** доводится вручную той же командой:
  `gh release create vX.Y.Z --verify-tag --title vX.Y.Z --generate-notes`. Повторный запуск
  сценария выпустил бы уже следующую версию.

### Защита main

Ветка `main` защищена ruleset'ом из [`.github/rulesets/main.json`](./.github/rulesets/main.json):
изменения попадают в неё только слиянием PR с зелёным job'ом `checks`, одобрения не требуются,
force-push и удаление ветки запрещены. Обход правил есть только у ключа развёртывания `release`,
которым сценарий публикует релизный коммит и тег; у администраторов обхода нет. Имя обязательной
проверки в файле совпадает с именем job'а в `checks.yml` — это сторожит тест
`tests/release/test_main_ruleset.py`.

Ruleset применяется к GitHub командой владельца после каждой правки файла; повторный запуск
ничего не меняет:

```bash
sh tools/github/apply-ruleset.sh .github/rulesets/main.json
```

| Код | Что значит | Что делается |
|-----|------------|--------------|
| `0` | Ruleset создан или обновлен | Правила проверяются: `gh api repos/{owner}/repo/rules/branches/main` |
| `1` | GitHub отклонил запрос | Проверяется право администрирования у `gh` и тело файла по тексту ошибки |
| `2` | Нет аргумента, файл не читается, в нём нет имени или `gh` не определил репозиторий | Команда повторяется из корня репозитория с путем к файлу |

Ключ развёртывания заводится и заменяется одними и теми же командами; закрытая часть остаётся
только в секрете. При замене старый ключ сначала удаляется: `gh repo deploy-key list`, затем
`gh repo deploy-key delete <id>`.

```bash
dir=$(mktemp -d)
ssh-keygen -t ed25519 -N "" -C release -f "$dir/release"
gh repo deploy-key add "$dir/release.pub" --allow-write --title release
gh secret set RELEASE_DEPLOY_KEY < "$dir/release"
rm -rf "$dir"
```

Если GitHub Actions не работает, PR в `main` не слить никому — это цена отказа от обхода
у администраторов. Владелец временно переводит ruleset в `disabled` в настройках репозитория
или через API, а после восстановления Actions возвращает правила командой применения выше.

## Проверки

Проверки запускаются до отправки изменений, каждая — своей задачей mise:

```bash
mise run lint             # линтер
mise run format-check     # форматирование
mise run types            # типы `src`
mise run test             # модульные и интеграционные тесты
```

Интеграционные тесты помечены маркером `integration`. Без учётных данных сервера тестов
(`FORGE_TEST_DB_USER`, `FORGE_TEST_DB_PASSWORD`) или без Liquibase с драйвером в `.forge/lib/`
они пропускаются с причиной, а при `FORGE_REQUIRE_INTEGRATION=1` — падают с той же причиной.
Если сервер задан, но не запущен, тесты наката и отката падают: недоступная среда не должна
выглядеть зелёным прогоном. Каждый тест с БД получает на общем экземпляре свою БД `t_<uuid>`
и удаляет её после себя. Тесты шаблонов операций без CLI `backlog` плагина `formular`
пропускаются.

Те же задачи прогоняет workflow [`checks`](./.github/workflows/checks.yml) — на каждый PR в `main`,
на push в `main` и первым job'ом сценария `release`. Совпадение перечня выше и шагов workflow
проверяет тест `tests/release/test_checks_workflow.py`: новая проверка добавляется в оба места
одной правкой.

Перед тестами job `checks` поднимает окружение интеграционных тестов скриптом
`tools/ci/integration-env.sh`: сервер PostgreSQL машины CI, инструменты mise и драйвер Liquibase.
Скрипт задаёт `FORGE_REQUIRE_INTEGRATION=1`, поэтому интеграционный тест,
не получивший окружения, в CI падает, а не пропускается. В CI с причиной пропускаются только
тесты шаблонов операций: CLI `backlog` плагина `formular` там нет. При сбое job печатает журнал
сервера PostgreSQL.

Полный перечень задач окружения печатает `mise tasks`.

## Правила и процесс

Изменения ведутся через OpenSpec: предложение, реализация и архивация изменения — навыки
`openspec-propose`, `openspec-apply-change` и `openspec-archive-change`. Перечень лежащих изменений
печатает `openspec list`.

Нормы читаются из плагина tessera через его навык-каталог; документ называет норму кодом правила.

| Вопрос | Норма |
|--------|-------|
| Формат сообщения коммита | `GIT-009` |
| Запрет служебных подписей агентов в коммитах и PR/MR | `GIT-012` |
| Когда коммитить и отправлять изменения | `GIT-015` |
| Сообщение релизного коммита | `GIT-021` |
| Оформление документов | `DOC-014` |
| Какой материал в каком документе | `DGN-001` |
| Направление зависимостей между слоями | `CLAR-001` |
| Состав окружения и сервисов | `ENV-002` |
| Задачи mise вместо `Makefile` | `ENV-006` |
