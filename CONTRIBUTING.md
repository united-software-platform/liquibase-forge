## Репозиторий разработки

Этот репозиторий — место разработки forge, а не целевой проект, и настраивается иначе.

- **Корень принятого состояния.** В `.env` вручную задаётся `FORGE_ACCEPTED_DIR=.forge/db`:
  `make forge-env-sync` дописывает значение `db` из шаблона. Каталог `.forge/` и `/db/` исключены
  `.gitignore`, поэтому проверочные прогоны `/forge` в git не попадают.
- **Что не входит в поставку forge.** `.gitignore`, `db/` и `backlog/` этого репозитория в целевой
  проект не переносятся: поставленный `.gitignore` скрыл бы принятое состояние и след целевого
  проекта. Файлы обмена в `.forge/` скрывает от git собственный `.forge/.gitignore`, который
  создают `forge` и шлюз.

## Отличия от поставки kit'а

Четыре файла поставки SDD Developer Kit изменены под forge, и их контрольные суммы расходятся
с `.sdd-kit-manifest.json`.

| Файл | Отличие | Основание |
|------|---------|-----------|
| [docker-compose.yml](./docker-compose.yml) | Секция `include:` файла [docker/lbfr/docker-compose.yaml](./docker/lbfr/docker-compose.yaml) | Окружение kit'а и инструмент lbfr описаны разными файлами: сервис агента `claude` остаётся в файле kit'а, сервисы инструмента живут в подкаталоге, и в корне Compose находит один файл |
| [Makefile](./Makefile) | Цели `liquibase-update`, `liquibase-rollback` и `forge-env-*` | Раннер исполняет только цели `make`: через них агент без Docker запускает Liquibase и готовит окружение |
| [.env.example](./.env.example) | Блоки переменных Liquibase Forge | Адреса и учётные данные БД, хостовый порт целевой БД, перечень тестовых БД, корень принятого состояния, версии образов |
| [tools/host-runner/runner.py](./tools/host-runner/runner.py) | Цели шлюза и `forge-env-*` в `ALLOWED_TARGETS` | Раннер отказывает целям вне белого списка; поддержки дополнительного списка из `.env` в kit'е пока нет |

После правки белого списка в `runner.py` раннер на хосте перезапускается: список читается при старте.

Установщик kit'а слияния не делает и при обновлении перезаписывает эти файлы целиком. Порядок
обновления такой: установщик запускается с тегом версии, после чего проектные версии четырёх файлов
возвращаются из резервной копии, а манифест сохраняет контрольные суммы kit'а — так следующее
обновление снова распознаёт отличия как конфликт. Требования к поставке — в спецификации
[sdd-kit-delivery](./openspec/specs/sdd-kit-delivery/spec.md).

## Блок бейджей

Блок бейджей стоит в [`README.md`](./README.md) между заголовком и назначением. Бейдж версии
динамический: номер читается сервисом бейджей из `pyproject.toml`, ручной копии номера в `README.md` нет.

| Бейдж | Источник значения | Режим | Цель ссылки |
|-------|-------------------|-------|-------------|
| `version` | `pyproject.toml` в ветке `main`, `$.project.version` | `dynamic/toml` | `./pyproject.toml` |
| `license` | статическое значение, носителя нет | — | `./LICENSE` |

Ограничения блока:

- **репозиторий должен быть доступен анонимно** — сервис бейджей читает `pyproject.toml`
  без аутентификации;
- **бейдж показывает версию ветки `main`** — номер в рабочей ветке он покажет только после слияния;
- **перенос версии из `pyproject.toml` ломает бейдж молча** — после правки носителя бейдж
  проверяется глазами.

## Проверки

Проверки запускаются в контейнере агента до отправки изменений, каждая — своей командой:

```bash
uv run pytest                 # модульные и интеграционные тесты
uv run ruff check             # линтер
uv run ruff format --check    # форматирование
uv run mypy src               # типы
sh tools/make-lint/check.sh   # объём секций Makefile
```

Интеграционные тесты помечены маркером `integration`. Без `FORGE_TEST_DB_HOST` или без настроенного
раннера (`AGENT_RUNNER_URL`, `AGENT_RUNNER_TOKEN`) они пропускаются с причиной. Каждый тест с БД
получает на сервере `lbfr-db-test` свою БД `t_<uuid>` и удаляет её после себя.

Полный перечень целей `make` печатает `make help`.
