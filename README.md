# liquibase-forge

[![версия Liquibase Forge из pyproject.toml](https://img.shields.io/badge/dynamic/toml?url=https%3A%2F%2Fraw.githubusercontent.com%2Funited-software-platform%2Fliquibase-forge%2Fmain%2Fpyproject.toml&query=%24.project.version&label=version&color=007EC6)](./pyproject.toml)
[![лицензия MIT](https://img.shields.io/badge/license-MIT-007EC6)](./LICENSE)

Liquibase Forge строит модель данных PostgreSQL по намерению, сформулированному агенту, проверяет её
накатом, сверкой и откатом и принимает в `db/` вашего проекта. Здесь — путь от установки до первой
принятой модели; другие задачи — в [документе кейсов](./docs/use-cases.md), правка самого forge —
в [`CONTRIBUTING.md`](./CONTRIBUTING.md).

## Что нужно

- SDD Developer Kit в вашем проекте и запущенный на хосте раннер целей `make`: окружение forge
  готовят цели из белого списка раннера, и агент вызывает их сам. Как запустить раннер и когда
  его перезапускать — в [tools/host-runner/README.md](./tools/host-runner/README.md).
- Docker Compose 2.20 или новее: `docker-compose.yml` kit'а подключает `docker/lbfr/docker-compose.yaml`
  секцией `include:`, которую старые версии не знают.
- `python3` на хосте: на нём работают раннер и шлюз Liquibase `tools/liquibase/gateway.py`.
  Сторонние пакеты не нужны.
- Доступ в сеть при первой сборке: образ `lbfr-liquibase` загружает драйвер PostgreSQL.

## Шаг 1. Установить Liquibase Forge

Скопируйте из этого репозитория в корень вашего проекта:

- `src/forge/`, `pyproject.toml`, `uv.lock` — CLI `forge`;
- `tools/liquibase/` и `tools/forge-env/` — шлюз Liquibase и подготовку окружения;
- `docker/lbfr/` — сервисы БД и образ Liquibase;
- `.claude/skills/forge/` — навык `forge`.

Затем перенесите в файлы kit'а вашего проекта отличия forge, перечисленные в разделе
[«Отличия от поставки kit'а»](./CONTRIBUTING.md#отличия-от-поставки-kitа): секцию `include:`
в `docker-compose.yml`, цели в `Makefile`, переменные в `.env.example` и цели в белом списке
`tools/host-runner/runner.py`. После правки `runner.py` перезапустите раннер — белый список
читается при старте.

`.gitignore`, `db/` и `backlog/` этого репозитория не копируйте: они настроены для разработки forge
и скрыли бы от git ваше принятое состояние и след операций.

## Шаг 2. Подготовить окружение

Попросите агента выполнить цели по порядку:

```text
make forge-env-sync
make forge-env-check
make forge-env-up
```

Цели дописывают в `.env` недостающие переменные Liquibase Forge, проверяют Compose и состав
сервисов, собирают образ Liquibase и поднимают БД `lbfr-db` и `lbfr-db-test` до `healthy`. Что
делает каждая цель, печатает `make help`. Сервисы `claude` и `lbfr-liquibase` стоят под профилями:
`docker compose up` их не запускает.

> **Важно:** сессия агента получает `.env` только при старте. После правки `.env` перезапустите её,
> иначе агент будет подключаться к БД по прежним адресам. Цели шлюза загружают `.env` сами
> и перезапуска раннера не требуют.

Подробнее — [кейс 2](./docs/use-cases.md#кейс-2-хочу-поднять-окружение-а-хостовый-порт-занят).

## Шаг 3. Подключить плагин backlog@formular

Навык `forge` исполняет беклог операции через CLI `backlog` плагина `formular`. Подключите маркетплейс
`formular` и установите из него плагин в область проекта:

```bash
claude plugin marketplace add united-software-platform/formular
claude plugin install backlog@formular
```

Перезапустите сессию агента: CLI `backlog` появляется в `PATH` только после перезапуска.

## Шаг 4. Построить модель

Опишите агенту нужную модель через навык `forge`:

```text
/forge Справочник клиентов: id, email, имя, дата регистрации
```

Навык начинает операцию по намерению, исполняет её беклог до подтверждённой модели или трёх неудач
и возвращает итоговый отчёт. При успехе модель и changelog принимаются в корень принятого состояния
`FORGE_ACCEPTED_DIR` — по умолчанию `db/`.

По умолчанию режим `interactive`: навык останавливается на стоп-знаках перед созданием модели,
накатом и закрытием и ждёт вашего решения. Ключ `--mode auto` заменяет стоп-знаки автоматическими
гейтами.

Подробнее — [кейс 3](./docs/use-cases.md#кейс-3-хочу-продолжить-остановленную-операцию).

## Шаг 5. Закоммитить результат

Коммит делаете вы. Итоговый отчёт называет в `commit.files` файлы для коммита: след операции
`backlog/forge-model/<штамп>/` и беклоги попыток `backlog/forge-apply/<штамп>-<N>/`, а при успехе —
и принятое состояние. След объясняет, как получена модель, а после неудачи — почему схема
не изменилась.

Коммитьте файлы и каталоги из `commit.files`, а не всё рабочее дерево (`git add -A`): след
остановленной операции и беклоги других операций `formular` в `backlog/` тоже видны git, но в коммит
этой операции не входят.

> **Внимание:** если по рекомендации плагина `formular` в `.gitignore` вашего проекта есть строка
> `backlog/*`, удалите её — иначе след не попадёт в коммит.

## Ограничения

- **Установщика нет.** forge переносится в проект копированием файлов по шагу 1; при обновлении
  forge копирование и перенос отличий повторяются вручную.
- **Liquibase 5.x распространяется под лицензией FSL**, а не Apache 2.0. FSL ограничивает только
  конкурирующее коммерческое использование Liquibase.
- **Корень следа — только `backlog/`.** `BACKLOG_ROOT` для операций forge не поддерживается: шаблоны
  называют пути следа литералами.
