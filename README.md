Liquibase Forge строит модель данных PostgreSQL по намерению, сформулированному агенту, проверяет её
накатом, сверкой и откатом и принимает в `db/` вашего проекта. Здесь — путь от установки до первой
принятой модели; другие задачи — в [документе кейсов](./docs/use-cases.md), правка самого forge —
в [`CONTRIBUTING.md`](./CONTRIBUTING.md).

## Что нужно

- SDD Developer Kit 1.5.0 или новее в вашем проекте и запущенный на хосте раннер целей `make`:
  окружение forge готовят цели из белого списка раннера, и агент вызывает их сам. Как запустить
  раннер и когда его перезапускать — в [tools/host-runner/README.md](./tools/host-runner/README.md).
- Docker Compose 2.20 или новее: `docker-compose.yml` kit'а подключает `docker/lbfr/docker-compose.yaml`
  секцией `include:`, которую старые версии не знают.
- `curl` и `tar` на хосте — для установщика; `python3` на хосте — на нём работают раннер и шлюз
  Liquibase `tools/liquibase/gateway.py`. Сторонние пакеты не нужны.
- Доступ в сеть при первой сборке: образ `lbfr-liquibase` загружает драйвер PostgreSQL.

## Шаг 1. Установить Liquibase Forge

Запустите установщик в корне вашего проекта на хосте:

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/liquibase-forge/main/install.sh | sh
```

Без ключей ставится последний релиз forge; другую версию задаёт `--ref` с тегом из
[Releases](https://github.com/united-software-platform/liquibase-forge/releases):

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/liquibase-forge/main/install.sh | sh -s -- --ref vX.Y.Z
```

Установщик сначала печатает план — какие файлы и блоки он создаст, обновит и оставит как есть, —
и только потом пишет. Посмотреть план без записи можно ключом `--dry-run`, перечень ключей печатает
ключ `--help`. CLI `forge` ложится в `tools/forge/` и с `pyproject.toml` вашего проекта
не пересекается. В файлы вашего проекта, которые план называет блоками, установщик пишет только
между строками `# >>> liquibase-forge` и `# <<< liquibase-forge`: ваш текст вне маркеров он
не трогает.

Если вы правили файл поставки или блок forge, установщик отметит это в плане как правку владельца
и спросит, перезаписать ли её; `--yes` перезаписывает без вопроса. Если forge уже перенесён в проект
вручную, его файлы попадут в план как правки владельца, а прежние отличия forge без маркеров
установщик назовёт — удалите их сами, иначе они задвоятся.

| Код | Что значит | Что делаю |
|-----|------------|-----------|
| `0` | Forge установлен или менять нечего | Перезапустите раннер на хосте — белый список целей читается при старте — и переходите к шагу 2 |
| `1` | Нет SDD Developer Kit 1.5.0+, версия forge не поддерживает установку, место вставки блока не найдено или вы отказались от перезаписи правки | Сделайте то, что назвало сообщение. Если место вставки не найдено, вставьте напечатанный блок вручную вместе с маркерами в названный файл и запустите установщик снова |
| `2` | Неизвестный или взаимоисключающие ключи, нет `curl`, `tar` или сети, у forge нет опубликованного релиза | Исправьте вызов или окружение; без релиза укажите версию ключом `--ref` |

Закоммитьте поставку вместе с `.forge-manifest.json`: по суммам в манифесте следующий запуск
установщика отличает ваши правки от прежней версии forge. После переустановки kit'а запустите
установщик forge снова — он вернёт блоки, которые kit стёр.

Подробнее — [кейс 7](./docs/use-cases.md#кейс-7-хочу-обновить-forge-до-новой-версии).

## Шаг 2. Подготовить окружение

Попросите агента выполнить цели по порядку:

```text
make forge-env-sync
make forge-env-check
make forge-env-up
```

Цели дописывают в `.env` недостающие переменные Liquibase Forge, проверяют Compose и состав
сервисов, собирают образ Liquibase и поднимают БД `lbfr-db` и `lbfr-db-test` до `healthy`. Что
делает каждая цель, печатает `make help`. Сервисы `claude` и `lbfr-liquibase` стоят под профилями:
`docker compose up` их не запускает.

Имена контейнеров начинаются с префикса проекта `LBFR_CONTAINER_PREFIX`: `make forge-env-sync`
выводит его из имени каталога проекта, например `shop-lbfr-db`. Поэтому окружения forge в разных
проектах на одном хосте не делят имена контейнеров. Если `make forge-env-up` сообщает, что имя
или порт занят другим проектом, поменяйте в `.env` названную им переменную.

> **Важно:** сессия агента получает `.env` только при старте. После правки `.env` перезапустите её,
> иначе агент будет подключаться к БД по прежним адресам. Цели шлюза загружают `.env` сами
> и перезапуска раннера не требуют.

Подробнее — [кейс 2](./docs/use-cases.md#кейс-2-хочу-поднять-окружение-а-хостовый-порт-занят),
[кейс 14](./docs/use-cases.md#кейс-14-хочу-поднять-forge-в-двух-проектах-на-одном-хосте).

## Шаг 3. Подключить плагин backlog@formular

Навык `forge` исполняет беклог операции через CLI `backlog` плагина `formular`. Подключите маркетплейс
`formular` и установите из него плагин в область проекта:

```bash
claude plugin marketplace add united-software-platform/formular
claude plugin install backlog@formular
```

Перезапустите сессию агента: CLI `backlog` появляется в `PATH` только после перезапуска.

## Шаг 4. Построить модель

Опишите агенту нужную модель через навык `forge`:

```text
/forge Справочник клиентов: id, email, имя, дата регистрации
```

Модель описывает таблицы и колонки с типами, первичный ключ, обязательность (NOT NULL), наборы
уникальности, внешние ключи между таблицами, автоинкремент колонки и перечень допустимых значений;
что из этого можно попросить — в [docs/model-format.md](./docs/model-format.md). Связь,
автоинкремент и перечень называйте в намерении прямо:

```text
/forge Заказы: id — автоинкремент, клиент — ссылка на справочник клиентов, сумма, дата заказа,
источник — одно из collector, manual
```

Навык начинает операцию по намерению, исполняет её беклог до подтверждённой модели или трёх неудач
и возвращает итоговый отчёт. При успехе модель и changelog принимаются в корень принятого состояния
`FORGE_ACCEPTED_DIR` — по умолчанию `db/`.

По умолчанию режим `interactive`: навык останавливается на стоп-знаках перед созданием модели,
накатом и закрытием и ждёт вашего решения. Ключ `--mode auto` заменяет стоп-знаки автоматическими
гейтами.

Строки справочных таблиц принятой модели заполняет тот же навык с ключом `--seed`; при успехе
в корень принятого состояния принимаются `seed.yaml` и changelog данных:

```text
/forge --seed "статусы заказа: черновик, оплачен, отменён"
```

Подробнее — [кейс 3](./docs/use-cases.md#кейс-3-хочу-продолжить-остановленную-операцию),
[кейс 11](./docs/use-cases.md#кейс-11-хочу-понять-почему-операция-закрылась-с-failure),
[кейс 13](./docs/use-cases.md#кейс-13-хочу-бросить-открытую-операцию),
[кейс 15](./docs/use-cases.md#кейс-15-хочу-заполнить-справочник),

## Шаг 5. Закоммитить результат

Коммит делаете вы. Итоговый отчёт называет в `commit.files` файлы для коммита: след операции
`backlog/forge-model/<штамп>/` и беклоги попыток `backlog/forge-apply/<штамп>-<N>/`, а при успехе —
и принятое состояние. След объясняет, как получена модель, а после неудачи или отказа — почему
схема не изменилась.

Коммитьте файлы и каталоги из `commit.files`, а не всё рабочее дерево (`git add -A`): след
остановленной операции и беклоги других операций `formular` в `backlog/` тоже видны git, но в коммит
этой операции не входят.

> **Внимание:** если по рекомендации плагина `formular` в `.gitignore` вашего проекта есть строка
> `backlog/*`, удалите её — иначе след не попадёт в коммит.

Подробнее — [кейс 10](./docs/use-cases.md#кейс-10-хочу-накатить-принятые-изменения-на-бд-своего-приложения).

## Ограничения

- **Только PostgreSQL и схема `public`.** Сверка видит таблицы, колонки, первичные ключи, наборы
  уникальности, перечни значений и FK; представления и индексы вне модели, а `CHECK` выражается
  только перечнем значений одной колонки —
  см. [docs/reconciliation.md](./docs/reconciliation.md#ограничения-и-допущения). Внешний ключ
  создаётся с действием `NO ACTION`: `ON DELETE`, `ON UPDATE` и отложенные ограничения
  (`DEFERRABLE`) не поддерживаются — см. [docs/model-format.md](./docs/model-format.md#ограничения-и-допущения).
- **Только БД из перечня тестовых.** Накат и откат идут лишь на БД из `FORGE_TEST_DB_ALLOWLIST`;
  production БД forge не предназначен. Схемой БД должен управлять только Liquibase Forge —
  см. [docs/migration.md](./docs/migration.md#ограничения-и-допущения).
- **Смена типа, NULL и первичного ключа не поддерживается.** Такую модель `forge generate`
  отклоняет, переименование выражается удалением и добавлением —
  см. [docs/migration.md](./docs/migration.md#неподдерживаемые-изменения).
- **Удаление теряет данные.** Откат удаления восстанавливает структуру, но не данные; в режиме
  `auto` удаления требуют ключа `--allow-drop` —
  см. [docs/operation.md](./docs/operation.md#согласие-на-удаления).
- **Новая колонка NOT NULL в справочнике с данными недоступна.** Если у таблицы есть строки
  в принятом seed, `forge generate` отклоняет такую колонку конфликтом `not_null_column_added`:
  добавьте колонку, допускающую NULL, и заполните её операцией seed —
  см. [docs/operation.md](./docs/operation.md#согласование-с-принятым-seed).
- **Не больше трёх попыток и одной открытой операции.** Закрытую операцию отменить нельзя —
  см. [docs/operation.md](./docs/operation.md#ограничения-и-допущения).
- **Установщик не удаляет forge.** Файлы, которые новая версия больше не поставляет, план называет,
  но удалять их и сам forge из проекта приходится вручную — порядок
  в [кейсе 12](./docs/use-cases.md#кейс-12-хочу-удалить-forge-из-проекта).
- **Liquibase 5.x распространяется под лицензией FSL**, а не Apache 2.0. FSL ограничивает только
  конкурирующее коммерческое использование Liquibase.
- **Корень следа — только `backlog/`.** `BACKLOG_ROOT` для операций forge не поддерживается: шаблоны
  называют пути следа литералами.
