# Сверка seed

Как Liquibase Forge выносит вердикт попытки seed: команда `forge reconcile-seed` сравнивает строки
таблиц seed тестовой БД с seed попытки и проверяет журнал Liquibase. Формат seed —
в [seed-format.md](./seed-format.md), changelog данных — в [seed-migration.md](./seed-migration.md).

## Команда

```bash
forge reconcile-seed --seed <каталог попытки>/seed.yaml --changelog <каталог попытки>/changelog.yaml \
  [--accepted-seed <принятый seed>] [--model <модель>]
```

Без `--accepted-seed` принятым seed служит `seed.yaml` корня принятого состояния
`FORGE_ACCEPTED_DIR` (по умолчанию `db/seed.yaml`), без `--model` — `model.yaml` того же корня,
см. [operation.md](./operation.md#принятое-состояние). Нет файла принятого seed — принятый seed
пуст. Нет файла модели по умолчанию — модель пуста.

| Код | Когда | `reconcile.json` |
|-----|-------|------------------|
| `0` | Расхождений нет, вердикт `success` | Записан |
| `1` | Есть расхождения, вердикт `failure` | Записан |
| `2` | Не заданы переменные окружения, БД вне перечня тестовых, БД недоступна, seed попытки, принятый seed, модель или changelog не прочитать либо они некорректны, некорректен `FORGE_ACCEPTED_DIR` | Не записан |

Целевая БД берётся из `FORGE_DB_*` и до подключения проверяется по `FORGE_TEST_DB_ALLOWLIST`.
Все файлы читаются и проверяются до подключения к БД. Вид ошибки в ответе с кодом `2`:
`settings_unavailable`, `database_not_allowed`, `database_unavailable`, `seed_unreadable`,
`seed_invalid`, `accepted_seed_invalid`, `model_unreadable`, `model_invalid`,
`changelog_unreadable`, `accepted_root_invalid`. Seed попытки некорректен, если он не проходит
`forge validate-seed`: нарушения перечисляет эта команда.

Код `1` — штатный исход: за ним идёт откат попытки, а расхождения ложатся в план правки seed
следующей попытки.

## Что сравнивается

Фактические строки читаются запросом к таблице напрямую через `psycopg`, а не из changelog.

| Объект | Сравнение |
|--------|-----------|
| Таблицы seed попытки | Строки сопоставляются в обе стороны по первичному ключу (Primary Key, PK): строка seed без строки БД и строка БД без строки seed. Таблица seed принадлежит seed целиком |
| Значения строки | Каждая колонка модели строки, найденной по PK, в нормализованной форме; колонка без ключа в seed ожидается NULL |
| Таблицы, убранные из seed | Таблица есть в принятом seed и отсутствует в seed попытки — ожидается пустой |
| Журнал Liquibase | Каждый changeset changelog попытки записан с тем же `id`, `author`, `filename` = `logicalFilePath` и `EXECTYPE = EXECUTED` — так же, как у `forge reconcile` |

Таблицы модели, которых нет ни в seed попытки, ни в принятом seed, не читаются, и их строки
расхождений не дают. Структура схемы не сверяется: seed её не меняет, расхождение структуры
с моделью находит сверка модели.

## Нормализация значений из БД

Значение `psycopg` переводится в сырое значение seed и приводится к типу колонки модели той же
фабрикой, что разбирает файл seed. Одна фабрика на обе стороны — гарантия, что разные записи
одного значения не дают расхождения.

| Тип модели | Значение `psycopg` | Нормализованная форма |
|------------|--------------------|-----------------------|
| `integer`, `bigint` | `int` | целое |
| `boolean` | `bool` | `true` или `false` |
| `string`, `text` | `str` | строка как есть |
| `decimal` | `Decimal` | десятичная запись без лишних нулей: `numeric 1.50` → `1.5` |
| `date` | `date` | `YYYY-MM-DD` |
| `timestamp` | `datetime` без смещения | ISO 8601 без хвостовых нулей дроби |
| `timestamp_tz` | `datetime` со смещением | момент в UTC с суффиксом `Z` |
| `uuid` | `UUID` | строка в нижнем регистре |

Так `valid_from: "2026-01-01T03:00:00+03:00"` из seed и момент `2026-01-01 00:00:00+00` из БД —
одно значение `2026-01-01T00:00:00Z`.

## Виды расхождений

Расхождение (Discrepancy) — то же понятие, что у сверки модели, с полем `key`: PK строки
отображением «колонка → значение». У расхождения журнала `key` равно `null`.

| Вид | Объект | Ожидаемое | Фактическое |
|-----|--------|-----------|-------------|
| `row_missing` | таблица и `key` | `present` | `absent` |
| `row_unexpected` | таблица и `key` | `absent` | значения строки по колонкам модели, например `[code=legacy, title=Устаревший]` |
| `value_mismatch` | таблица, `key` и колонка | значение seed, NULL — `null` | значение в БД, NULL — `null` |
| `changeset_not_executed` | `id` changeset | `EXECUTED` | `absent` или значение `EXECTYPE` |

Ожидаемое и фактическое — строки, как у сверки модели: значение записывается в нормализованной
форме, логическое — `true` или `false`, NULL — `null`. Отличие одной строки по нескольким колонкам
даёт по расхождению `value_mismatch` на колонку.

## Порядок расхождений

Порядок устойчив: повторная сверка неизменной БД даёт тот же перечень побайтово.

1. Таблицы seed попытки в порядке seed. Внутри таблицы — строки seed по порядку: для каждой
   `row_missing` либо `value_mismatch` по колонкам модели. Затем лишние строки по возрастанию PK.
1. Таблицы, убранные из seed, в порядке принятого seed: их строки по возрастанию PK.
1. Changeset в порядке changelog.

Возрастание PK задаёт PostgreSQL: строки читаются с `ORDER BY` по колонкам PK.

## Файл reconcile.json

Файл лежит рядом с changelog и совпадает с ответом команды. Пример — сверка seed попытки
из [примера changelog данных](./seed-migration.md#пример): у строки `draft` в БД остался прежний
заголовок, строка `new` не вставлена, строка `archived` не удалена. Значение `fee` строки `paid`
в БД — `numeric 12.50`, в seed — `"12.50"`, и расхождения по нему нет.

```json
{
  "seed": "backlog/forge-seed/20261025-101500/attempt-1/seed.yaml",
  "changelog": "backlog/forge-seed/20261025-101500/attempt-1/changelog.yaml",
  "database": "lbfr-db-test:5432/t_0001",
  "verdict": "failure",
  "discrepancies": [
    {
      "kind": "value_mismatch",
      "table": "order_status",
      "key": {"code": "draft"},
      "column": "title",
      "changeset": null,
      "expected": "Набросок",
      "actual": "Черновик",
      "message": "значение order_status[code=draft].title: ожидалось 'Набросок', в БД 'Черновик'"
    },
    {
      "kind": "row_missing",
      "table": "order_status",
      "key": {"code": "new"},
      "column": null,
      "changeset": null,
      "expected": "present",
      "actual": "absent",
      "message": "строки order_status[code=new] нет в БД"
    },
    {
      "kind": "row_unexpected",
      "table": "order_status",
      "key": {"code": "archived"},
      "column": null,
      "changeset": null,
      "expected": "absent",
      "actual": "[code=archived, group_code=active, title=Архив, fee=0]",
      "message": "лишняя строка order_status[code=archived]: в seed попытки её нет"
    }
  ]
}
```

Сообщения могут меняться, виды расхождений и поля — часть контракта.

## Ограничения и допущения

- **Ограничение:** NULL и строка `null` в полях `expected` и `actual` записываются одинаково.
  У `value_mismatch` их различает сообщение: строковое значение в нём взято в кавычки. В значениях
  строки `row_unexpected` они неразличимы.
- **Ограничение:** таблица seed читается целиком. Справочные данные малы по природе, таблицы вне
  seed не читаются.
- **Допущение:** схемой целевой БД управляет только Liquibase Forge. Если таблица seed удалена
  или колонка сменила тип между накатом и сверкой, запрос падает или значение не приводится
  к типу модели → код `2` с видом `database_unavailable` и диагностикой, а не вердикт.
- **Допущение:** порядок лишних строк задаёт сравнение PostgreSQL. Для текстового PK он зависит
  от правила сортировки БД, но на одной БД неизменен.
