# Кейсы Liquibase Forge

Что я делаю с Liquibase Forge, когда основного пути из [`README.md`](../README.md) мне мало: смотрю
схему клиентом, готовлю окружение с нуля, продолжаю остановленную операцию, переношу принятое
состояние, разрешаю накат на другую БД, меняю версию Liquibase, обновляю forge, разрешаю удаления
в режиме `auto`, меняю принятую модель, накатываю принятые изменения на БД приложения, разбираю
операцию, закрытую с `failure`, удаляю forge из проекта, бросаю открытую операцию, использую forge
в двух проектах workspace, заполняю справочник, убираю справочник из модели, переношу данные
целевой БД на общий экземпляр PostgreSQL и ставлю forge в проект вне workspace. Если я правлю сам forge — мне
в [`CONTRIBUTING.md`](../CONTRIBUTING.md).

## Кейс 1. Хочу посмотреть построенную схему клиентом с хоста

**Когда.** Модель принята, и я хочу посмотреть схему, которую построил Liquibase Forge, в `psql`
или в IDE на своей машине.

**Что делаю.** Подключаюсь к серверу PostgreSQL, на котором лежит целевая БД, с учётными данными
`FORGE_DB_USER` и `FORGE_DB_PASSWORD`. Внутри workspace это общий экземпляр на `localhost` и порту
`PG_PORT`, по умолчанию `5432`; имя базы — `FORGE_DB_NAME`:

```bash
psql -h localhost -p 5432 -U forge forge
```

Публикации портов больше нет: сервер слушает фиксированный localhost-порт, а forge берёт его
из `PG_PORT` каскада mise, вне workspace — `5432`.

**Что получаю.** Клиент показывает схему целевой БД такой, какой её оставила последняя операция.

**Если сервер не запущен.** Внутри workspace сервер — демон `postgres` общего набора: поднимаю
его задачей `mise run env-up`, состояние показывает `mise run env-status`. Вне workspace сервер
объявляет сам проект демоном в своём `mise.toml`.

## Кейс 2. Хочу подготовить окружение forge с нуля

**Когда.** В проекте установлены плагин forge и CLI, а среда ещё не готова: целевой базы нет,
драйвер Liquibase не загружен.

**Что делаю.** Объявляю координаты forge в `mise.toml` проекта, в секции `[env]`: `FORGE_DB_NAME`
и `FORGE_TEST_DB_ALLOWLIST` — обязательно, хост, порт и корень принятого состояния forge подставит
сам. Секреты — `FORGE_DB_PASSWORD` и учётные данные сервера тестов — кладу в `.env` по шаблону
`.env.example`. В оболочке с активированным mise поднимаю сервер и готовлю среду:

```bash
mise install
mise run env-up
forge env up
forge env check
```

`mise run env-up` поднимает общий набор workspace; вне workspace сервер запускает задача самого
проекта. Действую по коду `forge env check`:

| Код | Что значит | Что делаю |
|-----|------------|-----------|
| `0` | Среда готова | Запускаю первую операцию |
| `2` | Какая-то из проверок не пройдена — ответ перечисляет каждую с итогом и диагностикой | Устраняю причину по диагностике и повторяю проверку |

**Что получаю.** На сервере появились роль и база `FORGE_DB_NAME`, в `.forge/lib/` лежит драйвер
PostgreSQL, `forge env check` возвращает `0`.

**Если не вышло.**

- Проверка `database` не пройдена: сервер недоступен — смотрю `mise run env-status` внутри
  workspace; базы нет — выполняю `forge env up`.
- `forge env up` вернул `2` с недостающим правом: роли, из-под которой он работал, нельзя создавать
  роли и базы. Задаю в `.env` администратора сервера — `FORGE_DB_ADMIN_USER` и
  `FORGE_DB_ADMIN_PASSWORD`.
- Драйвер не загрузился: нет сети. Кладу файл драйвера в `.forge/lib/` вручную и повторяю
  `forge env check`.
- Проверка `liquibase` не пройдена: выполняю `mise install` — Liquibase и Java закреплены
  в `[tools]` файла `mise.toml`.

## Кейс 3. Хочу продолжить остановленную операцию

**Когда.** Операция forge остановилась — на стоп-знаке в режиме `interactive`, на непройденном
гейте или на ошибке окружения, — а модель ещё не принята.

**Что делаю.** Снова вызываю навык, намерение повторять не нужно:

```text
/forge
```

Навык находит открытую операцию через `forge status --latest`, при статусе `stopped` сам выполняет
`forge resume` и продолжает беклог с первой невыполненной задачи. Если я передам новое намерение,
навык его не примет и сообщит, что продолжает открытую операцию. Порядок работы навыка —
в разделе [«Навык forge»](./operation.md#навык-forge) справочника операции.

**Что получаю.** Операция доходит до итогового отчёта. Остановка попытку не тратит: из трёх попыток
я теряю только неудачные.

## Кейс 4. Хочу перенести корень принятого состояния

**Когда.** Принятые модель и changelog должны лежать не в `db/`, а в другом каталоге проекта.

**Что делаю.** Задаю в `mise.toml` проекта, в секции `[env]`, переменную `FORGE_ACCEPTED_DIR` —
относительный путь внутри проекта —
и вручную переношу каталог принятого состояния на новое место, например `git mv db schema/db`.
Затем прошу агента выполнить `forge status --latest`: проверка `accepted` называет итоговый корень.
Действую по коду возврата:

| Код | Что значит | Что делаю |
|-----|------------|-----------|
| `0` | Среда в порядке, `accepted` называет новый корень | Запускаю следующую операцию |
| `2` | Проверка среды не пройдена — например, путь абсолютный или выходит за корень проекта | Исправляю `FORGE_ACCEPTED_DIR` на относительный путь внутри проекта и повторяю проверку |

Правила корня описаны в разделе [«Принятое состояние»](./operation.md#принятое-состояние)
справочника операции.

**Что получаю.** Следующая операция начинается с принятой модели из нового корня, и `forge close`
принимает результат туда же.

**Если не вышло.**

- Если операция началась с пустой принятой модели, каталог не перенесён: forge принятые файлы
  не переносит, переношу их сам.
- Если агент по-прежнему видит прежний корень, его оболочка получила переменные при активации
  mise: открываю новую оболочку или выполняю команду через `mise x --`.

## Кейс 5. Хочу разрешить накат на другую БД

**Когда.** Команда `forge` отклоняет накат или откат кодом `2` с видом `database_not_allowed`:
нужной БД нет в перечне тестовых.

**Что делаю.** Дописываю БД в `FORGE_TEST_DB_ALLOWLIST` в `mise.toml` проекта — это несекретная
координата, она живёт в секции `[env]`. Записи — `хост:порт/имя` через запятую:

- имя базы — точное совпадение: `localhost:5432/shop_forge`;
- `*` целиком — любая база сервера: `localhost:5432/*`;
- `t_*` — любая база, чьё имя начинается с префикса: `localhost:5432/t_*`.

```toml
[env]
FORGE_TEST_DB_ALLOWLIST = "localhost:5432/shop_forge,localhost:5432/t_*"
```

**Что получаю.** `forge apply` и `forge rollback` принимают добавленную БД. Пустой перечень
запрещает любой запрос — так forge защищён от наката на незаданную БД.

**Если не вышло.**

- Команда вернула код `2` с видом `settings_unavailable` и называет запись перечня: звёздочка
  допускается одна и только в конце имени — записи вроде `t_*_x` и `*x` отклоняются.
- На общем экземпляре workspace не записываю `*` для всего сервера: такая запись открыла бы
  и базы соседних проектов — группу баз задаёт префикс.
- Команда обращается к БД по прежним адресам: оболочка получила переменные при активации mise.
  Открываю новую оболочку или выполняю команду через `mise x --`.

## Кейс 6. Хочу сменить версию Liquibase или драйвера PostgreSQL

**Когда.** Мне нужна другая версия Liquibase или драйвера PostgreSQL, чем та, с которой forge
работает сейчас.

**Что делаю.** Версию Liquibase меняю в `mise.toml` проекта — `[tools]`, `liquibase` — и выполняю
`mise install`. Версию драйвера задаю парой переменных в `.env`: `FORGE_LIQUIBASE_DRIVER_VERSION`
и `FORGE_LIQUIBASE_DRIVER_SHA256`. Сумму считаю сам от файла, скачанного из репозитория Maven, —
репозиторий публикует для драйвера только подпись и контрольные суммы SHA-1 и MD5:

```bash
curl -fsSLO https://repo1.maven.org/maven2/org/postgresql/postgresql/<версия>/postgresql-<версия>.jar
sha256sum postgresql-<версия>.jar
```

Затем выполняю `forge env up`: он положит драйвер новой версии в `.forge/lib/`.

**Что получаю.** Накат и откат идут новой версией: шлюз вызывает Liquibase из `PATH` и подключает
драйвер из `.forge/lib/`.

**Если не вышло.**

- `forge env up` вернул `2` с указанием на версию драйвера: версия задана без контрольной суммы.
  Сумма обязательна — без неё forge не загружает файл.
- `forge env check` называет прежнюю версию Liquibase: оболочка получила инструменты при активации
  mise. Открываю новую оболочку или выполняю команду через `mise x --`.
- Файл прежней версии драйвера остался в `.forge/lib/` — он не мешает; удаляю, если не нужен.

## Кейс 7. Хочу обновить forge до новой версии

**Когда.** На странице Releases репозитория forge вышла версия новее установленной. Плагин и CLI
обновляю вместе: они выпускаются одним тегом.

**Что делаю.** Обновляю плагин: в ZCode обновляю маркетплейс `liquibase-forge` и нажимаю Update
в разделе плагина, в Claude Code выполняю `/plugin update forge-plugin@liquibase-forge`. Затем
ставлю CLI с тегом новой версии и проверяю среду:

```bash
uv tool install "liquibase-forge @ git+https://github.com/united-software-platform/liquibase-forge@vX.Y.Z"
forge env up
forge env check
```

`forge env up` запускаю на всякий случай: он идемпотентен, а новая версия могла сменить драйвер
или потребовать новых объектов на сервере.

**Что получаю.** `uv tool list` называет новую версию CLI, `forge env check` возвращает `0`.
Файлы проекта не изменились: плагин ничего в них не пишет.

**Если не вышло.**

- Версии разошлись — `uv tool list` называет не тот номер: повторяю установку CLI с тегом новой
  версии, команда заменяет прежнюю версию.
- `forge env check` называет непройденной проверку `liquibase`: открываю новую оболочку —
  инструменты приходят при активации mise.
- Открытую операцию, начатую до обновления, продолжаю после него: её беклог уже порождён
  и исполняется по своему тексту.
- Проект с прежней поставкой установщика kit'а сначала перевожу на плагин —
  [кейс 12](#кейс-12-хочу-удалить-forge-из-проекта), раздел о прежней поставке.

## Кейс 8. Хочу разрешить удаления в режиме auto

**Когда.** Я веду операцию в режиме `auto`, и модель должна удалить таблицу или колонку.
Без моего согласия `forge generate` отклоняет такую модель с видом `drop_not_allowed`,
и операция останавливается.

**Что делаю.** Даю согласие при начале операции — ключ `--allow-drop` действует только вместе
с `--mode auto`:

```text
/forge Убрать таблицу legacy_log --mode auto --allow-drop
```

Если операция уже остановилась на `drop_not_allowed`, продолжаю её с согласием, намерение
не повторяю:

```text
/forge --allow-drop
```

Порядок согласия описан в разделе [«Согласие на удаления»](./operation.md#согласие-на-удаления)
справочника операции.

**Что получаю.** Changelog попытки содержит удаления, гейт перед накатом записывает решение
с обоснованием, а итоговый отчёт перечисляет удаления в `destructive`. Остановка на
`drop_not_allowed` попытку не тратит.

**Если не вышло.**

- Признак согласия после начала операции не снимается. Поэтому перед продолжением
  с `--allow-drop` сверяю перечень объектов в ответе `drop_not_allowed`: данные удалённых таблиц
  и колонок после успешного наката не вернуть, откат восстанавливает только структуру.
- Если навык ответил, что ключ не принят, операция исполняется, а не остановлена: дожидаюсь
  остановки и повторяю вызов.

## Кейс 9. Хочу изменить уже принятую модель

**Когда.** Модель уже принята, и мне нужна новая таблица, колонка или связь либо прежняя
больше не нужна.

**Что делаю.** Начинаю новую операцию и описываю в намерении изменение, а не всю модель:

```text
/forge Добавить клиентам телефон и убрать дату регистрации
```

Модель попытки строится от принятой модели, а changelog — из их разницы: новые и удалённые
таблицы, колонки, наборы уникальности и внешние ключи. Переименование forge не отличает
от удаления с добавлением: changelog удаляет прежнюю колонку вместе с данными и добавляет новую.
В режиме `interactive` стоп-знак перед накатом показывает changelog и отдельно перечисляет
удаления — решаю, накатывать ли. В режиме `auto` удаления требуют моего согласия — см.
[кейс 8](#кейс-8-хочу-разрешить-удаления-в-режиме-auto).

**Что получаю.** В корне принятого состояния, по умолчанию `db/`, `model.yaml` заменён новой
моделью, а changelog операции лёг в `changelog/` и подключён в конец `changelog/master.yaml`.

**Если не вышло.**

- Смену типа колонки, её допустимости NULL и первичного ключа forge не поддерживает:
  `forge generate` отклоняет такую модель, и агент сам убирает неподдерживаемое изменение
  из модели. Поэтому статус `success` ещё не значит, что намерение выполнено целиком: сверяю
  итоговую модель из отчёта с тем, что просил. Перечень таких изменений — в разделе
  [«Неподдерживаемые изменения»](./migration.md#неподдерживаемые-изменения).
- Вместо смены типа прошу явно удалить колонку и добавить новую с нужным типом — данные колонки
  при этом теряются — либо добавить колонку с другим именем и оставить прежнюю.
- Обязательная колонка в непустой таблице, а также внешний ключ или набор уникальности, которым
  не отвечают строки таблицы, не накатятся: накат завершится ошибкой Liquibase, и попытка будет
  неуспешной. Добавляю колонку необязательной либо сначала привожу данные в порядок.

## Кейс 10. Хочу накатить принятые изменения на БД своего приложения

**Когда.** Модель принята и закоммичена, и ту же схему нужно получить в БД моего приложения —
локальной, стенда или боевой.

**Что делаю.** Forge с такой БД не работает: его накат ограничен перечнем тестовых БД. Накатываю
принятый `master.yaml` своим Liquibase 5.x с драйвером PostgreSQL из корня проекта — так же,
как его накатывает шлюз forge:

```bash
LIQUIBASE_COMMAND_URL=jdbc:postgresql://localhost:5432/app \
LIQUIBASE_COMMAND_USERNAME=app \
LIQUIBASE_COMMAND_PASSWORD=change_me \
liquibase update --changelog-file=db/changelog/master.yaml
```

Если корень принятого состояния перенесён (кейс 4), путь `--changelog-file` беру от него.

**Что получаю.** Liquibase накатывает changelog операций в порядке их принятия и пропускает уже
накатанные: повторный запуск ничего не меняет. Журнал `databasechangelog` записывает каждый
changeset с файлом `db/changelog/<штамп>.yaml` независимо от того, где лежит корень, поэтому
перенос корня не заставит Liquibase накатить их заново.

**Если не вышло.**

- Накат идёт без гейтов, сверки и отката forge — отвечаю за него сам. Схемой БД приложения
  должны управлять только эти changelog'и: объекты, созданные в ней иначе, forge не видел.
- Changelog с удалениями теряет данные удалённых таблиц и колонок. Перед накатом на БД
  с ценными данными сверяю перечень удалений в отчётах операций и делаю резервную копию.

## Кейс 11. Хочу понять, почему операция закрылась с failure

**Когда.** Навык вернул отчёт со статусом `failure`: три попытки не дали модели, которую подтвердила
сверка, и схема осталась такой, какой была до операции.

**Что делаю.** Если отчёта уже нет перед глазами, прошу агента собрать его снова:

```bash
forge report --operation backlog/forge-model/<штамп>/tasks.md
```

Ненулевой код здесь — ответ на статус `failure`, а не сбой команды; коды `forge report` —
в [таблице команд](./operation.md#команды). В отчёте по каждой попытке из
`attempts` смотрю вердикт, расхождения сверки в `reconcile` и итог отката в `rollback`; что значит
каждое поле — в разделе [«Итоговый отчёт»](./operation.md#итоговый-отчёт). Файлы попытки лежат
в `backlog/forge-model/<штамп>/attempt-N/`: модель `model.yaml`, changelog `changelog.yaml`,
вывод наката `apply.json`, сверка `reconcile.json` и откат `rollback.json`.

Причину ищу так:

| Что вижу в попытке | Где подробности | Что меняю в намерении |
|--------------------|-----------------|-----------------------|
| Накат завершился ошибкой Liquibase | Вывод и диагностика Liquibase в `apply.json` | Объект, на котором упал накат: имя, тип или связь |
| Расхождение типа колонки `column_type_mismatch` | `expected` и `actual` в `reconcile.json` | Называю тип прямо — из [перечня типов](./model-format.md#типы-колонок) |
| Нет набора уникальности или внешнего ключа (`unique_missing`, `foreign_key_missing`) | `expected` в `reconcile.json` | Называю колонки набора и таблицу, на которую ведёт связь |

Остальные виды расхождений и их поля — в разделе [«Виды расхождений»](./reconciliation.md#виды-расхождений).
С исправленным намерением начинаю новую операцию: закрытая операция не продолжается.

**Что получаю.** Знаю, на чём споткнулась каждая попытка, и формулирую намерение, которое это
обходит. После `failure` откат каждой попытки подтверждён, схема БД и корень принятого состояния
прежние. След операции коммичу — его перечисляет поле `commit.files` отчёта: он объясняет, почему
схема не изменилась.

**Если не вышло.**

- Навык не дошёл до `failure`, а остановился на откате попытки: в её `rollback.json` —
  `verified: false`, операция осталась открытой, и закрыть её нельзя. Смотрю в `rollback.json`
  непройденные проверки в `checks` и причину в `fallback_reason`, устраняю её — чаще всего это
  недоступный Liquibase или ошибка шлюза — и вызываю навык снова: он повторит откат той же попытки.
  Если доводить операцию я больше не хочу, бросаю её — см.
  [кейс 13](#кейс-13-хочу-бросить-открытую-операцию): отказ тоже начинает с отката этой попытки.
- Если в `checks` не прошла проверка `accepted_restored`, перед повтором убеждаюсь по выводу шлюза
  в поле `fallback`, что принятый `master.yaml` накатывается: повторный откат эту проверку
  не повторяет.
- След не попал в коммит — в `.gitignore` осталась строка `backlog/*`; см.
  [шаг 4](../README.md#шаг-4-закоммитить-результат) `README.md`.

## Кейс 12. Хочу удалить forge из проекта

**Когда.** Forge в проекте больше не нужен. Плагин и CLI сами ничего в проекте не удаляют —
убираю только то, что мне больше не нужно.

**Что делаю.** Иду по порядку.

1. Убеждаюсь, что открытых операций нет: `forge status --latest` называет `operation: null`.
   Открытую бросаю — [кейс 13](#кейс-13-хочу-бросить-открытую-операцию).
1. Удаляю плагин: в ZCode — Personal → liquibase-forge → удалить Liquibase Forge (и Backlog
   (formular), если он больше не нужен), в Claude Code — `/plugin uninstall forge-plugin@liquibase-forge`.
1. Удаляю CLI, если его не использует ни один проект:

   ```bash
   uv tool uninstall liquibase-forge
   ```

1. Убираю из проекта локальные файлы и след операций — след, если он мне больше не нужен:

   ```bash
   rm -rf .forge
   rm -rf backlog/forge-model backlog/forge-seed backlog/forge-apply backlog/forge-seed-apply
   ```

   Принятое состояние — `db/` или каталог из `FORGE_ACCEPTED_DIR` — оставляю: это схема моего
   проекта, её changelog накатывается и без forge —
   [кейс 10](#кейс-10-хочу-накатить-принятые-изменения-на-бд-своего-приложения).
1. Убираю из `mise.toml` и `.env` координаты и секреты forge; инструменты `uv`, `java` и `liquibase`
   — если их не использует ничего другое.
1. Удаляю базу и роль проекта на сервере, если они больше не нужны: `DROP DATABASE <имя>` и
   `DROP ROLE <роль>` клиентом PostgreSQL под администратором сервера.

**Что получаю.** Навык `/forge` больше не вызывается, файлов forge в проекте не осталось;
`git status` показывает удаление следа операций, если он был закоммичен. Коммичу удаление.

**Если не вышло.** `/forge` по-прежнему вызывается: сессия харнеса начата до удаления плагина —
перезапускаю её.

### Проект с прежней поставкой установщика

До плагина forge ставился установщиком: он копировал файлы поставки в проект и вставлял блоки
в файлы SDD Developer Kit. Такой проект перевожу на плагин так.

1. Не оставляю открытых операций и выгружаю данные целевой БД клиентом PostgreSQL из контейнера
   `lbfr-db`, пока тот работает, —
   [кейс 17](#кейс-17-хочу-перенести-данные-целевой-бд-на-общий-экземпляр-workspace).
1. Удаляю контейнеры прежнего окружения и нахожу его сеть — Compose добавляет к имени сети имя
   проекта:

   ```bash
   docker compose --profile tools rm -s -f lbfr-db lbfr-db-test lbfr-liquibase
   docker network ls --filter name=lbfr-net
   ```

   Удаляю каталог данных `data/lbfr-db`, найденную сеть по имени из вывода и собранный образ
   Liquibase. Файлы `data/lbfr-db` принадлежат пользователю PostgreSQL в контейнере, поэтому
   каталог удаляю одноразовым контейнером образа БД, а `data/` — только если он опустел:

   ```bash
   docker run --rm -v "$PWD/data:/data" "$(sed -n 's/^LBFR_POSTGRES_IMAGE=//p' .env)" rm -rf /data/lbfr-db
   rmdir data 2>/dev/null
   docker network rm <проект>_lbfr-net
   docker image rm "$(sed -n 's/^LBFR_LIQUIBASE_IMAGE=//p' .env)"
   ```

   `docker compose down` не подходит: он остановил бы и сервисы самого проекта.
1. Удаляю файлы поставки по перечню `files` из `.forge-manifest.json`, затем каталог CLI вместе
   с его окружением uv и опустевшие каталоги:

   ```bash
   sed -n '/"files"/,/"blocks"/s/.*"path": "\([^"]*\)".*/\1/p' .forge-manifest.json | xargs rm -f --
   rm -rf tools/forge
   find tools docker .claude templates -type d -empty -delete 2>/dev/null
   ```

1. В редакторе удаляю блоки forge — строки от `# >>> liquibase-forge` до `# <<< liquibase-forge`
   включительно — в `Makefile`, `.env.example`, `docker-compose.yml`, `tools/host-runner/runner.py`
   и `.gitignore`. В `docker-compose.yml` убираю и строку `include:`, если под ней не осталось
   подключений, в `.gitignore` — пустую строку перед блоком.
1. В `.env` удаляю блок, который начинается строкой
   `# Liquibase Forge: добавлено make forge-env-sync`, — переменные `FORGE_*` и `LBFR_*`. Затем
   удаляю каталог `.forge/` и файл `.forge-manifest.json`.
1. Перезапускаю раннер на хосте: белый список целей он читает при старте.
1. Ставлю плагин и CLI по [шагу 1](../README.md#шаг-1-установить-плагин-и-cli), объявляю окружение
   по [шагу 2](../README.md#шаг-2-подготовить-окружение), восстанавливаю данные в базу на общем
   экземпляре — [кейс 17](#кейс-17-хочу-перенести-данные-целевой-бд-на-общий-экземпляр-workspace).

## Кейс 13. Хочу бросить открытую операцию

**Когда.** Операция открыта — я отказал на стоп-знаке или она остановилась на гейте либо ошибке
окружения, — и я передумал: доводить её до конца не хочу, а новое намерение навык не примет,
пока она открыта.

**Что делаю.** Вызываю навык с ключом и причиной, без намерения и других ключей:

```text
/forge --abandon "передумал: таблица заказов будет в другом сервисе"
```

Навык находит открытую операцию, выполняет `forge abandon` и возвращает отчёт `forge report`.
Стоп-знака нет ни в `interactive`, ни в `auto`: сам вызов с ключом — моё решение. Начатые попытки
откатываются по убыванию номера, в том числе накатанная попытка с вердиктом `success`; попытку
с уже подтверждённым откатом навык не трогает. Порядок и коды — в разделе
[«Отказ от операции»](./operation.md#отказ-от-операции) справочника операции.

**Что получаю.** Операция закрыта статусом `abandoned`, моя причина — в `stop_reason` отчёта. Схема
тестовой БД такая, какой была до операции, корень принятого состояния — `db/` или каталог
из `FORGE_ACCEPTED_DIR` — не тронут. Следующий `/forge` с намерением начинает новую операцию.
След брошенной операции коммичу — его перечисляет поле `commit.files` отчёта, файлов принятого
состояния в нём нет.

**Если не вышло.**

- Навык ответил, что бросать нечего, — открытой операции нет: начинаю новую с намерением.
- Отказ вернул `refused`: откат попытки не подтверждён, операция осталась открытой. Смотрю
  `rollback.json` попытки, как в [кейсе 11](#кейс-11-хочу-понять-почему-операция-закрылась-с-failure),
  устраняю причину и вызываю `/forge --abandon` снова: подтверждённые откаты он не повторяет.
- Навык вернул диагностику окружения — Liquibase или БД недоступны: проверяю среду командой
  `forge env check`, устраняю причину по её диагностике и повторяю вызов. Операция при этом
  не остановлена и не брошена.
- Операцию сейчас исполняет агент в другой сессии — бросать её нельзя: сначала дожидаюсь
  остановки или стоп-знака.
- Ключ отклонён: я передал вместе с ним намерение, `--mode` или `--allow-drop`. Сначала бросаю
  операцию, новое намерение передаю следующим вызовом.

## Кейс 14. Хочу использовать forge в двух проектах workspace

**Когда.** Forge нужен в двух моих проектах workspace, а сервер PostgreSQL там один — общий
экземпляр.

**Что делаю.** Ничего не поднимаю и портов не выбираю. В каждом проекте задаю в `mise.toml` своё
имя целевой базы `FORGE_DB_NAME` — например `shop_forge` и `crm_forge` — и выполняю `forge env up`:
на общем сервере появляется отдельная база проекта.

**Что получаю.** Оба проекта работают с forge одновременно: у каждого своя база на общем
экземпляре, и накат в одном проекте не трогает другой. Тестовые базы `t_<идентификатор>` уникальны
по имени, и каждый тест удаляет свою.

**Если не вышло.**

- Имя базы совпало: оба проекта пишут в одну базу. Меняю `FORGE_DB_NAME` во втором проекте
  и выполняю `forge env up` там.
- Роль `FORGE_DB_USER` уже есть на сервере с другим паролем: `forge env up` существующую роль
  не меняет. Записываю её пароль в `FORGE_DB_PASSWORD` либо задаю другой `FORGE_DB_USER`.
- Накат отклонён с кодом `2`: база не входит в `FORGE_TEST_DB_ALLOWLIST` проекта — добавляю её
  в перечень, как в [кейсе 5](#кейс-5-хочу-разрешить-накат-на-другую-бд).

## Кейс 15. Хочу заполнить справочник

**Когда.** Модель принята, в ней есть справочные таблицы — статусы, типы, роли, — и я хочу, чтобы
их строки задавал проект: попадали в принятое состояние и changelog, а не вставлялись в БД руками.

**Что делаю.** Вызываю навык с ключом `--seed` и намерением. Если значения лежат в моём файле,
называю его ключом `--from` — путь относительный, внутри проекта, ключ повторяю по файлу:

```text
/forge --seed "статусы заказа: черновик, оплачен, отменён"
/forge --seed "статусы из выгрузки" --from data/statuses.csv
```

Операция идёт как операция модели, только артефакт попытки — `seed.yaml`, полное целевое
состояние строк. На стоп-знаке перед накатом я вижу changelog данных и отдельным перечнем —
строки, которые будут удалены. Формат seed — в [seed-format.md](./seed-format.md), порядок
операции — в разделе [«Операция seed»](./operation.md#операция-seed) справочника операции.

**Что получаю.** Строки справочников в тестовой БД совпадают с seed, сверка подтвердила их.
В корне принятого состояния появились `seed.yaml` и changelog данных, `master.yaml` дополнен
`include` после changelog модели. Отчёт называет число вставленных, изменённых и удалённых строк
по таблицам; файлы для коммита — в поле `commit.files`.

**Если не вышло.**

- Навык ответил, что открыта операция: одновременно открыта одна операция любого вида. Довожу
  её до конца или бросаю, как в [кейсе 13](#кейс-13-хочу-бросить-открытую-операцию).
- Ключ `--from` отклонён: путь абсолютный, выходит за проект, ведёт к несуществующему файлу либо
  передан без `--seed`. Кладу файл в проект и повторяю вызов с `--seed`.
- В режиме `auto` операция остановилась на `drop_not_allowed`: seed удаляет строки. Продолжаю
  с согласием, как в [кейсе 8](#кейс-8-хочу-разрешить-удаления-в-режиме-auto).
- Нужна новая обязательная колонка в справочнике с данными. Сначала операция модели добавляет
  колонку, допускающую NULL, затем операция seed заполняет её значения.

## Кейс 16. Хочу убрать справочник из модели

**Когда.** Справочная таблица или её колонка больше не нужна, а у справочника есть строки
в принятом seed.

**Что делаю.** Если убираю колонку — вызываю навык с намерением модели, как в
[кейсе 9](#кейс-9-хочу-изменить-уже-принятую-модель): колонку справочника удалять можно,
закрытие операции само уберёт её ключ из строк `seed.yaml`.

Если убираю таблицу — сначала операцией seed убираю её из seed, затем операцией модели удаляю
таблицу:

```text
/forge --seed "убрать справочник цветов статуса из seed"
/forge "удалить таблицу status_color"
```

Операция модели проверяет модель попытки по принятому seed: удаление таблицы, которая ещё есть
в seed, она отклоняет конфликтом `seeded_table_dropped`. Виды конфликтов — в разделе
[«Согласование с принятым seed»](./operation.md#согласование-с-принятым-seed).

**Что получаю.** Таблица или колонка удалена из модели и схемы, принятый `seed.yaml` проходит
проверку по принятой модели. Если закрытие операции модели правило `seed.yaml`, он входит
в `commit.files` отчёта вместе с моделью.

**Если не вышло.**

- `forge generate` вернул `seed_conflict`: модель попытки ломает принятый seed. Ответ называет
  таблицу и вид конфликта — выполняю операцию seed, которая снимает его, и повторяю операцию
  модели.
- В режиме `auto` удаление остановилось на `drop_not_allowed`: даю согласие, как в
  [кейсе 8](#кейс-8-хочу-разрешить-удаления-в-режиме-auto).

## Кейс 17. Хочу перенести данные целевой БД на общий экземпляр workspace

**Когда.** Проект переходит на новый forge: прежде целевая БД жила в контейнере `lbfr-db`
Docker Compose, теперь её место — база на общем экземпляре PostgreSQL workspace.

**Что делаю.** Пока старый контейнер работает, выгружаю его данные клиентом того же сервера:

```bash
docker compose exec -T lbfr-db pg_dump -U forge -d forge -Fc > forge.dump
```

Готовлю базу на общем экземпляре и загружаю дамп клиентом PostgreSQL не старше того, что его
делал:

```bash
forge env up
pg_restore -h localhost -p 5432 -U forge -d forge --no-owner --no-privileges forge.dump
```

Имя прежней базы задаю в `FORGE_DB_NAME` — тогда накат продолжится с того места, где остановился:
журнал `databasechangelog` приезжает вместе с данными. Проверяю среду командой `forge env check`,
схему смотрю клиентом, как в [кейсе 1](#кейс-1-хочу-посмотреть-построенную-схему-клиентом-с-хоста).
Старое окружение убираю по [кейсу 12](#кейс-12-хочу-удалить-forge-из-проекта).

**Что получаю.** Целевая БД на общем экземпляре с прежней схемой и данными, проверки среды
пройдены. Старый контейнер, его каталог данных и образ Liquibase больше не нужны.

**Если не вышло.**

- Дампа нет — старое окружение уже удалено. Схему собираю заново накатом принятого `master.yaml`,
  как в [кейсе 10](#кейс-10-хочу-накатить-принятые-изменения-на-бд-своего-приложения).
- `pg_restore` не читает дамп: клиент старше того, что его сделал. Беру клиент той же или более
  новой версии.
- `forge env up` отказался из-за существующей роли или прав администратора — действую, как
  в [кейсе 14](#кейс-14-хочу-использовать-forge-в-двух-проектах-workspace).

## Кейс 18. Хочу поставить forge в проект вне workspace

**Когда.** Мой проект лежит вне workspace: каскад mise не приносит ни сервер PostgreSQL, ни его
порт.

**Что делаю.** Объявляю сервер в `mise.toml` проекта тем же способом, что и корень workspace, —
демоном mise:

```toml
[settings]
experimental = true

[daemons.postgres]
preset = "postgres"
version = "18"
port = 5432
```

Пароль суперпользователя сервера задаю в `.env` переменной `POSTGRES_PASSWORD` — её читает пресет
демона; тем же значением заполняю `FORGE_DB_ADMIN_PASSWORD` из
[шага 2](../README.md#шаг-2-подготовить-окружение). Запускаю сервер и готовлю среду:

```bash
mise daemons start postgres
forge env up
forge env check
```

**Что получаю.** Сервер поднят демоном mise проекта, база и роль проекта созданы на нём,
`forge env check` возвращает `0`. Дальше — [шаг 3](../README.md#шаг-3-построить-модель) `README.md`.

**Если не вышло.**

- mise отвечает, что демоны — экспериментальная функция: в `mise.toml` нет `experimental = true`.
- Порт `5432` занят — например, сервером workspace на той же машине: меняю `port` демона и той же
  правкой указываю порт в координатах forge — `FORGE_DB_PORT` в `[env]` и тем же портом
  в `FORGE_TEST_DB_ALLOWLIST`.
- `forge env up` вернул `2`, не найдя сервер: демон не запущен — состояние показывает
  `mise daemons status`.
