# Кейсы Liquibase Forge

Что я делаю с Liquibase Forge, когда основного пути из [`README.md`](../README.md) мне мало: смотрю
схему с хоста, обхожу занятый порт, продолжаю остановленную операцию, переношу принятое состояние,
разрешаю накат на другую БД, меняю версию Liquibase, обновляю forge, разрешаю удаления в режиме
`auto`, меняю принятую модель, накатываю принятые изменения на БД приложения, разбираю операцию,
закрытую с `failure`, удаляю forge из проекта, бросаю открытую операцию и поднимаю forge в двух
проектах на одном хосте. Если я правлю сам forge — мне
в [`CONTRIBUTING.md`](../CONTRIBUTING.md).

## Кейс 1. Хочу посмотреть построенную схему клиентом с хоста

**Когда.** Модель принята, и я хочу посмотреть схему, которую построил Liquibase Forge, в `psql`
или в IDE на своей машине.

**Что делаю.** Подключаюсь к целевой БД `lbfr-db` по хостовому порту `FORGE_DB_HOST_PORT` из `.env`,
по умолчанию `11932`. Порт опубликован на всех интерфейсах хоста:

```bash
psql -h localhost -p 11932 -U forge forge
```

`FORGE_DB_PORT` — другой порт: по нему агент и шлюз обращаются к БД внутри сети Compose, и от
публикации он не зависит. Сервер тестов `lbfr-db-test` на хост не публикуется, с хоста к нему
не подключиться.

**Что получаю.** Клиент показывает схему БД `forge` такой, какой её оставила последняя операция.

**Если порт открыт наружу.** Порт виден всей сети хоста, а учётные данные по умолчанию —
`forge`/`forge`. Вне изолированной машины меняю `FORGE_DB_PASSWORD` либо закрываю порт. Docker
публикует порты собственными правилами iptables в обход `ufw` и подобных экранов: правило
`ufw deny` порт не закроет.

## Кейс 2. Хочу поднять окружение, а хостовый порт занят

**Когда.** `make forge-env-up` падает с `port is already allocated`: порт `FORGE_DB_HOST_PORT` занят
другим процессом на хосте.

**Что делаю.** Проверяю порт на хосте:

```bash
ss -ltn | grep -q ':11932 ' && echo "11932 занят" || echo "11932 свободен"
```

Подбираю свободный порт из диапазона проекта `11900–11999` по
[DOCK-008](../rules/docker.md#порты-dock-008) — в том же диапазоне и порт раннера `AGENT_RUNNER_PORT`.
Записываю его в `FORGE_DB_HOST_PORT` в `.env` и прошу агента снова выполнить `make forge-env-up`.

**Что получаю.** `make forge-env-up` пересоздаёт контейнер `lbfr-db` на новом порту, данные тома
`lbfr-db-data` сохраняются.

**Если не вышло.** Если `make forge-env-check` завершается ошибкой и называет `FORGE_DB_HOST_PORT`,
переменной нет в `.env` — прошу агента выполнить `make forge-env-sync`, она допишет переменную
из `.env.example`, не трогая заданные значения. Если порт занят контейнером другого моего проекта
с forge, `make forge-env-up` называет его сам — это
[кейс 14](#кейс-14-хочу-поднять-forge-в-двух-проектах-на-одном-хосте).

## Кейс 3. Хочу продолжить остановленную операцию

**Когда.** Операция forge остановилась — на стоп-знаке в режиме `interactive`, на непройденном
гейте или на ошибке окружения, — а модель ещё не принята.

**Что делаю.** Снова вызываю навык, намерение повторять не нужно:

```text
/forge
```

Навык находит открытую операцию через `forge status --latest`, при статусе `stopped` сам выполняет
`forge resume` и продолжает беклог с первой невыполненной задачи. Если я передам новое намерение,
навык его не примет и сообщит, что продолжает открытую операцию. Порядок работы навыка —
в разделе [«Навык forge»](./operation.md#навык-forge) справочника операции.

**Что получаю.** Операция доходит до итогового отчёта. Остановка попытку не тратит: из трёх попыток
я теряю только неудачные.

## Кейс 4. Хочу перенести корень принятого состояния

**Когда.** Принятые модель и changelog должны лежать не в `db/`, а в другом каталоге проекта.

**Что делаю.** Задаю в `.env` переменную `FORGE_ACCEPTED_DIR` — относительный путь внутри проекта —
и вручную переношу каталог принятого состояния на новое место, например `git mv db schema/db`.
Затем прошу агента выполнить `forge status --latest`: проверка `accepted` называет итоговый корень.
Действую по коду возврата:

| Код | Что значит | Что делаю |
|-----|------------|-----------|
| `0` | Среда в порядке, `accepted` называет новый корень | Запускаю следующую операцию |
| `2` | Проверка среды не пройдена — например, путь абсолютный или выходит за корень проекта | Исправляю `FORGE_ACCEPTED_DIR` на относительный путь внутри проекта и повторяю проверку |

Правила корня описаны в разделе [«Принятое состояние»](./operation.md#принятое-состояние)
справочника операции.

**Что получаю.** Следующая операция начинается с принятой модели из нового корня, и `forge close`
принимает результат туда же.

**Если не вышло.**

- Если операция началась с пустой принятой модели, каталог не перенесён: forge принятые файлы
  не переносит, переношу их сам.
- Если агент по-прежнему видит прежний корень, перезапускаю сессию агента: `.env` она получает
  только при старте.

## Кейс 5. Хочу разрешить накат на другую БД

**Когда.** Шлюз Liquibase отклоняет накат или откат: нужной БД нет в перечне разрешённых.

**Что делаю.** Дописываю БД в `FORGE_TEST_DB_ALLOWLIST` в `.env`. Записи — `хост:порт/имя` через
запятую, `*` на месте имени разрешает любую БД сервера:

```bash
FORGE_TEST_DB_ALLOWLIST=lbfr-db:5432/forge,lbfr-db-test:5432/*
```

**Что получаю.** Шлюз принимает накат и откат на добавленную БД. Пустой перечень запрещает любой
запрос — так шлюз защищён от наката на незаданную БД.

**Если не вышло.** Цели шлюза загружают `.env` сами, поэтому раннер перезапускать не нужно. Если
агент обращается к БД по прежним адресам, перезапускаю сессию агента: `.env` она получает только
при старте.

## Кейс 6. Хочу сменить версию Liquibase или драйвера PostgreSQL

**Когда.** Мне нужна другая версия Liquibase или драйвера PostgreSQL, чем закреплённая в `.env`.

**Что делаю.** Меняю в `.env` `LBFR_LIQUIBASE_BASE_IMAGE` и/или `LBFR_LIQUIBASE_POSTGRESQL_DRIVER`
и вместе с ними `LBFR_LIQUIBASE_IMAGE`: имя собранного образа включает обе версии. Затем прошу агента
выполнить `make forge-env-up`.

**Что получаю.** Compose собирает образ `lbfr-liquibase` заново, и накат идёт новой версией.

**Если не вышло.**

- Если накат идёт прежней версией, имя `LBFR_LIQUIBASE_IMAGE` не изменилось, и Compose взял уже
  собранный образ — меняю имя.
- После правки образов перезапускаю раннер и сессию агента, как требует комментарий
  в `.env.example`.

## Кейс 7. Хочу обновить forge до новой версии

**Когда.** На странице Releases репозитория forge вышла версия новее той, что записана
в `tools/forge/VERSION` моего проекта.

**Что делаю.** Сначала смотрю план без записи — без `--ref` установщик берёт последний релиз,
с `--ref vX.Y.Z` — названную версию:

```bash
curl -fsSL https://raw.githubusercontent.com/united-software-platform/liquibase-forge/main/install.sh | sh -s -- --dry-run
```

В плане проверяю две пометки: «правка владельца» — файл поставки или блок, который я менял, его
установщик перезапишет только с моего согласия; «больше не поставляется» — файл прежней версии,
которого в новой нет, его установщик не удаляет. Запускаю ту же команду без `--dry-run` и отвечаю
на вопрос о правках. Затем перезапускаю раннер на хосте и прошу агента выполнить
`make forge-env-sync` и `make forge-env-check` — новая версия могла принести новые переменные
окружения.

**Что получаю.** В `tools/forge/VERSION` и в поле `forge_version` файла `.forge-manifest.json` —
новый номер. Коммичу поставку вместе с `.forge-manifest.json`.

**Если не вышло.**

- Если я отказался перезаписать правку, установщик ничего не записал: сохраняю правку отдельно
  или соглашаюсь на перезапись и запускаю его снова. Что значит каждый код возврата, —
  в таблице [шага 1](../README.md#шаг-1-установить-liquibase-forge) `README.md`.
- Файлы с пометкой «больше не поставляется» удаляю сам, если они мне не нужны.
- Если план обновил `docker/lbfr/` или `docker/liquibase/`, прошу агента выполнить
  `make forge-env-up`: сервисы и образ Liquibase пересоберутся по новой версии.

## Кейс 8. Хочу разрешить удаления в режиме auto

**Когда.** Я веду операцию в режиме `auto`, и модель должна удалить таблицу или колонку.
Без моего согласия `forge generate` отклоняет такую модель с видом `drop_not_allowed`,
и операция останавливается.

**Что делаю.** Даю согласие при начале операции — ключ `--allow-drop` действует только вместе
с `--mode auto`:

```text
/forge Убрать таблицу legacy_log --mode auto --allow-drop
```

Если операция уже остановилась на `drop_not_allowed`, продолжаю её с согласием, намерение
не повторяю:

```text
/forge --allow-drop
```

Порядок согласия описан в разделе [«Согласие на удаления»](./operation.md#согласие-на-удаления)
справочника операции.

**Что получаю.** Changelog попытки содержит удаления, гейт перед накатом записывает решение
с обоснованием, а итоговый отчёт перечисляет удаления в `destructive`. Остановка на
`drop_not_allowed` попытку не тратит.

**Если не вышло.**

- Признак согласия после начала операции не снимается. Поэтому перед продолжением
  с `--allow-drop` сверяю перечень объектов в ответе `drop_not_allowed`: данные удалённых таблиц
  и колонок после успешного наката не вернуть, откат восстанавливает только структуру.
- Если навык ответил, что ключ не принят, операция исполняется, а не остановлена: дожидаюсь
  остановки и повторяю вызов.

## Кейс 9. Хочу изменить уже принятую модель

**Когда.** Модель уже принята, и мне нужна новая таблица, колонка или связь либо прежняя
больше не нужна.

**Что делаю.** Начинаю новую операцию и описываю в намерении изменение, а не всю модель:

```text
/forge Добавить клиентам телефон и убрать дату регистрации
```

Модель попытки строится от принятой модели, а changelog — из их разницы: новые и удалённые
таблицы, колонки, наборы уникальности и внешние ключи. Переименование forge не отличает
от удаления с добавлением: changelog удаляет прежнюю колонку вместе с данными и добавляет новую.
В режиме `interactive` стоп-знак перед накатом показывает changelog и отдельно перечисляет
удаления — решаю, накатывать ли. В режиме `auto` удаления требуют моего согласия — см.
[кейс 8](#кейс-8-хочу-разрешить-удаления-в-режиме-auto).

**Что получаю.** В корне принятого состояния, по умолчанию `db/`, `model.yaml` заменён новой
моделью, а changelog операции лёг в `changelog/` и подключён в конец `changelog/master.yaml`.

**Если не вышло.**

- Смену типа колонки, её допустимости NULL и первичного ключа forge не поддерживает:
  `forge generate` отклоняет такую модель, и агент сам убирает неподдерживаемое изменение
  из модели. Поэтому статус `success` ещё не значит, что намерение выполнено целиком: сверяю
  итоговую модель из отчёта с тем, что просил. Перечень таких изменений — в разделе
  [«Неподдерживаемые изменения»](./migration.md#неподдерживаемые-изменения).
- Вместо смены типа прошу явно удалить колонку и добавить новую с нужным типом — данные колонки
  при этом теряются — либо добавить колонку с другим именем и оставить прежнюю.
- Обязательная колонка в непустой таблице, а также внешний ключ или набор уникальности, которым
  не отвечают строки таблицы, не накатятся: накат завершится ошибкой Liquibase, и попытка будет
  неуспешной. Добавляю колонку необязательной либо сначала привожу данные в порядок.

## Кейс 10. Хочу накатить принятые изменения на БД своего приложения

**Когда.** Модель принята и закоммичена, и ту же схему нужно получить в БД моего приложения —
локальной, стенда или боевой.

**Что делаю.** Forge с такой БД не работает: его накат ограничен перечнем тестовых БД. Накатываю
принятый `master.yaml` своим Liquibase 5.x с драйвером PostgreSQL из корня проекта — так же,
как его накатывает шлюз forge:

```bash
LIQUIBASE_COMMAND_URL=jdbc:postgresql://localhost:5432/app \
LIQUIBASE_COMMAND_USERNAME=app \
LIQUIBASE_COMMAND_PASSWORD=change_me \
liquibase update --changelog-file=db/changelog/master.yaml
```

Если корень принятого состояния перенесён (кейс 4), путь `--changelog-file` беру от него.

**Что получаю.** Liquibase накатывает changelog операций в порядке их принятия и пропускает уже
накатанные: повторный запуск ничего не меняет. Журнал `databasechangelog` записывает каждый
changeset с файлом `db/changelog/<штамп>.yaml` независимо от того, где лежит корень, поэтому
перенос корня не заставит Liquibase накатить их заново.

**Если не вышло.**

- Накат идёт без гейтов, сверки и отката forge — отвечаю за него сам. Схемой БД приложения
  должны управлять только эти changelog'и: объекты, созданные в ней иначе, forge не видел.
- Changelog с удалениями теряет данные удалённых таблиц и колонок. Перед накатом на БД
  с ценными данными сверяю перечень удалений в отчётах операций и делаю резервную копию.

## Кейс 11. Хочу понять, почему операция закрылась с failure

**Когда.** Навык вернул отчёт со статусом `failure`: три попытки не дали модели, которую подтвердила
сверка, и схема осталась такой, какой была до операции.

**Что делаю.** Если отчёта уже нет перед глазами, прошу агента собрать его снова:

```bash
sh tools/forge-env/forge.sh report --operation backlog/forge-model/<штамп>/tasks.md
```

Ненулевой код здесь — ответ на статус `failure`, а не сбой команды; коды `forge report` —
в [таблице команд](./operation.md#команды). В отчёте по каждой попытке из
`attempts` смотрю вердикт, расхождения сверки в `reconcile` и итог отката в `rollback`; что значит
каждое поле — в разделе [«Итоговый отчёт»](./operation.md#итоговый-отчёт). Файлы попытки лежат
в `backlog/forge-model/<штамп>/attempt-N/`: модель `model.yaml`, changelog `changelog.yaml`,
вывод наката `apply.json`, сверка `reconcile.json` и откат `rollback.json`.

Причину ищу так:

| Что вижу в попытке | Где подробности | Что меняю в намерении |
|--------------------|-----------------|-----------------------|
| Накат завершился ошибкой Liquibase | Вывод и диагностика Liquibase в `apply.json` | Объект, на котором упал накат: имя, тип или связь |
| Расхождение типа колонки `column_type_mismatch` | `expected` и `actual` в `reconcile.json` | Называю тип прямо — из [перечня типов](./model-format.md#типы-колонок) |
| Нет набора уникальности или внешнего ключа (`unique_missing`, `foreign_key_missing`) | `expected` в `reconcile.json` | Называю колонки набора и таблицу, на которую ведёт связь |

Остальные виды расхождений и их поля — в разделе [«Виды расхождений»](./reconciliation.md#виды-расхождений).
С исправленным намерением начинаю новую операцию: закрытая операция не продолжается.

**Что получаю.** Знаю, на чём споткнулась каждая попытка, и формулирую намерение, которое это
обходит. После `failure` откат каждой попытки подтверждён, схема БД и корень принятого состояния
прежние. След операции коммичу — его перечисляет поле `commit.files` отчёта: он объясняет, почему
схема не изменилась.

**Если не вышло.**

- Навык не дошёл до `failure`, а остановился на откате попытки: в её `rollback.json` —
  `verified: false`, операция осталась открытой, и закрыть её нельзя. Смотрю в `rollback.json`
  непройденные проверки в `checks` и причину в `fallback_reason`, устраняю её — чаще всего это
  недоступный раннер или ошибка шлюза — и вызываю навык снова: он повторит откат той же попытки.
  Если доводить операцию я больше не хочу, бросаю её — см.
  [кейс 13](#кейс-13-хочу-бросить-открытую-операцию): отказ тоже начинает с отката этой попытки.
- Если в `checks` не прошла проверка `accepted_restored`, перед повтором убеждаюсь по выводу шлюза
  в поле `fallback`, что принятый `master.yaml` накатывается: повторный откат эту проверку
  не повторяет.
- След не попал в коммит — в `.gitignore` осталась строка `backlog/*`; см.
  [шаг 5](../README.md#шаг-5-закоммитить-результат) `README.md`.

## Кейс 12. Хочу удалить forge из проекта

**Когда.** Forge в проекте больше не нужен. Установщик его не удаляет — убираю всё, что он
поставил, сам.

**Что делаю.** Иду по порядку. Сервисы удаляю первыми: пока `docker-compose.yml` подключает
`docker/lbfr/docker-compose.yaml`, Compose их видит, а после правки файла — уже нет.

1. На хосте в корне проекта удаляю контейнеры сервисов forge и нахожу их том и сеть — Compose
   добавляет к их именам имя проекта:

   ```bash
   docker compose --profile tools rm -s -f lbfr-db lbfr-db-test lbfr-liquibase
   docker volume ls --filter name=lbfr-db-data
   docker network ls --filter name=lbfr-net
   ```

   Удаляю найденные том и сеть по именам из вывода и собранный образ Liquibase:

   ```bash
   docker volume rm <проект>_lbfr-db-data
   docker network rm <проект>_lbfr-net
   docker image rm "$(sed -n 's/^LBFR_LIQUIBASE_IMAGE=//p' .env)"
   ```

   `docker compose down` не подходит: он остановил бы и сервисы самого проекта.
1. Удаляю файлы поставки по перечню `files` из `.forge-manifest.json`, затем каталог CLI вместе
   с его окружением uv и опустевшие каталоги:

   ```bash
   sed -n '/"files"/,/"blocks"/s/.*"path": "\([^"]*\)".*/\1/p' .forge-manifest.json | xargs rm -f --
   rm -rf tools/forge
   find tools docker .claude templates -type d -empty -delete 2>/dev/null
   ```

1. В редакторе удаляю блоки forge — строки от `# >>> liquibase-forge` до `# <<< liquibase-forge`
   включительно — в `Makefile`, `.env.example`, `docker-compose.yml`, `tools/host-runner/runner.py`
   и `.gitignore`. В `docker-compose.yml` убираю и строку `include:`, если под ней не осталось
   подключений, в `.gitignore` — пустую строку перед блоком.
1. В `.env` удаляю блок, который начинается строкой
   `# Liquibase Forge: добавлено make forge-env-sync`, — переменные `FORGE_*` и `LBFR_*`. Затем
   удаляю каталог `.forge/` и файл `.forge-manifest.json`.
1. Перезапускаю раннер на хосте: белый список целей он читает при старте.

**Что получаю.** `git status` показывает удалённые файлы поставки и `.forge-manifest.json` и правки
пяти файлов с блоками, `docker compose ps -a` — ни одного сервиса `lbfr-*`. Принятое состояние —
`db/` или каталог из `FORGE_ACCEPTED_DIR` — и след операций `backlog/forge-*` остаются: это файлы
проекта, а принятый changelog накатывается и без forge — см.
[кейс 10](#кейс-10-хочу-накатить-принятые-изменения-на-бд-своего-приложения). Коммичу удаление.

**Если не вышло.**

- Том не удаляется с ошибкой `volume is in use` — контейнер forge ещё остался: нахожу его
  `docker ps -a --filter name=lbfr` и повторяю шаг 1.
- `.forge-manifest.json` уже удалён — возвращаю его из git (`git checkout -- .forge-manifest.json`)
  и повторяю шаг 2.
- После правки в файлах остались строки forge вне маркеров — их могли вписать вручную до установки,
  установщик о таких строках предупреждал. Ищу их
  `grep -n "forge\|lbfr" Makefile .env.example docker-compose.yml .gitignore tools/host-runner/runner.py`
  и удаляю.

## Кейс 13. Хочу бросить открытую операцию

**Когда.** Операция открыта — я отказал на стоп-знаке или она остановилась на гейте либо ошибке
окружения, — и я передумал: доводить её до конца не хочу, а новое намерение навык не примет,
пока она открыта.

**Что делаю.** Вызываю навык с ключом и причиной, без намерения и других ключей:

```text
/forge --abandon "передумал: таблица заказов будет в другом сервисе"
```

Навык находит открытую операцию, выполняет `forge abandon` и возвращает отчёт `forge report`.
Стоп-знака нет ни в `interactive`, ни в `auto`: сам вызов с ключом — моё решение. Начатые попытки
откатываются по убыванию номера, в том числе накатанная попытка с вердиктом `success`; попытку
с уже подтверждённым откатом навык не трогает. Порядок и коды — в разделе
[«Отказ от операции»](./operation.md#отказ-от-операции) справочника операции.

**Что получаю.** Операция закрыта статусом `abandoned`, моя причина — в `stop_reason` отчёта. Схема
тестовой БД такая, какой была до операции, корень принятого состояния — `db/` или каталог
из `FORGE_ACCEPTED_DIR` — не тронут. Следующий `/forge` с намерением начинает новую операцию.
След брошенной операции коммичу — его перечисляет поле `commit.files` отчёта, файлов принятого
состояния в нём нет.

**Если не вышло.**

- Навык ответил, что бросать нечего, — открытой операции нет: начинаю новую с намерением.
- Отказ вернул `refused`: откат попытки не подтверждён, операция осталась открытой. Смотрю
  `rollback.json` попытки, как в [кейсе 11](#кейс-11-хочу-понять-почему-операция-закрылась-с-failure),
  устраняю причину и вызываю `/forge --abandon` снова: подтверждённые откаты он не повторяет.
- Навык вернул диагностику окружения — раннер или БД недоступны: поднимаю окружение и повторяю
  вызов. Операция при этом не остановлена и не брошена.
- Операцию сейчас исполняет агент в другой сессии — бросать её нельзя: сначала дожидаюсь
  остановки или стоп-знака.
- Ключ отклонён: я передал вместе с ним намерение, `--mode` или `--allow-drop`. Сначала бросаю
  операцию, новое намерение передаю следующим вызовом.

## Кейс 14. Хочу поднять forge в двух проектах на одном хосте

**Когда.** forge стоит в двух моих проектах, окружение одного уже поднято, а `make forge-env-up`
во втором завершается ошибкой: имя контейнера или хостовый порт `lbfr-db` занят контейнером
другого Compose-проекта. Сообщение называет контейнер, каталог проекта-владельца и переменную,
которую нужно поменять.

**Что делаю.** Меняю во втором проекте в `.env` переменную, которую назвало сообщение:

- `LBFR_CONTAINER_PREFIX` — задаю свой префикс: строчные латинские буквы, цифры и дефис, первый
  символ — буква или цифра. Префикс совпадает, когда `make forge-env-sync` вывел его из одинаковых
  имён каталогов либо я задал одно значение в обоих проектах;
- `FORGE_DB_HOST_PORT` — выбираю свободный порт из диапазона проекта по
  [DOCK-008](../rules/docker.md#порты-dock-008), как в
  [кейсе 2](#кейс-2-хочу-поднять-окружение-а-хостовый-порт-занят).

Прошу агента выполнить `make forge-env-check` и `make forge-env-up`.

**Что получаю.** Окружения обоих проектов работают одновременно: у каждого свои контейнеры
`<префикс>-lbfr-db` и `<префикс>-lbfr-db-test` и свой хостовый порт целевой БД.

**Если не вышло.**

- Каталоги проектов называются одинаково. Тогда у них совпадает и имя Compose-проекта, Compose
  считает их одним проектом, и `make forge-env-up` второго пересоздаёт контейнеры первого вместо
  отказа. Задаю во втором проекте в `.env` и свой `LBFR_CONTAINER_PREFIX`, и `COMPOSE_PROJECT_NAME`.
  Том `lbfr-db-data` второго проекта после этого новый и пустой.
- `make forge-env-check` называет `LBFR_CONTAINER_PREFIX`: переменной нет или значение
  недопустимо. Прошу агента выполнить `make forge-env-sync` либо исправляю значение сам.
- `make forge-env-sync` отказывает, потому что из имени каталога префикс не выводится, например
  в имени нет латиницы и цифр. Задаю `LBFR_CONTAINER_PREFIX` в `.env` вручную.
