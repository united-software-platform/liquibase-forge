# Сверка

Как Liquibase Forge выносит вердикт попытки: команда `forge reconcile` сравнивает фактическую
схему тестовой БД с моделью данных и проверяет запись Liquibase о changeset попытки.
Понятия сверки определены в [domain.md](./domain.md), changelog — в [migration.md](./migration.md).

## Команда

```bash
forge reconcile --model <каталог попытки>/model.yaml --changelog <каталог попытки>/changelog.yaml
```

| Код | Когда | `reconcile.json` |
|-----|-------|------------------|
| `0` | Расхождений нет, вердикт `success` | Записан |
| `1` | Есть расхождения, вердикт `failure` | Записан |
| `2` | Не заданы переменные окружения, БД вне перечня тестовых, БД недоступна, модель не прочитать или она некорректна, changelog не прочитать | Не записан |

Целевая БД берётся из `FORGE_DB_*` и до подключения проверяется по `FORGE_TEST_DB_ALLOWLIST`:
сверка тоже работает только с тестовой БД. Вид ошибки в ответе с кодом `2`:
`settings_unavailable`, `database_not_allowed`, `database_unavailable`, `model_unreadable`,
`model_invalid`, `changelog_unreadable`.

Код `1` — штатный исход: за ним идёт откат попытки, а расхождения ложатся в план правки модели
следующей попытки.

## Что сравнивается

Фактическая схема (Actual Schema) читается интроспекцией каталога PostgreSQL напрямую через
`psycopg`, а не из changelog.

| Объект | Сравнение |
|--------|-----------|
| Таблицы схемы `public` | В обе стороны: отсутствующая таблица модели и лишняя таблица БД. Таблицы журнала `databasechangelog` и `databasechangeloglock` исключены |
| Колонки таблицы | В обе стороны по имени; порядок колонок не сравнивается |
| Тип колонки | Тип модели с параметрами против фактического типа |
| Допустимость NULL | Итоговая допустимость модели с учётом первичного ключа и генерации значения против `NOT NULL` в БД |
| Генерация значения | `generated: identity` модели против `pg_attribute.attidentity`: `d` — identity `BY DEFAULT`, `a` — `ALWAYS`, пусто — без генерации |
| Первичный ключ (Primary Key, PK) | Упорядоченный список колонок; имя ограничения не сравнивается |
| Наборы уникальности | В обе стороны по составу колонок: порядок колонок и имя ограничения не сравниваются. Читаются ограничения `UNIQUE`, уникальные индексы без ограничения — нет |
| Перечни значений | В обе стороны по колонке и множеству значений: порядок значений и имя ограничения не сравниваются. Читаются ограничения `CHECK`; нераспознанное определение — лишнее ограничение |
| Внешние ключи (Foreign Key, FK) | В обе стороны по целевой таблице и парам «колонка FK → колонка цели»; порядок пар и имя ограничения не сравниваются |
| Журнал Liquibase | Каждый changeset changelog попытки записан с тем же `id`, `author`, `filename` = `logicalFilePath` и `EXECTYPE = EXECUTED` |

Отсутствующая таблица даёт одно расхождение, её колонки, наборы уникальности, перечни и FK
отдельно не перечисляются. Ограничения читаются из `pg_constraint` с раскрытием номеров колонок через
`pg_attribute`.

## Обратное отображение типов

Тип PostgreSQL переводится в тип модели, и сравниваются типы модели:

| Тип PostgreSQL | Тип модели |
|----------------|------------|
| `integer`, `bigint`, `boolean`, `text`, `date`, `uuid` | одноимённый |
| `character varying(n)` | `string(n)` |
| `numeric(p,s)` | `decimal(p, s)` |
| `timestamp without time zone` | `timestamp` |
| `timestamp with time zone` | `timestamp_tz` |
| любой другой, в том числе `character varying` без длины и `numeric` без точности | вне формата: расхождение `column_type_mismatch` с исходным типом |

Прямое отображение при построении changelog описано в [model-format.md](./model-format.md#типы-колонок).
Интеграционный тест накатывает модель со всеми десятью типами и сверяет её без расхождений:
так два отображения не расходятся.

## Распознавание перечня значений

PostgreSQL хранит `CHECK (source IN ('collector', 'manual'))` в нормализованной записи, которую
возвращает `pg_get_constraintdef`. Переводчик Сверки восстанавливает из неё колонку и множество
значений для форм, которые PostgreSQL даёт перечню над типами формата:

```text
CHECK ((source = ANY (ARRAY['collector'::text, 'manual'::text])))
CHECK (((source)::text = ANY ((ARRAY['collector'::character varying, 'manual'::character varying])::text[])))
CHECK ((priority = ANY (ARRAY[1, 2, 3])))
CHECK (((source)::text = 'collector'::text))
```

Первая форма — у `text`, вторая — у `string`, третья — у `integer` и `bigint`: у `bigint`
элементы записываются как `(1)::bigint`. Перечень из одного значения PostgreSQL сворачивает в `=`.
Значение в кавычках — строка, кавычки внутри удвоены; значение без кавычек или с приведением
к `integer` и `bigint` — целое. Ограничение над одной колонкой, отличное от этих форм, —
выражение, функция, сравнение — перечнем не считается и даёт `check_unexpected` с исходным
определением.

## Виды расхождений

Расхождение (Discrepancy) — одно несоответствие: вид, объект, ожидаемое и фактическое значение.

| Вид | Объект | Ожидаемое | Фактическое |
|-----|--------|-----------|-------------|
| `table_missing` | таблица | `present` | `absent` |
| `table_unexpected` | таблица | `absent` | `present` |
| `column_missing` | таблица и колонка | тип модели | `absent` |
| `column_unexpected` | таблица и колонка | `absent` | тип в БД |
| `column_type_mismatch` | таблица и колонка | тип модели, например `string(255)` | тип в БД, например `string(320)` или `smallint` |
| `column_nullable_mismatch` | таблица и колонка | `NULL` или `NOT NULL` | `NULL` или `NOT NULL` |
| `column_generated_mismatch` | таблица и колонка | `identity` или `absent` | `identity`, `identity_always` или `absent` |
| `primary_key_mismatch` | таблица | `[a, b]` | `[b, a]` или `absent` |
| `unique_missing` | таблица | набор модели, например `[tenant_id, code]` | `absent` |
| `unique_unexpected` | таблица | `absent` | набор в БД |
| `check_missing` | таблица и колонка | перечень модели, например `[collector, manual]` | `absent` |
| `check_unexpected` | таблица и колонка либо таблица | `absent` | перечень в БД либо определение нераспознанного `CHECK` |
| `foreign_key_missing` | таблица | FK модели, например `[customer_id] → customer[id]` | `absent` |
| `foreign_key_unexpected` | таблица | `absent` | FK в БД |
| `changeset_not_executed` | `id` changeset | `EXECUTED` | `absent` или значение `EXECTYPE` |

## Порядок расхождений

Порядок устойчив: повторная сверка неизменной БД даёт тот же перечень.

1. Таблицы модели в порядке модели. Внутри таблицы — колонки модели по порядку (тип, NULL,
   генерация значения), затем лишние колонки по имени, первичный ключ, наборы уникальности
   модели по порядку, лишние наборы, перечни модели по порядку колонок, лишние перечни, FK
   модели по порядку и лишние FK. Лишние ограничения идут по записи колонками; нераспознанный
   `CHECK` — по своему определению, раньше перечней с колонкой.
1. Лишние таблицы по имени.
1. Changeset в порядке changelog.

## Файл reconcile.json

Файл лежит рядом с changelog и совпадает с ответом команды:

```json
{
  "model": "backlog/forge-model/20261017-153000/attempt-1/model.yaml",
  "changelog": "backlog/forge-model/20261017-153000/attempt-1/changelog.yaml",
  "database": "lbfr-db:5432/forge",
  "verdict": "failure",
  "discrepancies": [
    {
      "kind": "column_type_mismatch",
      "table": "customer",
      "column": "email",
      "changeset": null,
      "expected": "string(255)",
      "actual": "string(320)",
      "message": "тип колонки customer.email: ожидался string(255), в БД string(320)"
    },
    {
      "kind": "unique_missing",
      "table": "customer",
      "column": null,
      "changeset": null,
      "expected": "[email]",
      "actual": "absent",
      "message": "набора уникальности customer[email] нет в БД"
    }
  ]
}
```

Сообщения могут меняться, виды расхождений и поля — часть контракта.

Поле `key` — PK строки — есть только у расхождений сверки seed, см.
[seed-reconciliation.md](./seed-reconciliation.md#виды-расхождений). В ответе `forge reconcile`
и его `reconcile.json` оно не выводится: расхождения схемы и журнала к строке не относятся.

## Ограничения и допущения

- **Ограничение:** сверяются только таблицы, колонки с генерацией значения, первичные ключи,
  ограничения уникальности, ограничения `CHECK` и FK схемы `public`. Представления,
  последовательности, индексы, в том числе уникальные индексы без ограничения, не видны: в модели
  их нет. Параметры последовательности identity-колонки не сравниваются.
- **Ограничение:** `CHECK`, не выражаемый перечнем значений одной колонки, всегда даёт
  `check_unexpected`: модель такие ограничения не описывает.
- **Риск:** новая версия PostgreSQL может записывать определение `CHECK` иначе → перечень
  перестанет распознаваться и даст пару `check_missing` и `check_unexpected`; интеграционный тест
  сверки после наката перечней падает при смене `LBFR_POSTGRES_IMAGE`.
- **Ограничение:** строки таблиц `forge reconcile` не сверяет. Строки таблиц seed сверяет
  `forge reconcile-seed`, см. [seed-reconciliation.md](./seed-reconciliation.md).
- **Ограничение:** действия FK `ON DELETE` и `ON UPDATE` не сравниваются: модель их не описывает,
  а changelog создаёт FK с действием `NO ACTION`.
- **Допущение:** схема целевой БД управляется только Liquibase Forge, поэтому посторонних
  объектов, невидимых сверке, в ней нет.
- **Риск:** новая версия PostgreSQL может записывать типы иначе → интеграционный тест сверки
  после наката падает при смене `LBFR_POSTGRES_IMAGE`.
