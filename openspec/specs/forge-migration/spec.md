# forge-migration Specification

## Purpose

Превращение модели данных в изменение схемы тестовой БД: changelog Liquibase из разницы
принятой модели и модели попытки — добавлений и удалений таблиц, колонок и ограничений, — его
накат через шлюз и откат неуспешной попытки с проверкой возврата схемы.

## Requirements

### Requirement: Changelog строится из добавляющей разницы моделей
`forge generate --model <модель попытки> [--accepted <принятая модель>] --operation <беклог
операции> --out <путь>` MUST строить changelog из новых таблиц, новых колонок существующих
таблиц, удалённых таблиц и удалённых колонок существующих таблиц. Без `--accepted` принятой
моделью SHALL считаться `<корень>/model.yaml` корня принятого состояния. Если принятой модели
нет, она SHALL считаться пустой.

#### Scenario: Первая операция
- **WHEN** файла `--accepted` нет, а модель попытки содержит две таблицы
- **THEN** команда возвращает код `0`, и changelog содержит по одному changeset на каждую таблицу

#### Scenario: Новая колонка существующей таблицы
- **WHEN** модель попытки добавляет колонку `phone` в таблицу `customer` принятой модели
- **THEN** changelog содержит один changeset добавления колонки `phone` и не трогает остальные объекты

#### Scenario: Модели совпадают
- **WHEN** модель попытки совпадает с принятой
- **THEN** команда возвращает код `0`, и changelog не содержит ни одного changeset

#### Scenario: Принятая модель из корня
- **WHEN** `--accepted` не передан, `FORGE_ACCEPTED_DIR=.forge/db`, а в `.forge/db/model.yaml` есть таблица `customer`
- **THEN** changelog не содержит changeset создания `customer`

#### Scenario: Корень принятого состояния некорректен
- **WHEN** `--accepted` не передан, а `FORGE_ACCEPTED_DIR` — абсолютный путь
- **THEN** команда возвращает код `2`, changelog не записан

#### Scenario: Удаление колонки
- **WHEN** в модели попытки нет колонки `email` таблицы `customer`, которая есть в принятой модели, и колонка не входит в первичный ключ
- **THEN** команда возвращает код `0`, changelog содержит один changeset удаления колонки `customer.email`, а ответ называет его видом `drop_column`

#### Scenario: Удалённая таблица
- **WHEN** в модели попытки нет таблицы `invoice_line`, которая есть в принятой модели
- **THEN** changelog содержит один changeset удаления таблицы `invoice_line` вида `drop_table` и не содержит changeset удаления её колонок
### Requirement: Неаддитивные изменения отклоняются
Смена типа или его параметров, смена итоговой допустимости NULL и смена первичного ключа MUST
отклоняться кодом `1` с перечнем всех таких изменений. Удаление колонки первичного ключа SHALL
отклоняться как смена первичного ключа. Переименование SHALL распознаваться как удаление
с добавлением. Changelog при отказе MUST NOT записываться, а прежний файл `--out` SHALL удаляться.

#### Scenario: Удалённая колонка
- **WHEN** в модели попытки нет колонки `id`, входящей в первичный ключ таблицы `customer` принятой модели
- **THEN** команда возвращает код `1`, перечень содержит `primary_key_changed` для `customer`, а файла changelog нет

#### Scenario: Несколько неаддитивных изменений
- **WHEN** модель попытки меняет тип одной колонки и первичный ключ другой таблицы
- **THEN** перечень содержит оба изменения

#### Scenario: Переименование колонки
- **WHEN** модель попытки содержит колонку `mail` вместо колонки `email` принятой модели с тем же типом
- **THEN** команда возвращает код `0`, changelog удаляет `email` и добавляет `mail`
### Requirement: Модели проверяются перед построением changelog
Модель попытки с нарушениями формата MUST давать код `1` с перечнем нарушений, как у
`forge validate`. Нечитаемая модель попытки, а также существующая, но некорректная принятая
модель SHALL давать код `2`.

#### Scenario: Некорректная модель попытки
- **WHEN** у колонки модели попытки тип `varchar`
- **THEN** команда возвращает код `1` и нарушение с путём этой колонки, changelog не записан

#### Scenario: Повреждённая принятая модель
- **WHEN** файл `--accepted` существует, но не проходит проверку формата
- **THEN** команда возвращает код `2` и указание на принятую модель

### Requirement: Changeset однозначно идентифицирован
Каждый changeset MUST содержать одну таблицу, одну колонку либо одно ограничение — внешний ключ
или набор уникальности, иметь `id` вида `<штамп>-<NN>` с номером по порядку от `01`,
`author: forge` и `logicalFilePath` `db/changelog/<штамп>.yaml` независимо от корня принятого
состояния. Штамп SHALL браться из `subject` беклога операции и соответствовать шаблону
`YYYYMMDD-HHMMSS`.

#### Scenario: Идентичность changeset
- **WHEN** беклог операции имеет `subject: "20261017-153000"`, и строятся два changeset
- **THEN** их `id` — `20261017-153000-01` и `20261017-153000-02`, а `logicalFilePath` у обоих `db/changelog/20261017-153000.yaml`

#### Scenario: Штамп не по шаблону
- **WHEN** `subject` беклога операции не соответствует шаблону штампа либо беклога нет
- **THEN** команда возвращает код `2`, changelog не записан

#### Scenario: Логический путь не зависит от корня
- **WHEN** `FORGE_ACCEPTED_DIR=.forge/db`, а беклог операции имеет `subject: "20261017-153000"`
- **THEN** `logicalFilePath` changeset — `db/changelog/20261017-153000.yaml`

#### Scenario: Ограничение — отдельный changeset
- **WHEN** модель попытки создаёт таблицу `invoice` с одним FK и одним набором `unique`
- **THEN** changelog содержит changeset создания `invoice`, отдельный changeset набора уникальности и отдельный changeset внешнего ключа

### Requirement: Changelog воспроизводим
Повторный вызов `forge generate` с теми же моделями и беклогом операции MUST давать побайтово
тот же файл. Порядок changeset SHALL следовать порядку таблиц и колонок модели попытки.

#### Scenario: Повторная генерация
- **WHEN** `forge generate` вызвана дважды с одинаковыми аргументами
- **THEN** оба файла changelog совпадают побайтово

### Requirement: Схема после наката соответствует модели
Накат changelog MUST создавать колонки с типами PostgreSQL по таблице отображения формата,
NOT NULL по итоговой допустимости NULL и первичный ключ `pk_<таблица>` с колонками в порядке
`primary_key` модели.

#### Scenario: Составной ключ в порядке модели
- **WHEN** таблица объявляет колонки `line_no`, `invoice_id` и `primary_key: [invoice_id, line_no]`
- **THEN** после наката ограничение `pk_<таблица>` содержит колонки в порядке `invoice_id`, `line_no`

#### Scenario: Типы PostgreSQL
- **WHEN** накатан changelog модели со всеми десятью типами формата
- **THEN** фактические типы колонок совпадают с таблицей отображения `docs/model-format.md`

### Requirement: Накат выполняется через шлюз на БД из перечня тестовых
`forge apply --changelog <путь>` MUST накатывать changelog на БД из `FORGE_DB_*` только через
шлюз Liquibase и раннер. БД вне `FORGE_TEST_DB_ALLOWLIST` SHALL отклоняться кодом `2` до обращения
к раннеру.

#### Scenario: Успешный накат
- **WHEN** changelog корректен, БД входит в перечень тестовых, раннер доступен
- **THEN** команда возвращает код `0`, а рядом с changelog записан `apply.json` с кодом исхода и выводом Liquibase

#### Scenario: БД вне перечня
- **WHEN** `FORGE_DB_*` указывает на БД, которой нет в `FORGE_TEST_DB_ALLOWLIST`
- **THEN** команда возвращает код `2`, раннер не вызывается, `apply.json` не записан

### Requirement: Исход наката различает ошибку Liquibase и ошибку окружения
Ошибка Liquibase MUST давать код `1` и записанный `apply.json`. Недоступный раннер, отсутствие
или чужой идентификатор файла результата, отказ шлюза и не заданные переменные окружения SHALL
давать код `2` без `apply.json`.

#### Scenario: Ошибка Liquibase
- **WHEN** Liquibase завершает накат ошибкой
- **THEN** команда возвращает код `1`, `apply.json` содержит диагностику Liquibase

#### Scenario: Раннер недоступен
- **WHEN** раннер не отвечает
- **THEN** команда возвращает код `2` с указанием на раннер, `apply.json` не записан

### Requirement: Откат не трогает подтверждённую попытку
`forge rollback --operation <беклог операции> --attempt <N>` при вердикте `success` попытки N
MUST возвращать код `0`, не меняя БД и не записывая `rollback.json`.

#### Scenario: Откат после успешной сверки
- **WHEN** во фронтматтере беклога операции `verdict.attempt_1: success`
- **THEN** команда возвращает код `0`, схема и журнал Liquibase не изменились

### Requirement: Откат снимает фактически применённые changeset попытки
При любом другом вердикте команда MUST откатывать столько changeset changelog попытки, сколько
их записано в `DATABASECHANGELOG`, предварительно проверив, что эти записи — хвост журнала.
Если записей нет, Liquibase SHALL NOT вызываться.

#### Scenario: Частичный накат
- **WHEN** из трёх changeset попытки в журнале записаны два последних по порядку исполнения
- **THEN** Liquibase откатывает ровно два changeset

#### Scenario: Попытка ничего не накатила
- **WHEN** в журнале нет записей changelog попытки
- **THEN** Liquibase не вызывается, проверка возврата выполняется, `rollback.json` записан

### Requirement: Возврат схемы подтверждается проверкой
После отката команда MUST проверять, что в журнале нет записей changelog попытки, таблиц
и колонок, которые changelog попытки добавляет, нет в схеме `public`, а таблицы и колонки,
которые он удаляет, в схеме есть. Результат SHALL записываться в `rollback.json` каталога
попытки; код `0` — возврат подтверждён, `1` — нет.

#### Scenario: Возврат подтверждён
- **WHEN** откат Liquibase прошёл успешно
- **THEN** `rollback.json` содержит число откатанных changeset и подтверждённую проверку, команда возвращает код `0`

#### Scenario: Удалённая колонка восстановлена
- **WHEN** откатывается попытка, changelog которой удалил колонку `customer.email`
- **THEN** колонка `customer.email` есть в схеме, `rollback.json` содержит пройденную проверку `column_present` для неё

#### Scenario: Удалённая таблица не восстановлена
- **WHEN** после отката попытки, удалившей таблицу `invoice_line`, таблицы в схеме нет
- **THEN** проверка `table_present` для `invoice_line` не пройдена, команда возвращает код `1`
### Requirement: Запасной путь пересоздаёт тестовую БД
Если откат Liquibase завершился ошибкой, записи попытки не являются хвостом журнала или
changelog попытки отсутствует, команда MUST пересоздать целевую БД из перечня тестовых через SQL
и накатить принятый `<корень>/changelog/master.yaml` корня принятого состояния, если он есть.
Затем SHALL выполняться та же проверка возврата.

#### Scenario: Хвост журнала не подтверждён
- **WHEN** после записей попытки в журнале есть запись другого changelog
- **THEN** Liquibase rollback не вызывается, БД пересоздана, принятый changelog накатан, `rollback.json` называет запасной путь

#### Scenario: Принятого состояния нет
- **WHEN** запасной путь выполняется, а `<корень>/changelog/master.yaml` отсутствует
- **THEN** БД пересоздана пустой, проверка возврата подтверждена

#### Scenario: Принятое состояние вне db
- **WHEN** запасной путь выполняется, `FORGE_ACCEPTED_DIR=.forge/db`, а `.forge/db/changelog/master.yaml` есть
- **THEN** накатывается `.forge/db/changelog/master.yaml`, а `db/changelog/master.yaml` не читается

### Requirement: Удаления идут перед добавлениями
Changeset удалений MUST идти в changelog раньше changeset добавлений: сначала удалённые таблицы
в порядке принятой модели, затем удалённые колонки по таблицам и колонкам принятой модели,
затем добавления в порядке модели попытки. Номера `id` SHALL идти подряд через весь changelog.

#### Scenario: Удаление и добавление в одной модели
- **WHEN** модель попытки удаляет колонку `customer.legacy` и добавляет таблицу `invoice`
- **THEN** changeset `<штамп>-01` удаляет `customer.legacy`, а changeset `<штамп>-02` создаёт `invoice`

### Requirement: Changeset удаления несёт откат по принятой модели
Каждый changeset удаления MUST содержать явный откат, восстанавливающий структуру объекта
по принятой модели: таблицу с колонками, типами, NOT NULL и первичным ключом `pk_<таблица>`,
колонку — с типом и NOT NULL. Данные удалённого объекта откат SHALL NOT восстанавливать.

#### Scenario: Откат удаления таблицы через Liquibase
- **WHEN** накатан changelog, удаливший таблицу `invoice_line` с первичным ключом `[invoice_id, line_no]`, и выполнен его откат Liquibase
- **THEN** таблица `invoice_line` есть в схеме с колонками и типами принятой модели и ключом `pk_invoice_line` по `invoice_id, line_no`

#### Scenario: Частичный накат с удалением
- **WHEN** changelog удаляет колонку и добавляет таблицу, а Liquibase записал в журнал только первый changeset
- **THEN** откат снимает ровно один changeset, и удалённая колонка восстановлена

### Requirement: Удаления в режиме auto требуют согласия операции
Если беклог операции в режиме `auto` не содержит `allow_drop: true`, а модель попытки требует
удаления, `forge generate` MUST вернуть код `2` с видом ошибки `drop_not_allowed`, перечислив
удаляемые объекты, и SHALL NOT записывать changelog. Беклог без поля `allow_drop` MUST
считаться беклогом без согласия. В режиме `interactive` удаления SHALL разрешаться без признака.

#### Scenario: Удаление в auto без согласия
- **WHEN** беклог операции имеет `mode: auto` и `allow_drop: false`, а модель попытки удаляет колонку
- **THEN** команда возвращает код `2` с видом `drop_not_allowed`, changelog не записан, прежний файл `--out` удалён

#### Scenario: Удаление в auto с согласием
- **WHEN** беклог операции имеет `mode: auto` и `allow_drop: true`, а модель попытки удаляет таблицу
- **THEN** команда возвращает код `0`, и changelog содержит changeset удаления таблицы

#### Scenario: Беклог прежнего шаблона
- **WHEN** беклог операции в режиме `auto` не содержит поля `allow_drop`, а модель попытки удаляет колонку
- **THEN** команда возвращает код `2` с видом `drop_not_allowed`

#### Scenario: Удаление в interactive
- **WHEN** беклог операции имеет `mode: interactive`, а модель попытки удаляет колонку
- **THEN** команда возвращает код `0`, и changelog содержит changeset удаления колонки

### Requirement: Ограничения отождествляются по содержимому
`forge generate` MUST сравнивать внешние ключи принятой модели и модели попытки по колонкам FK,
целевой таблице и колонкам цели, наборы уникальности — по составу колонок. Новое ограничение
SHALL давать changeset добавления, исчезнувшее — changeset удаления; изменение ограничения
MUST выражаться удалением прежнего и добавлением нового.

#### Scenario: Новый внешний ключ существующей таблицы
- **WHEN** модель попытки добавляет FK `invoice.customer_id` → `customer.id` к таблицам принятой модели
- **THEN** changelog содержит один changeset добавления этого FK и не трогает остальные объекты

#### Scenario: Перестановка наборов
- **WHEN** модель попытки отличается от принятой только порядком элементов `unique` и `foreign_keys`
- **THEN** changelog не содержит ни одного changeset

#### Scenario: Смена цели внешнего ключа
- **WHEN** FK таблицы `invoice` в модели попытки ссылается на `customer.email` вместо `customer.id`
- **THEN** changelog содержит changeset удаления прежнего FK и changeset добавления нового

### Requirement: Имя ограничения вычисляется из содержимого
Имя внешнего ключа MUST быть `fk_<таблица>_<hash8>`, имя набора уникальности —
`uq_<таблица>_<hash8>`, где `hash8` — восемь шестнадцатеричных знаков хеша содержимого
ограничения. Имя таблицы SHALL обрезаться так, чтобы имя ограничения не превышало 63 символов.
Одинаковое содержимое MUST давать одинаковое имя в любой модели.

#### Scenario: Имя не зависит от порядка
- **WHEN** один и тот же FK стоит первым в одной модели и вторым в другой
- **THEN** имя его ограничения в обоих changelog одинаково

#### Scenario: Длинное имя таблицы
- **WHEN** имя таблицы состоит из 60 символов, и у неё есть набор уникальности
- **THEN** имя ограничения не длиннее 63 символов и заканчивается восемью шестнадцатеричными знаками

### Requirement: Порядок changeset учитывает ограничения
Changeset MUST идти группами: удаление внешних ключей, удаление наборов уникальности, удаление
таблиц, удаление колонок, создание таблиц, добавление колонок, добавление наборов уникальности,
добавление внешних ключей. Внутри группы порядок SHALL следовать модели, из которой взят объект.

#### Scenario: Ссылка на таблицу ниже по модели
- **WHEN** модель попытки создаёт `invoice` раньше `customer`, а `invoice` ссылается на `customer`
- **THEN** changeset внешнего ключа идёт после создания обеих таблиц, и накат проходит

#### Scenario: Внешний ключ на новый набор уникальности
- **WHEN** модель попытки добавляет `unique: [[email]]` к `customer` и FK на `customer.email`
- **THEN** changeset набора уникальности идёт раньше changeset внешнего ключа

### Requirement: Удаление таблицы снимает связанные внешние ключи отдельно
Внешние ключи удаляемой таблицы и внешние ключи других таблиц на неё MUST удаляться отдельными
changeset до удаления таблицы. Откат удаления таблицы SHALL восстанавливать таблицу, первичный
ключ и её наборы уникальности; внешние ключи MUST восстанавливаться откатом своих changeset.

#### Scenario: Удаление таблицы со ссылкой
- **WHEN** модель попытки удаляет таблицы `invoice` и `customer`, где `invoice` ссылается на `customer`
- **THEN** changeset удаления FK `invoice` идёт раньше changeset удаления обеих таблиц

#### Scenario: Откат удаления таблицы со связями
- **WHEN** откатывается попытка, удалившая `invoice` с FK на `customer` и набором `unique`
- **THEN** после отката таблица `invoice`, её набор уникальности и FK на `customer` есть в схеме

### Requirement: Удаление ограничения откатывается и не требует согласия
Changeset удаления внешнего ключа или набора уникальности MUST содержать откат, восстанавливающий
ограничение по принятой модели. Удаление ограничения SHALL NOT требовать `allow_drop` в режиме
`auto` и SHALL NOT считаться удалением данных.

#### Scenario: Удаление FK в auto без согласия
- **WHEN** беклог операции имеет `mode: auto` и `allow_drop: false`, а модель попытки только убирает FK
- **THEN** команда возвращает код `0`, и changelog содержит changeset удаления FK с откатом

#### Scenario: Удаление колонки из набора
- **WHEN** модель попытки удаляет колонку `customer.email` и набор `unique: [[email]]`
- **THEN** changeset удаления набора уникальности идёт раньше changeset удаления колонки

### Requirement: Схема после наката содержит ограничения модели
Накат changelog MUST создавать внешние ключи с колонками в порядке FK, целевой таблицей
и колонками цели в парном порядке, с действием `NO ACTION`, и ограничения уникальности
с колонками набора.

#### Scenario: Составной внешний ключ
- **WHEN** накатан FK `[invoice_id, line_no]` → `invoice_line.[invoice_id, line_no]`
- **THEN** ограничение в БД связывает колонки попарно в этом порядке

### Requirement: Возврат ограничений подтверждается проверкой
После отката `forge rollback` MUST проверять по вычисленному имени, что ограничений, которые
changelog попытки добавляет, нет в схеме (`foreign_key_absent`, `unique_absent`), а ограничения,
которые он удаляет, есть (`foreign_key_present`, `unique_present`). Непройденная проверка SHALL
давать код `1`.

#### Scenario: Добавленный FK снят
- **WHEN** откатывается попытка, добавившая FK
- **THEN** `rollback.json` содержит пройденную проверку `foreign_key_absent` с именем ограничения

#### Scenario: Удалённый набор не восстановлен
- **WHEN** после отката попытки, удалившей набор уникальности, ограничения в схеме нет
- **THEN** проверка `unique_present` не пройдена, команда возвращает код `1`
