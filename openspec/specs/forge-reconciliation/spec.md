# forge-reconciliation Specification

## Purpose

Сверка результата попытки: фактическая схема тестовой БД сравнивается с моделью данных,
а журнал Liquibase — с changelog попытки, чтобы вердикт попытки опирался на состояние БД,
а не на исход наката.

## Requirements

### Requirement: Сверка сравнивает фактическую схему с моделью
`forge reconcile --model <модель> --changelog <changelog>` MUST читать фактическую схему `public`
целевой БД из `FORGE_DB_*` интроспекцией каталога PostgreSQL, а не из changelog. Таблицы журнала
Liquibase SHALL исключаться из сравнения.

#### Scenario: Схема совпадает с моделью
- **WHEN** changelog модели со всеми десятью типами формата накатан и других таблиц в БД нет
- **THEN** команда возвращает код `0`, перечень расхождений пуст

#### Scenario: Служебные таблицы Liquibase
- **WHEN** в БД есть `databasechangelog` и `databasechangeloglock`
- **THEN** они не считаются лишними таблицами

### Requirement: Таблицы и колонки сверяются в обе стороны
Таблица или колонка модели, которой нет в БД, MUST давать расхождение `table_missing`
либо `column_missing`. Таблица или колонка в БД, которой нет в модели, SHALL давать
`table_unexpected` либо `column_unexpected`. Порядок колонок MUST NOT сравниваться.

#### Scenario: Лишняя колонка
- **WHEN** в таблице `customer` БД есть колонка `legacy`, которой нет в модели
- **THEN** перечень содержит расхождение `column_unexpected` для `customer.legacy`

#### Scenario: Отсутствующая таблица
- **WHEN** таблицы модели `invoice` в БД нет
- **THEN** перечень содержит `table_missing` для `invoice` и не содержит расхождений её колонок

#### Scenario: Другой порядок колонок
- **WHEN** колонки таблицы в БД идут в другом порядке, чем в модели
- **THEN** расхождений нет

### Requirement: Колонка сверяется по типу и допустимости NULL
Для колонки, которая есть и в модели, и в БД, тип с параметрами MUST совпадать с отображением
типа модели в PostgreSQL, иначе — расхождение `column_type_mismatch`. Итоговая допустимость NULL
SHALL совпадать, иначе — `column_nullable_mismatch`. Тип PostgreSQL вне отображения формата MUST
давать `column_type_mismatch` с фактическим типом в расхождении.

#### Scenario: Другая длина строки
- **WHEN** в модели `email` — `string` с `length: 255`, а в БД `varchar(320)`
- **THEN** перечень содержит `column_type_mismatch` с ожидаемым `string(255)` и фактическим `string(320)`

#### Scenario: Колонка допускает NULL вопреки модели
- **WHEN** в модели колонка NOT NULL, а в БД допускает NULL
- **THEN** перечень содержит `column_nullable_mismatch`

#### Scenario: Тип вне формата
- **WHEN** колонка в БД имеет тип `smallint`
- **THEN** перечень содержит `column_type_mismatch`, где фактическое значение — `smallint`

### Requirement: Первичный ключ сверяется как упорядоченный список колонок
Первичный ключ таблицы в БД MUST совпадать с `primary_key` модели по составу и порядку колонок.
Имя ограничения SHALL NOT сравниваться. Отсутствие ключа в БД MUST давать расхождение
`primary_key_mismatch`.

#### Scenario: Ключ в другом порядке
- **WHEN** в модели `primary_key: [invoice_id, line_no]`, а в БД ключ по `line_no, invoice_id`
- **THEN** перечень содержит `primary_key_mismatch`

#### Scenario: Имя ограничения отличается
- **WHEN** ключ в БД совпадает по колонкам, но называется не `pk_<таблица>`
- **THEN** расхождений нет

### Requirement: Каждый changeset попытки записан Liquibase как исполненный
Для каждого changeset changelog попытки в `DATABASECHANGELOG` MUST быть запись с тем же `id`,
`author` и `filename`, равным `logicalFilePath`, и `EXECTYPE = EXECUTED`. Иначе SHALL давать
расхождение `changeset_not_executed`.

#### Scenario: Changeset не записан
- **WHEN** второго changeset попытки нет в журнале
- **THEN** перечень содержит `changeset_not_executed` для его `id`

#### Scenario: Changeset помечен, но не исполнен
- **WHEN** запись changeset имеет `EXECTYPE = MARK_RAN`
- **THEN** перечень содержит `changeset_not_executed` с фактическим значением `MARK_RAN`

#### Scenario: Пустой changelog
- **WHEN** changelog попытки не содержит changeset
- **THEN** проверка журнала не даёт расхождений

### Requirement: Результат сверки пишется в reconcile.json
Команда MUST печатать один JSON-объект с вердиктом и перечнем расхождений и писать
`reconcile.json` рядом с changelog. Каждое расхождение SHALL содержать вид, таблицу, колонку
или `id` changeset, ожидаемое и фактическое значение и сообщение. Порядок расхождений MUST
быть устойчивым.

#### Scenario: Расхождения найдены
- **WHEN** сверка нашла хотя бы одно расхождение
- **THEN** команда возвращает код `1`, вердикт `failure`, `reconcile.json` записан с тем же перечнем

#### Scenario: Повторная сверка
- **WHEN** сверка дважды выполнена на неизменной БД
- **THEN** перечни расхождений совпадают

### Requirement: Ошибка окружения не даёт вердикта
Не заданные переменные окружения, БД вне перечня тестовых, недоступная БД, нечитаемая или
некорректная модель и нечитаемый changelog MUST давать код `2` без `reconcile.json`.

#### Scenario: БД недоступна
- **WHEN** целевая БД не принимает подключения
- **THEN** команда возвращает код `2`, `reconcile.json` не записан

#### Scenario: БД вне перечня
- **WHEN** `FORGE_DB_*` указывает на БД вне `FORGE_TEST_DB_ALLOWLIST`
- **THEN** команда возвращает код `2`, к БД не подключается

### Requirement: Внешние ключи сверяются по содержимому
Сверка MUST читать внешние ключи таблиц схемы `public` интроспекцией каталога и сравнивать
их с моделью по колонкам FK, целевой таблице и колонкам цели в парном порядке. FK модели,
которого нет в БД, SHALL давать `foreign_key_missing`; FK в БД, которого нет в модели, —
`foreign_key_unexpected`. Имя ограничения MUST NOT сравниваться.

#### Scenario: Внешний ключ совпадает
- **WHEN** в БД есть FK `invoice.customer_id` → `customer.id` с произвольным именем, и он объявлен в модели
- **THEN** расхождений по внешним ключам нет

#### Scenario: Внешнего ключа нет в БД
- **WHEN** модель объявляет FK `invoice.customer_id` → `customer.id`, а в БД его нет
- **THEN** перечень содержит `foreign_key_missing` для таблицы `invoice`

#### Scenario: Лишний внешний ключ
- **WHEN** в БД есть FK, которого нет в модели
- **THEN** перечень содержит `foreign_key_unexpected` для его таблицы

#### Scenario: Отсутствующая таблица
- **WHEN** таблицы модели `invoice` с FK в БД нет
- **THEN** перечень содержит `table_missing` для `invoice` и не содержит расхождений её внешних ключей

### Requirement: Наборы уникальности сверяются по составу
Сверка MUST читать ограничения уникальности таблиц схемы `public` и сравнивать их с наборами
`unique` модели по составу колонок. Набор модели, которого нет в БД, SHALL давать
`unique_missing`; ограничение в БД, которого нет в модели, — `unique_unexpected`. Имя
ограничения и уникальные индексы без ограничения MUST NOT сравниваться.

#### Scenario: Набор совпадает
- **WHEN** модель объявляет `unique: [[tenant_id, code]]`, а в БД ограничение по `code, tenant_id`
- **THEN** расхождений по уникальности нет

#### Scenario: Набора нет в БД
- **WHEN** модель объявляет `unique: [[email]]` у `customer`, а ограничения в БД нет
- **THEN** перечень содержит `unique_missing` для `customer`

### Requirement: Расхождения ограничений идут в устойчивом порядке
Расхождения ограничений таблицы MUST следовать за расхождением её первичного ключа: наборы
уникальности модели по порядку, лишние наборы, перечни значений модели по порядку колонок,
лишние перечни, внешние ключи модели по порядку, лишние внешние ключи; лишние ограничения —
в порядке их описания колонками.

#### Scenario: Повторная сверка
- **WHEN** сверка с расхождениями ограничений дважды выполнена на неизменной БД
- **THEN** перечни расхождений совпадают

#### Scenario: Перечень между уникальностью и внешними ключами
- **WHEN** у таблицы `event` в БД нет набора уникальности, перечня `source` и внешнего ключа модели
- **THEN** перечень содержит `unique_missing`, затем `check_missing`, затем `foreign_key_missing`

### Requirement: Генерация значения колонки сверяется
Для колонки, которая есть и в модели, и в БД, генерация значения MUST совпадать: колонка
с `generated: identity` SHALL быть identity `BY DEFAULT`, колонка без `generated` — не identity.
Иначе SHALL давать расхождение `column_generated_mismatch` с ожидаемым `identity` или `absent`
и фактическим `identity`, `identity_always` или `absent`. Расхождение идёт после расхождений
типа и NULL этой колонки.

#### Scenario: Генерация совпадает
- **WHEN** в модели `customer.id` имеет `generated: identity`, а в БД колонка — identity `BY DEFAULT`
- **THEN** расхождений по генерации нет

#### Scenario: Генерации нет в БД
- **WHEN** в модели `customer.id` имеет `generated: identity`, а в БД колонка не identity
- **THEN** перечень содержит `column_generated_mismatch` с ожидаемым `identity` и фактическим `absent`

#### Scenario: Генерация ALWAYS
- **WHEN** в модели `customer.id` имеет `generated: identity`, а в БД колонка — identity `ALWAYS`
- **THEN** перечень содержит `column_generated_mismatch` с фактическим `identity_always`

#### Scenario: Лишняя генерация
- **WHEN** в модели `customer.id` без `generated`, а в БД колонка — identity
- **THEN** перечень содержит `column_generated_mismatch` с ожидаемым `absent` и фактическим `identity`

### Requirement: Перечни значений сверяются по содержимому
Сверка MUST читать ограничения `CHECK` таблиц схемы `public` и сравнивать их с перечнями `check`
модели по колонке и множеству значений. Перечень модели, которого нет в БД, SHALL давать
`check_missing`; ограничение в БД, которого нет в модели, — `check_unexpected`. Имя ограничения
и порядок значений MUST NOT сравниваться.

#### Scenario: Перечень совпадает
- **WHEN** модель объявляет у `event.source` `check: [collector, manual]`, а в БД ограничение с произвольным именем допускает `manual` и `collector`
- **THEN** расхождений по перечням нет

#### Scenario: Перечня нет в БД
- **WHEN** модель объявляет перечень у `event.source`, а ограничения в БД нет
- **THEN** перечень расхождений содержит `check_missing` для `event` с колонкой `source`

#### Scenario: Другой набор значений
- **WHEN** модель объявляет у `event.source` `check: [collector, manual]`, а в БД ограничение допускает `collector`, `manual` и `import`
- **THEN** перечень содержит `check_missing` для перечня модели и `check_unexpected` для ограничения в БД

#### Scenario: Перечни целых колонок
- **WHEN** модель объявляет у `task.priority` типа `integer` `check: [1, 2, 3]`, и ограничение накатано changelog модели
- **THEN** расхождений по перечням нет

#### Scenario: Отсутствующая таблица
- **WHEN** таблицы модели `event` с перечнем в БД нет
- **THEN** перечень содержит `table_missing` для `event` и не содержит расхождений её перечней

### Requirement: Нераспознанное ограничение CHECK считается лишним
Ограничение `CHECK` в БД, которое не выражается перечнем значений одной колонки — выражение
над несколькими колонками, сравнение, вызов функции, — MUST давать расхождение `check_unexpected`
с исходным определением ограничения в фактическом значении. Такое ограничение SHALL NOT приводить
к ошибке окружения.

#### Scenario: Ограничение-выражение
- **WHEN** в таблице `invoice` БД есть ограничение `CHECK (amount > 0)`, а в модели перечней у `invoice` нет
- **THEN** перечень содержит `check_unexpected` для `invoice`, фактическое значение — определение ограничения, команда возвращает код `1`
