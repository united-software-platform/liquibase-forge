# forge-checks Specification

## Purpose

Автоматические проверки репозитория Liquibase Forge в GitHub Actions: когда они запускаются,
что проверяют и как их вердикт соотносится с локальным прогоном проверок перед отправкой
изменений.

## Requirements

### Requirement: Проверки запускаются на PR и на push в main
Workflow проверок MUST запускаться на каждый `pull_request` в ветку `main` и на каждый `push`
в `main`. Он SHALL также вызываться другими workflow репозитория. Push в иные ветки без PR
SHALL NOT запускать проверки.

#### Scenario: PR в main
- **WHEN** открыт или обновлён PR из ветки `release/v0.2.0` в `main`
- **THEN** workflow проверок запускается на коммите PR, и его статус виден в PR

#### Scenario: Слияние в main
- **WHEN** PR влит в `main`
- **THEN** workflow проверок запускается на коммите слияния

### Requirement: Проверки повторяют локальный прогон
Workflow MUST выполнять ровно команды раздела «Проверки» `CONTRIBUTING.md`: линтер,
проверку форматирования, проверку типов `src`, тесты и проверку объёма секций `Makefile` без
ключа `--max-lines`. Зависимости SHALL устанавливаться по `uv.lock` без его обновления.

#### Scenario: Команда добавлена в CONTRIBUTING
- **WHEN** в разделе «Проверки» появляется команда, которой нет в workflow
- **THEN** тест репозитория на соответствие workflow и раздела падает

#### Scenario: Lock-файл расходится с pyproject.toml
- **WHEN** `pyproject.toml` изменён, а `uv.lock` нет
- **THEN** установка зависимостей завершается ошибкой, и проверки не проходят

### Requirement: Любая непройденная проверка делает прогон красным
Workflow MUST завершаться ошибкой, если хотя бы одна проверка завершилась ненулевым кодом.
Проверка SHALL NOT отключаться через `continue-on-error`.

#### Scenario: Ошибка линтера
- **WHEN** `ruff check` находит нарушение
- **THEN** прогон завершается ошибкой, и статус PR — красный

#### Scenario: Превышение объёма секции Makefile
- **WHEN** секция цели `Makefile` длиннее 30 строк
- **THEN** проверка объёма завершается кодом `1`, и прогон завершается ошибкой

### Requirement: Тесты, требующие окружения, пропускаются с причиной
Тесты, которым нужны сервер БД интеграционных тестов, раннер на хосте или CLI `backlog`, MUST
пропускаться в workflow с указанием причины, а не завершаться ошибкой. Workflow SHALL NOT
задавать `FORGE_TEST_DB_HOST`, `AGENT_RUNNER_URL` и `AGENT_RUNNER_TOKEN`.

#### Scenario: Интеграционные тесты в CI
- **WHEN** workflow запускает тесты
- **THEN** тесты с маркером `integration` отмечены пропущенными с причиной, а остальные тесты исполнены

### Requirement: Проверки только читают репозиторий
Workflow проверок MUST иметь право только на чтение содержимого репозитория. Он SHALL NOT
коммитить, ставить теги и публиковать релизы.

#### Scenario: Права workflow
- **WHEN** проверяется описание workflow проверок
- **THEN** его права ограничены `contents: read`

### Requirement: В main попадают только PR с пройденными проверками
Ветка `main` MUST быть защищена правилами репозитория. Изменение SHALL попадать в `main` только
слиянием PR, у которого job проверок завершился успешно. Обязательных одобрений PR SHALL NOT
требоваться. Force-push в `main` и удаление `main` MUST отклоняться. Обходить правила MUST NOT ни
один человек, включая администраторов репозитория. Единственное исключение задаёт требование
`forge-release` о публикации релизного коммита.

#### Scenario: PR с красными проверками
- **WHEN** в PR в `main` job проверок завершился ошибкой
- **THEN** GitHub не даёт слить PR ни автору, ни администратору

#### Scenario: PR с зелёными проверками
- **WHEN** в PR в `main` job проверок завершился успешно, и одобрений у PR нет
- **THEN** PR можно слить

#### Scenario: Прямой push в main
- **WHEN** администратор отправляет коммит прямо в `main`, минуя PR
- **THEN** push отклоняется

### Requirement: Правила защиты main описаны в репозитории
Правила защиты `main` MUST храниться в репозитории файлом, который применяется к GitHub.
Обязательная проверка в этом файле MUST называться так же, как job проверок в workflow `checks`.
Переименование job'а без правки файла SHALL обнаруживаться тестом репозитория.

#### Scenario: Job проверок переименован
- **WHEN** имя job'а в `checks.yml` изменено, а файл правил нет
- **THEN** тест репозитория на соответствие имени обязательной проверки падает

#### Scenario: В файле правил появился обход
- **WHEN** в файл правил добавлен обход для роли администратора
- **THEN** тест репозитория на состав обхода падает
