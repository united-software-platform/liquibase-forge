# forge-operation-commands Specification

## Purpose

Команды CLI состояния операции Liquibase Forge: статус и проверка тестовой среды, остановка
и продолжение, закрытие с принятием модели в `db/` и итоговый отчёт для LLM.

## Requirements

### Requirement: Статус операции читается из её беклога
`forge status --operation <беклог операции>` MUST печатать намерение, режим, признак согласия
на удаления `allow_drop`, статус операции, вердикт, беклог и каталог каждой попытки и номер
подтверждённой попытки. Подтверждённой SHALL считаться попытка с вердиктом `success`. Беклог
без поля `allow_drop` MUST давать `allow_drop: false`.

#### Scenario: Операция после первой неудачи
- **WHEN** у операции `verdict.attempt_1: failure`, остальные вердикты пусты
- **THEN** ответ называет статус `running`, одну использованную попытку и отсутствие подтверждённой попытки

#### Scenario: Беклога нет
- **WHEN** путь `--operation` не ведёт к беклогу операции
- **THEN** команда возвращает код `2`

#### Scenario: Признак согласия на удаления
- **WHEN** беклог операции содержит `mode: auto` и `allow_drop: true`
- **THEN** ответ называет режим `auto` и `allow_drop: true`

#### Scenario: Беклог прежнего шаблона
- **WHEN** беклог операции не содержит поля `allow_drop`
- **THEN** ответ называет `allow_drop: false`
### Requirement: Статус проверяет тестовую среду
`forge status` MUST проверять подключение к целевой БД из `FORGE_DB_*`, вхождение БД в
`FORGE_TEST_DB_ALLOWLIST`, ответ раннера на цель `help` и корректность корня принятого
состояния из `FORGE_ACCEPTED_DIR`. Любая непройденная проверка SHALL давать код `2`, а ответ
MUST называть каждую проверку и её итог. Проверка `accepted` MUST называть итоговый путь корня.

#### Scenario: Раннер не отвечает
- **WHEN** БД доступна и входит в перечень, корень принятого состояния корректен, а раннер не отвечает
- **THEN** команда возвращает код `2`, проверка раннера отмечена непройденной, остальные — пройденными

#### Scenario: Среда в порядке
- **WHEN** все четыре проверки пройдены
- **THEN** команда возвращает код `0`

#### Scenario: Корень принятого состояния назван
- **WHEN** `FORGE_ACCEPTED_DIR=.forge/db`, а остальные проверки пройдены
- **THEN** проверка `accepted` пройдена и называет путь `.forge/db`, команда возвращает код `0`

#### Scenario: Корень вне проекта
- **WHEN** `FORGE_ACCEPTED_DIR=../db`
- **THEN** проверка `accepted` не пройдена, команда возвращает код `2`

### Requirement: Открытая операция находится по ключу latest
`forge status --latest` MUST находить в следе `backlog/forge-model/` операцию со статусом `running`
или `stopped`. Если открытых операций нет, ответ SHALL содержать `operation: null` с кодом,
определяемым только проверкой среды. Более одной открытой операции MUST давать код `2`.

#### Scenario: Открытых операций нет
- **WHEN** все операции в следе закрыты либо следа нет, а среда в порядке
- **THEN** команда возвращает код `0` и `operation: null`

#### Scenario: Остановленная операция
- **WHEN** в следе есть операция со статусом `stopped`
- **THEN** ответ называет её путь и статус `stopped`

### Requirement: Остановка и продолжение меняют только статус
`forge stop --operation <беклог> --reason <текст>` MUST переводить операцию из `running`
в `stopped` и записывать причину во фронтматтер. `forge resume --operation <беклог>` MUST
переводить `stopped` в `running`. Закрытую операцию ни одна из команд SHALL NOT менять: код `1`.
Остальной текст беклога MUST оставаться побайтово неизменным; единственное исключение — строка
`allow_drop` при продолжении с согласием на удаления.

#### Scenario: Остановка по ошибке окружения
- **WHEN** `forge stop` вызвана для операции `running` с причиной «раннер недоступен»
- **THEN** статус `stopped`, `stop_reason` содержит причину, задачи и отметки беклога не изменились

#### Scenario: Продолжение не остановленной операции
- **WHEN** `forge resume` вызвана для операции `running`
- **THEN** команда возвращает код `1`, беклог не изменён

#### Scenario: Повторная остановка
- **WHEN** `forge stop` вызвана для уже остановленной операции
- **THEN** код `0`, статус `stopped`, причина заменена новой
### Requirement: Закрытие успешной операции принимает модель в db
`forge close --operation <беклог>` при подтверждённой попытке MUST скопировать её `model.yaml`
в `<корень>/model.yaml` и `changelog.yaml` в `<корень>/changelog/<штамп>.yaml`, добавить
`include` этого файла в конец `<корень>/changelog/master.yaml`, если его там нет, и поставить
статус `success`. `<корень>` — корень принятого состояния. Команда SHALL NOT коммитить.

#### Scenario: Первая успешная операция
- **WHEN** корня принятого состояния ещё нет, а попытка 2 подтверждена
- **THEN** появились `<корень>/model.yaml`, `<корень>/changelog/<штамп>.yaml` и `master.yaml` с одним `include`, статус `success`

#### Scenario: Принятый master накатывается
- **WHEN** после двух успешных операций накатывается `<корень>/changelog/master.yaml` на пустую БД
- **THEN** Liquibase применяет changeset обеих операций в порядке их принятия

### Requirement: Закрытие после трёх неудач не меняет db
При вердикте `failure` у всех трёх попыток и подтверждённом `rollback.json` каждой
`forge close` MUST ставить статус `failure`, не трогая корень принятого состояния. Если нет
ни подтверждённой попытки, ни трёх неудач с подтверждённым откатом, команда SHALL возвращать
код `1` с причиной и ничего не менять.

#### Scenario: Три неудачи
- **WHEN** все три попытки неуспешны и откат каждой подтверждён
- **THEN** статус `failure`, содержимое корня принятого состояния не изменилось

#### Scenario: Закрывать рано
- **WHEN** у операции одна неуспешная попытка
- **THEN** команда возвращает код `1`, статус остаётся `running`

#### Scenario: Повторное закрытие
- **WHEN** `forge close` вызвана для уже закрытой операции
- **THEN** код `0`, статус и корень принятого состояния не изменились

### Requirement: Отчёт содержит всё для разбора исхода
`forge report --operation <беклог>` MUST печатать статус, число использованных попыток, пути
модели и changelog, перечень беклогов, а для каждой попытки — вердикт, расхождения сверки
из `reconcile.json` и итог отката из `rollback.json`. Для закрытой операции отчёт SHALL
перечислять файлы для коммита: след операции, а при `success` — и файлы корня принятого
состояния. Код `1` MUST возвращаться только при статусе `failure`.

#### Scenario: Отчёт об успехе
- **WHEN** операция закрыта со статусом `success` на второй попытке
- **THEN** отчёт называет две попытки, пути в корне принятого состояния, расхождения первой попытки, её откат и файлы для коммита, код `0`

#### Scenario: Отчёт о неудаче
- **WHEN** операция закрыта со статусом `failure`
- **THEN** отчёт содержит три попытки с расхождениями и откатом каждой, код `1`

#### Scenario: Отчёт при корне вне db
- **WHEN** `FORGE_ACCEPTED_DIR=.forge/db`, а операция закрыта со статусом `success`
- **THEN** файлы для коммита названы путями в `.forge/db/`

#### Scenario: След успешной операции для коммита
- **WHEN** операция `20261017-153000` закрыта со статусом `success` на второй попытке
- **THEN** файлы для коммита — файлы корня принятого состояния, каталог `backlog/forge-model/20261017-153000/` и каталоги `backlog/forge-apply/20261017-153000-1/` и `backlog/forge-apply/20261017-153000-2/`

#### Scenario: След неудачной операции для коммита
- **WHEN** операция `20261017-153000` закрыта со статусом `failure`
- **THEN** файлы для коммита — каталог операции и каталоги беклогов трёх попыток, файлов корня принятого состояния среди них нет

#### Scenario: Открытая операция
- **WHEN** операция в статусе `running` либо `stopped`
- **THEN** отчёт не перечисляет файлов для коммита

### Requirement: Корень принятого состояния задаётся переменной окружения
Команды `forge` MUST брать корень принятого состояния из `FORGE_ACCEPTED_DIR`. Незаданная или
пустая переменная SHALL давать корень `db`. Значение MUST быть относительным путём внутри
корня проекта: абсолютный путь либо выход за корень проекта SHALL давать код `2` у команд,
обращающихся к принятому состоянию.

#### Scenario: Переменная не задана
- **WHEN** `FORGE_ACCEPTED_DIR` не задана, а попытка операции подтверждена
- **THEN** `forge close` принимает модель в `db/model.yaml`

#### Scenario: Корень вне db
- **WHEN** `FORGE_ACCEPTED_DIR=.forge/db`, а попытка операции подтверждена
- **THEN** `forge close` принимает модель в `.forge/db/model.yaml`, а каталог `db/` не появляется

#### Scenario: Абсолютный путь
- **WHEN** `FORGE_ACCEPTED_DIR=/srv/db`
- **THEN** `forge close` возвращает код `2` с указанием на `FORGE_ACCEPTED_DIR` и ничего не принимает

### Requirement: Продолжение операции может дать согласие на удаления
`forge resume --operation <беклог> --allow-drop` MUST для остановленной операции в режиме `auto`
переводить её в `running` и записывать `allow_drop: true` во фронтматтер беклога операции
и беклогов попыток, названных в `backlog.attempt_N`. Беклог без строки `allow_drop` SHALL получить
её после строки `mode`. Согласие SHALL NOT сниматься. Операцию в режиме `interactive` и операцию
не в статусе `stopped` команда с ключом SHALL NOT менять: код `1`.

#### Scenario: Согласие при продолжении
- **WHEN** операция в режиме `auto` остановлена, у неё `allow_drop: false`, и порождён беклог попытки 1
- **THEN** команда возвращает код `0`, статус `running`, беклог операции и беклог попытки 1 содержат `allow_drop: true`, прочие строки беклогов не изменились

#### Scenario: Беклог прежнего шаблона
- **WHEN** в беклоге остановленной операции `auto` нет строки `allow_drop`
- **THEN** строка `allow_drop: true` вставлена после строки `mode`

#### Scenario: Согласие уже дано
- **WHEN** у остановленной операции уже `allow_drop: true`
- **THEN** команда возвращает код `0`, статус `running`, `allow_drop` остаётся `true`

#### Scenario: Операция interactive
- **WHEN** ключ передан для остановленной операции в режиме `interactive`
- **THEN** команда возвращает код `1`, беклог не изменён

#### Scenario: Исполняемая операция
- **WHEN** ключ передан для операции в статусе `running`
- **THEN** команда возвращает код `1`, беклог не изменён

### Requirement: Отчёт перечисляет удаления итогового changelog
`forge report` MUST содержать `allow_drop` операции и перечень `destructive` — удаления
итогового changelog отчёта: принятого при `success`, иначе changelog последней начатой попытки.
Элемент перечня SHALL содержать таблицу и колонку; удалённая таблица MUST иметь `column: null`.
Нет итогового changelog или удалений в нём — перечень пуст.

#### Scenario: Успешная операция с удалениями
- **WHEN** операция закрыта со статусом `success`, а принятый changelog удаляет таблицу `invoice_line` и колонку `customer.email`
- **THEN** `destructive` содержит `{table: invoice_line, column: null}` и `{table: customer, column: email}`

#### Scenario: Операция без удалений
- **WHEN** итоговый changelog операции только создаёт таблицы
- **THEN** `destructive` — пустой перечень

#### Scenario: Попыток не было
- **WHEN** операция остановлена до первой попытки
- **THEN** `destructive` — пустой перечень
