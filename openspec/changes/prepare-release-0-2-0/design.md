# Design

## Context

Зачем нужен change — см. `proposal.md`. Здесь только то, что определяет способ реализации.

- `release.yml` состоит из одного job'а `release`. Право `contents: write` задано на уровне
  workflow. Тест `tests/release/test_release_workflow.py` проверяет структуру по тексту:
  `permissions` верхнего уровня, `jobs.release.steps`, гейт ветки первым шагом.
- Тесты, которым нужно окружение, уже пропускаются сами: без `FORGE_TEST_DB_HOST`
  (`tests/conftest.py`), без `AGENT_RUNNER_URL`/`AGENT_RUNNER_TOKEN` (`tests/integration/conftest.py`)
  и без CLI `backlog` (`tests/operation/backlogs.py`). Если раннер настроен, но не запущен,
  интеграционные тесты падают с `runner_unavailable` — так их и задумывали, документ это
  описывает неверно.
- Локально стоит uv 0.12.7, `uv.lock` — формата `revision = 3`, Python `>=3.12`.
- `main` не защищена, в `default_workflow_permissions` задано `read`: права, объявленные
  в workflow явно, действуют.

## Goals / Non-Goals

**Goals:**

- зелёный `checks` — обязательное условие выпуска, а не договорённость;
- одна копия перечня проверок: команды CI сверяются с разделом «Проверки» `CONTRIBUTING.md`
  тестом, а не глазами.

**Non-Goals:**

- матрица версий Python и ОС — CLI работает в контейнере агента на Linux с Python 3.12;
- кеширование сверх встроенного кеша `setup-uv`;
- изменение логики повышения номера в `release.yml`.

## Decisions

### `checks.yml` — один job с шагами от дешёвых к дорогим

Шаги идут так: `actions/checkout@v4` → `astral-sh/setup-uv@v6` с `version: "0.12.7"`
и `python-version: "3.12"` → `uv sync --frozen` → `uv run ruff check` → `uv run ruff format --check`
→ `uv run mypy src` → `uv run pytest` → `sh tools/make-lint/check.sh`.

- **Почему один job, а не параллельные.** Проверок пять, все быстрые. Отдельные job'ы
  пять раз повторили бы checkout и `uv sync`, а упавший шаг в логе одного job'а виден не хуже.
- **Почему `--frozen`.** CLI в целевом проекте запускается по `uv.lock`, и в CI зависимости
  ставятся так же. Lock-файл, разошедшийся с `pyproject.toml`, ловится явно (спека
  `forge-checks`), а не молча пересобирается.
- **Почему версия uv закреплена.** Новый uv может поменять формат lock-файла, и тогда
  проверка покраснела бы без правки репозитория. Закреплённая версия совпадает с локальной.
- **`uv run pytest` без фильтра маркеров.** Пропуск по окружению уже встроен в фикстуры:
  фильтр `-m "not integration"` спрятал бы тесты, а пропуск с причиной виден в логе.
  Переменные `FORGE_TEST_DB_HOST` и `AGENT_RUNNER_*` workflow не задаёт.

Триггеры: `pull_request` с `branches: [main]`, `push` с `branches: [main]`, `workflow_call`.
Права workflow: `contents: read`.

### `release.yml` вызывает `checks` через `workflow_call`

```text
jobs:
  checks:  uses: ./.github/workflows/checks.yml   permissions: contents: read
  release: needs: checks                           permissions: contents: write
```

- **Альтернатива — проверять статус `checks` на коммите `main` через API.** Отклонена: статус
  может отсутствовать (push без PR, повторный запуск), и тогда понадобилась бы ветка
  «нет статуса». Прогон внутри релиза даёт вердикт на том же коммите, который выпускается.
- **Альтернатива — копировать шаги проверок в `release.yml`.** Отклонена: два перечня
  разошлись бы при первой правке.
- **Права.** Права верхнего уровня `permissions` получают все job'ы, в том числе вызванный
  workflow. Поэтому `permissions` верхнего уровня — `contents: read`, а `contents: write`
  задаётся только job'у `release`.
- **Гейт ветки остаётся первым шагом job'а `release`.** При запуске не из `main` сначала
  отработают проверки, затем гейт завершит прогон ошибкой. Это лишняя минута CI на ошибочном
  запуске, зато сохраняются формулировка и тест гейта.

### Совпадение команд CI и `CONTRIBUTING.md` проверяет тест

Новый `tests/release/test_checks_workflow.py` извлекает команды из блока `bash` раздела
«Проверки» `CONTRIBUTING.md` (без комментариев) и сравнивает их с `run` шагов `checks.yml`
(без `uv sync`). Строки `uv run pytest tests/delivery` и `uv run pytest tests/release` в
`CONTRIBUTING.md` — частные случаи полного `uv run pytest` и в сравнении считаются им
покрытыми. Так требование «Проверки повторяют локальный прогон» становится проверяемым.

### Правки документов и спек

- **Purpose `forge-delivery` и `forge-migration`** правятся прямо в `openspec/specs/`: дельта
  Purpose не переносит. Переименования требований идут через `RENAMED` дельты `forge-migration`.
- **`BUSINESS-REQUIREMENTS.md`.** Пункт границ «только добавляющие изменения» заменяется
  действующими границами со ссылкой на `docs/migration.md`. Номера BR не меняются, новая
  строка версии — `0.3.0`: меняются границы поставки.
- **README «Ограничения»** — по пункту на ограничение продукта, каждый со ссылкой на справочник,
  где ограничение описано. Норма называется кодом, не пересказывается (DGN-010).
- **Кейсы** добавляются в конец как 7 и 8, номера 1–6 не меняются, ссылки
  «Подробнее — кейс N» из README остаются верными (DGN-007). Кейс 7 «обновить forge» —
  ссылкой из шага 1 README (DGN-005).

## Risks / Trade-offs

- [Тесты шаблонов и интеграционные тесты в CI пропускаются] → гейт для них — локальный прогон
  с раннером перед слиянием (критерий задачи #6). Перенос в CI — задача LBFR-019 (#7).
- [`checks` не обязателен для слияния, `main` не защищена] → PR-дисциплина плюс гейт
  проверок внутри релиза. Защита ветки — задача LBFR-020 (#8).
- [`setup-uv@v6` — подвижный major-тег] → это сторонний action с правом только на чтение;
  закрепление по SHA отложено вместе с защитой ветки.
- [Проверки впервые запускаются на PR и могут упасть из-за отличий окружения GitHub от
  контейнера агента: нет `curl`, другая locale] → разбирается на PR до слияния; при сбое
  чинится тест или workflow, а не ослабляется проверка.

## Migration Plan

1. Реализация в `release/v0.2.0`, локальные проверки и полный `pytest` с раннером.
1. Архивация change в ветке, коммит `LBFR-018`, push ветки.
1. PR в `main` с `Closes #5`, `Closes #6`. На PR запускается `checks`, сливается зелёный.
1. `gh workflow run release.yml --ref main -f bump=minor` → `v0.2.0`.
1. Проверка: `releases/latest`, бейдж, установщик `--dry-run` без `--ref`. Текст релиза —
   `gh release edit v0.2.0`.

Откат: если `release` упал на проверках, ничего не записано, и после исправления сценарий
запускается снова. Если сбой случился после push тега — порядок из раздела «Выпуск версии»
`CONTRIBUTING.md`.
