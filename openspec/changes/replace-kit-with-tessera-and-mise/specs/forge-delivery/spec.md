# Spec Delta

## REMOVED Requirements

### Requirement: Установка требует SDD Developer Kit

**Reason**: Kit уходит из разработки, а установщик, который ставил forge только в проект
с kit'ом, удаляется вместе с ним.

**Migration**: forge ставится плагином из маркетплейса репозитория, CLI — из релизного тега.

### Requirement: Версия forge задаётся тегом или локальной копией

**Reason**: Установщик с ключами `--ref` и `--source` удаляется: файлы поставки больше
не копируются в проект.

**Migration**: Версию выбирает тег, переданный команде установки CLI; навык и шаблоны
приходят из плагина, установленного харнесом.

### Requirement: Состав поставки задаёт перечень

**Reason**: Перечень `delivery.txt` удаляется: состав плагина определён его манифестом,
а файлы поставки в проект не попадают.

**Migration**: Шаблоны операций остаются в плагине: навык указывает их каталог команде
`backlog generate` — требование «Шаблоны операций читаются из плагина».

### Requirement: Отличия в файлах kit'а вносятся маркированными блоками

**Reason**: Файлов kit'а больше нет, и отличия forge не во что вносить: целей `make`,
сервиса `claude` и раннера не существует.

**Migration**: Переменные forge объявляет сам проект — в `mise.toml` и `.env.example`
способности `forge-environment`.

### Requirement: Отсутствующий блок вставляется заново

**Reason**: Блоков forge нет, и переустановка kit'а больше не может их стереть.

**Migration**: Не требуется.

### Requirement: Блок раннера стоит за определением белого списка

**Reason**: Раннер удаляется: агент работает на хосту, и CLI вызывает шлюз Liquibase
в своём процессе.

**Migration**: Целей `liquibase-update` и `liquibase-rollback` больше нет; накат и откат
описывает способность `forge-liquibase-gateway`.

### Requirement: Блок внутри литерала переносится за присваивание

**Reason**: Раннера и его белого списка нет, переносить блок некуда.

**Migration**: Проекты со старым блоком в `tools/host-runner/runner.py` удаляют его
по кейсу 12 документа кейсов.

### Requirement: Манифест установки фиксирует поставленное

**Reason**: Установщика нет: манифесту нечего фиксировать, а установленную версию плагина
знает харнес.

**Migration**: Файл `.forge-manifest.json` удаляется из проектов вместе с прежней поставкой.

### Requirement: Правки владельца перезаписываются только с согласия

**Reason**: План установщика и сверка контрольных сумм исчезают вместе с копированием файлов
поставки: файлов, переносимых в проект, больше нет.

**Migration**: Правки владельца в файлах поставки больше не возникают — плагин не записывает
в проект ни одного файла поставки; прежде правленные шаблоны в `templates/` остаются файлами
проекта, но навык их не читает.

### Requirement: Повторная установка идемпотентна

**Reason**: Повторную установку выполняет харнес плагинов, а не репозиторий forge.

**Migration**: Повторный вызов навыка ничего не записывает в проект: шаблоны читаются
из плагина.

### Requirement: Установщик называет следующие шаги

**Reason**: Установщика нет.

**Migration**: Путь после установки описывает `README.md`.

### Requirement: Коды возврата установщика

**Reason**: Установщика нет.

**Migration**: Коды возврата CLI описывает `docs/operation.md`; коды команд среды —
способность `forge-environment-commands`.

## MODIFIED Requirements

### Requirement: CLI запускается одной командой в любом репозитории

Команда `forge <аргументы>` MUST запускать CLI из корня любого проекта, передавая аргументы,
stdout и код возврата без изменений. CLI SHALL быть установлен как изолированный инструмент
и MUST NOT зависеть от `pyproject.toml`, `src/` и виртуального окружения проекта.

#### Scenario: Вызов в целевом проекте

- **WHEN** в установленном проекте выполнено `forge status --latest`
- **THEN** выполняется установленный CLI, и код возврата совпадает с кодом `forge status`

#### Scenario: Собственный Python-проект

- **WHEN** в проекте есть собственные `pyproject.toml` и `src/`
- **THEN** после вызова они не изменились, а окружение проекта не получило зависимостей forge

## ADDED Requirements

### Requirement: Плагин несёт навык и шаблоны операций

В корне репозитория MUST лежать каталог маркетплейса `.claude-plugin/marketplace.json`
с записью `forge-plugin` и записью зависимости `backlog`. Плагин MUST иметь зеркальные
манифесты для ZCode и Claude Code с одинаковым содержимым и нести только каталог навыка
`forge`: инструкции и шаблоны операций.

#### Scenario: Манифесты идентичны

- **WHEN** манифесты плагина для ZCode и Claude Code сравниваются
- **THEN** оба являются корректным JSON и совпадают содержимым

#### Scenario: Зависимость в том же маркетплейсе

- **WHEN** читается каталог маркетплейса
- **THEN** в нём есть записи `forge-plugin` и `backlog`

#### Scenario: Состав плагина

- **WHEN** проверяется содержимое плагина
- **THEN** в нём нет `tests/`, `docs/` и `openspec/` репозитория forge

### Requirement: CLI ставится из релизного тега

CLI MUST устанавливаться из релизного тега репозитория как изолированный инструмент. Версия
установленного пакета SHALL равняться номеру тега.

#### Scenario: Версия из тега

- **WHEN** пакет собран из дерева тега `vX.Y.Z`
- **THEN** его метаданные называют версию `X.Y.Z`

#### Scenario: Тег не существует

- **WHEN** установке передан тег, которого в репозитории нет
- **THEN** установка завершается ошибкой, и команды `forge` не появляется

### Requirement: Навык вызывает CLI одной командой

Навык `forge` MUST вызывать CLI командой `forge`. Если команды нет в `PATH`, навык SHALL
отказать с командой установки до любых вызовов, меняющих статус операции.

#### Scenario: CLI не установлен

- **WHEN** команда `forge` не найдена, и навык вызван с намерением
- **THEN** владелец получает команду установки, беклог не порождён, команд, меняющих статус, не было

#### Scenario: Команда беклога

- **WHEN** в беклоге названа команда `forge …`
- **THEN** она выполняется как `forge …` из корня проекта

### Requirement: Навык находит CLI плагина backlog

Навык `forge` MUST находить исполняемый файл `backlog` и каталог его поставки сам: в `PATH`,
затем в каталогах кеша установленных плагинов харнесов ZCode и Claude Code. Найденный каталог
поставки навык SHALL передавать командам `backlog` переменной `BACKLOG_HOME`. Без CLI или без
каталога поставки навык SHALL отказать с командой установки плагина `backlog` до любых вызовов,
меняющих статус операции.

#### Scenario: CLI в PATH без каталога поставки

- **WHEN** `backlog` найден в `PATH`, а каталог его поставки — только каталог кеша плагина харнеса
- **THEN** команды `backlog` выполняются с `BACKLOG_HOME`, равным найденному каталогу кеша

#### Scenario: Плагин backlog не установлен

- **WHEN** нет ни `backlog` в `PATH`, ни каталога кеша плагина
- **THEN** навык останавливается с командой установки плагина `backlog`, беклог не порождён

### Requirement: Шаблоны операций читаются из плагина

Навык `forge` MUST передавать команде `backlog generate` каталог шаблонов плагина — `templates/`
каталога навыка — ключом `--templates` и значением `templates`. Шаблон операции MUST записывать
это значение во фронтматтер беклога и указывать тем же каталогом в командах порождения беклогов
попыток: агент исполняет их отдельными командами, и переменная окружения между ними не живёт.
Шаблоны в проект не копируются: они всегда соответствуют установленной версии плагина.

#### Scenario: Первый вызов в проекте

- **WHEN** в проекте нет `templates/`, и навык вызван с намерением
- **THEN** беклог порождён по шаблону плагина, и каталог `templates/` в проекте не появился

#### Scenario: Вложенное порождение

- **WHEN** агент исполняет из беклога операции задачу порождения беклога попытки
- **THEN** команда задачи называет каталог шаблонов плагина, и беклог попытки порождён по шаблону плагина

#### Scenario: Обновление плагина

- **WHEN** плагин обновился, и навык вызван в проекте, где операции forge исполнялись прежде
- **THEN** новый беклог порождён по шаблону обновлённого плагина, файлы проекта не изменились

### Requirement: CLI работает в другом проекте

CLI, установленный как инструмент, MUST работать в проекте, отличном от репозитория forge:
поднимать и проверять среду по координатам, объявленным в `mise.toml` проекта, и проходить полный
цикл операции — модель, changelog, накат, сверка, закрытие, отчёт — с принятием результата
в корень принятого состояния этого проекта.

#### Scenario: Полный цикл в чистом проекте

- **WHEN** CLI установлен из репозитория forge, а в другом проекте объявлены инструменты и координаты в `mise.toml`, секреты — в `.env`
- **THEN** `forge env up` и `forge env check` завершаются кодом `0`, операция закрывается со статусом `success`, её таблица появляется в базе проекта, а принятое состояние — в корне принятого состояния проекта

### Requirement: Установка не правит файлы проекта

Установка плагина и CLI MUST NOT добавлять в проект файлы поставки и менять существующие:
конфигурация, документы, `pyproject.toml`, `.gitignore` и `mise.toml` проекта остаются своими.
В проекте появляются только файлы самой работы forge — след операций, локальные файлы в `.forge/`
и принятое состояние.

#### Scenario: Конфигурация проекта не тронута

- **WHEN** плагин установлен, и навык впервые вызван в проекте
- **THEN** `pyproject.toml`, `README.md`, `.gitignore` и `mise.toml` проекта не изменились

#### Scenario: Файлы поставки не появляются в проекте

- **WHEN** навык отработал в проекте
- **THEN** в проекте нет `tests/`, `openspec/`, `docs/` и `templates/` репозитория forge
