# Design

## Context

Мотивация — в [proposal.md](./proposal.md), требования — в дельтах `specs/`. Здесь — только
исходное состояние, которое определяет подход.

- **Цепочка исполнения сегодня**: агент в контейнере kit'а → HTTP-вызов раннера на хосте →
  `make liquibase-<действие>` → `tools/liquibase/gateway.py` → `docker compose run lbfr-liquibase`.
  Параметры и исход проходят файлами `.forge/liquibase-request.json` и `.forge/liquibase-result.json`,
  потому что `make` и клиент раннера искажают код возврата.
- **Поставка сегодня**: `install.sh` копирует файлы по `delivery.txt` и вставляет блоки
  в пять файлов kit'а; манифест `.forge-manifest.json` хранит суммы для защиты правок владельца.
- **Окружение workspace** (проверено в каталоге проекта): каскад mise доносит задачи общего
  набора (`env-up`, `env-status`), в реестре mise есть `liquibase` до `5.0.4`, демон `postgres`
  workspace объявлен на порту `5432`. Имён задач workspace, совпадающих с `forge-*`, `lint`,
  `format-check`, `types`, `test`, нет.
- **Защита `main`**: ruleset требует проверку с именем job'а — «Линтер, форматирование, типы,
  тесты, Makefile». Имя job'а — имя проверки в GitHub.
- **Ограничение OpenSpec 2.1.0**: внутри MODIFIED-блока имена сценариев сохраняются — валидатор
  отклоняет блок, который теряет сценарий текущей спецификации.
- **Changelog forge**: `master.yaml` собирает изменения записями `include` с относительными
  путями; контейнер Liquibase запускался из корня проекта с `--search-path=.`.

## Goals / Non-Goals

**Goals:**

- Одно окружение для репозитория разработки и целевого проекта: mise, PostgreSQL общего набора,
  нативный Liquibase — без Docker, Compose, раннера и `Makefile`.
- CLI `forge` — единственная точка входа в среду: подготовка, проверка, накат и откат.
- Поставку можно обновить переустановкой плагина и CLI из тега, не правя файлы проекта.
- Все нормы изменённой среды выражены требованиями, а не только документами.

**Non-Goals:**

- Публикация CLI в PyPI и запись `forge-plugin` в маркетплейс tessera — отдельно от изменения.
- Смена формата модели, миграций и операций: предметная часть forge не меняется.
- Правки самого tessera и workspace: их правила и каскад потребляются как есть.
- Изменение правил `GIT-021` и `GIT-009`.

## Decisions

### 1. Правила приходят из плагина, точка входа одна — `AGENTS.md`

`AGENTS.md` переписывается в короткую точку входа: источник правил — плагин tessera и его
навык-каталог; для харнеса без плагинов — клон tessera и регистрация навыков его скриптом;
далее — проектные документы. `CLAUDE.md` удаляется.

- **Почему так**: правила tessera лежат в установленном плагине, путь к которому зависит
  от харнеса и пользователя, — относительная ссылка из репозитория на них невозможна.
- **Альтернатива — держать копии правил в `rules/`**: расходится с плагином при первом
  обновлении и удерживает kit в репозитории.
- **Альтернатива — вести и `AGENTS.md`, и `CLAUDE.md`**: две точки входа расходятся; tessera
  ведёт одну.
- **Следствие**: норм `MAKE-*`, `DOCK-*` и `TERM-*` в плагине tessera нет — их коды уходят
  из документов вместе с `Makefile` и Compose; нормы называют кодом tessera (`ENV-006`,
  `GIT-009`, `DOC-014`) без ссылки на локальный файл.

### 2. Каталоги харнесов остаются на диске и покидают индекс

`.claude/` и `.zcode/` исключаются из индекса командой `git rm --cached`, файлы на диске
не трогаются. Навыки и команды OpenSpec разворачивает локально `openspec init`; каталог
`openspec/` со спецификациями остаётся в репозитории.

- **Почему так**: регистрация харнеса — выбор разработчика, а не поставка; зафиксированные
  навыки OpenSpec отставали бы от версии CLI.
- **Альтернатива — удалить каталоги с диска**: ломает рабочее место разработчика, которое
  изменить изменение не обязано.
- **Действия владельца**: навык `forge` переносится в плагин, поэтому ссылка
  `.zcode/skills/forge` на старый путь заменяется ссылкой на каталог навыка плагина;
  локальная копия навыка `project-docs` kit'а удаляется после установки плагина tessera.
  Обе команды — в разделе «Локальная настройка» `CONTRIBUTING.md`.

### 3. Шлюз Liquibase вызывается в процессе CLI

Контракт шлюза (`GatewayResult`, `GatewayUnavailableError`) сохраняется. Реализация через
раннер заменяется локальной: проверки (путь changelog, перечень тестовых БД), запуск Liquibase
подпроцессом и разбор кода возврата выполняются в процессе `forge`. Проверки шлюза переходят
в модуль миграции CLI; `tools/liquibase/gateway.py`, `src/forge/shared/infrastructure/runner.py`
и `runner_gateway.py` удаляются.

- **Почему так**: файлы обмена существовали из-за границы процессов и искажения кода возврата;
  в одном процессе причина исчезла.
- **Альтернатива — сохранить протокол файлов и вызывать шлюз подпроцессом**: два процесса
  и два файла без причины; требование «Каталог обмена скрыт от git» остаётся выполненным
  через запись `.forge/.gitignore` при загрузке драйвера.
- **Коды ошибок**: `runner_unavailable` заменяется на `liquibase_unavailable`; `gateway_result_invalid`
  уходит вместе с файлом результата; `gateway_refused` сохраняется.

### 4. Liquibase — инструмент mise, драйвер — в `.forge/lib/`

Liquibase закрепляется в `[tools]` файла `mise.toml` вместе с Java; драйвер PostgreSQL
скачивается с закреплёнными в CLI адресом, версией и контрольной суммой и подключается
параметром classpath.

- **Почему так**: в реестре mise есть Liquibase `5.0.4`; нативный запуск убирает Docker
  полностью, как решено владельцем.
- **Альтернатива — одноразовый `docker run`**: оставляет Docker в предусловиях и расходится
  со стандартом workspace для инструмента, который mise ставит сам.
- **Альтернатива — положить драйвер в пакет CLI**: привязывает драйвер к выпуску CLI и
  утяжеляет пакет; локальный каталог позволяет сменить пару «версия — сумма» переменными.
- **Загрузка**: `forge env up` скачивает драйвер, если файла с верной суммой нет; шлюз
  отказывает с кодом `2`, не скачивая на ходу, — обращение к сети не прячется в накат.

### 5. Процесс Liquibase работает вне проекта, читая проект через search path

Шлюз запускает Liquibase с рабочим каталогом во временном каталоге вне проекта, передаёт
путь changelog относительно корня проекта и задаёт search path корнём проекта.

- **Почему так**: записи `include` с относительными путями разрешаются от корня проекта,
  как в контейнере с `--search-path=.`; относительная запись при этом попала бы во временный
  каталог, а не в проект.
- **Альтернатива — рабочим каталогом сделать корень проекта**: полный паритет с контейнером,
  но проект открыт и для записи, которой раньше не давало монтирование «только чтение».
- **Проверка**: интеграционный тест сравнивает дерево проекта до и после наката — меняются
  только файлы, которые пишет сам `forge`.

### 6. PostgreSQL — общий экземпляр workspace, изоляция базами

Собственные сервисы БД удаляются. Целевая БД репозитория разработки — база на демоне `postgres`
workspace; тесты создают на нём же базы `t_<идентификатор>`. В перечень тестовых БД добавляется
шаблон префикса: `t_*` разрешает базы с этим началом имени.

- **Почему так**: стандарт окружения (ENV-007) делит общий экземпляр базами; записи `*` на
  общем сервере было бы слишком широко — она разрешала бы базу любого проекта.
- **Альтернатива — собственный демон `postgres` в `mise.toml` проекта на отдельном порту**:
  осознанное исключение стандарта, второй сервер ради тестов; владельцем выбран общий экземпляр.
- **Адрес по умолчанию**: хост `localhost`, порт `PG_PORT` из каскада, иначе `5432` — умолчания
  живут в инструменте (ENV-005), а не дублируются в `mise.toml`.

### 7. Подготовка среды — команды CLI, а не скрипты поставки

Добавляются `forge env check` и `forge env up`. Первая повторяет четыре проверки `forge status`
и печатает каждую; вторая идемпотентно создаёт роль и базу, загружает драйвер. Сценарии лежат
в модуле `shared` — среда не предметное понятие; реализации — подключение администратора
к PostgreSQL и хранилище драйвера.

- **Почему так**: в целевом проекте у плагина нет стабильного пути — задачи mise могут звать
  только то, что лежит на `PATH`. Логика в CLI проверяется тестами и поставляется с версией CLI.
- **Альтернатива — скрипты внутри плагина**: путь к установленному плагину зависит от харнеса.
- **Альтернатива — задачи mise с логикой в рецептах**: рецепт копируется в каждый проект
  и расходится с версией forge.
- **Альтернатива — обойтись `forge status`**: он занят поиском операции и не готовит среду.

### 8. `mise.toml` — инструменты, переменные и задачи в одном файле

`[tools]`: интерпретатор Python, `uv`, Java, Liquibase. `[env]`: несекретные координаты forge
и подключение `.env`. Задачи: `forge-env-up`, `forge-env-check`, `forge` — обёртки над CLI;
`lint`, `format-check`, `types`, `test` — проверки.

- **Почему так**: ENV-001 и ENV-006 задают один файл и задачи mise вместо `Makefile`.
- **Имена с `forge-`**: в каскаде задачи проекта и workspace видны вместе; непроиндексированные
  имена (`env-up`, `init`) перекрыли бы общий набор.
- **Альтернатива — задачи файлами в `mise-tasks/`**: восемь коротких задач читаются и в одном
  файле; вынос допустим позже без смены поведения.

### 9. Плагин по образцу tessera

`plugins/forge-plugin/` несёт зеркальные манифесты `.zcode-plugin/plugin.json` и
`.claude-plugin/plugin.json` и каталог навыка `skills/forge` с шаблонами операций; в корне —
`.claude-plugin/marketplace.json` с записями `forge-plugin` и `backlog` (зависимость навыка).
CLI ставится из релизного тега: `uv tool install` собранного пакета.

- **Почему так**: форма, к которой приспособлены ZCode и Claude Code; зависимость ставится
  с той же страницы маркетплейса.
- **Версия в манифестах** (решение владельца): номер вносит разработчик в подготовительном
  изменении `prepare-release-X.Y.Z`, релизный сценарий сверяет его с выпускаемым. Релизный
  коммит остаётся одним файлом, правило `GIT-021` не трогается.
- **Альтернатива — версию пишет релизный сценарий**: один источник, но требуется расширить
  `GIT-021` в tessera до набора носителей версии.
- **Альтернатива — независимая версия плагина**: номер плагина и номер CLI расходятся.
- **Альтернатива — публикация в PyPI**: нужны учётные данные и шаг в релизе; тег уже является
  носителем версии.

### 10. Шаблоны операций читаются из плагина

Навык `forge` передаёт команде `backlog generate` каталог шаблонов плагина — `templates/`
внутри каталога навыка — ключом `--templates` и значением `templates`. Значение записывается
во фронтматтер беклога операции и стоит в командах порождения беклогов попыток: агент исполняет
их отдельными командами, и переменная окружения (`BACKLOG_TEMPLATES`) между ними не живёт.
В проект не копируется ничего: шаблоны всегда соответствуют установленной версии плагина.
Навык вызывает CLI командой `forge` и при её отсутствии отказывает с командой установки.

- **Почему так**: у CLI `backlog` есть ключ `--templates` — обнаружено при реализации, им уже
  пользуется набор тестов репозитория; копии шаблонов в проекте отставали бы от плагина.
- **Альтернатива — копировать шаблоны в `templates/` проекта**: так делал установщик; копии
  устаревают, а правки владельца в них не отслеживаются. Отвергнута владельцем.
- **Цена**: настроить шаблон под отдельный проект нельзя — изменение шаблона идёт предложением
  в репозиторий forge.
- **В репозитории разработки** навык вызывает `forge` в оболочке с активированным mise
  (`uv sync` ставит CLI на `PATH`); ссылка на навык плагина в `.zcode/skills/` — локальная
  настройка.

### 11. Проверки в CI — mise и нативный PostgreSQL

Workflow ставит инструменты mise по `mise.toml`, запускает задачи проверок, поднимает
предустановленный сервер PostgreSQL образа раннера и передаёт тестам его координаты;
драйвер загружает `forge env up`. Job переименован в «Линтер, форматирование, типы, тесты».

- **Почему так**: те же команды, что локально (требование «Проверки повторяют локальный
  прогон»), и ни одного вызова Docker.
- **Альтернатива — сервис-контейнер `postgres`**: под капотом Docker, от которого решено уйти.
- **Альтернатива — демон mise в CI**: экспериментальная функция на одноразовой машине.
- **Имя проверки**: ruleset `main` обновляется той же правкой; порядок переключения — в «Migration Plan».

### 12. Замена требований через REMOVED и ADDED

Там, где имена сценариев стали ложными («Раннер недоступен», «Превышение объёма секции
Makefile», «Первый запрос в проекте»), требования заменены: старое удаляется с причиной
и миграцией, новое добавляется под точным именем. Прочие требования меняются блоками MODIFIED.

- **Почему так**: валидатор OpenSpec 2.1.0 сохраняет имена сценариев MODIFIED-блока; тело
  сценария «Раннер недоступен» теперь описывает Liquibase.
- **Альтернатива — оставить старые имена сценариев с новым телом**: имя обещает несуществующую среду.

### 13. Инструменты объявляет проект, куда ставится forge

В `mise.toml` целевого проекта закрепляются `uv`, `java` и `liquibase` — тем же фрагментом,
что и в репозитории разработки; координаты forge — в его секции `[env]`, секреты — в `.env`.
Внутри workspace каскад доносит до проекта сервер PostgreSQL (`PG_PORT`) и инструменты корня;
сами `uv`, `java` и `liquibase` в корне workspace не закрепляются.

- **Почему так**: состав закреплённого в workspace минимален (ENV-001) — Java и Liquibase нужны
  только проектам с forge.
- **Альтернатива — закрепить инструменты в корне workspace**: один фрагмент на все дочерние
  проекты, но правка в другом репозитории, где forge сейчас отключён, и инструменты для всех
  подряд. Отвергнута владельцем.
- **CLI — на пользователя**: `uv tool install` ставит одну версию на машину. Разные версии
  в разных проектах не поддерживаются — ограничение фиксируется в `README.md`.
- **База в другом проекте**: внутри workspace — общий экземпляр через каскад; вне workspace
  проект объявляет демона `postgres` в своём `mise.toml` либо задаёт адрес внешнего сервера.

### 14. Сквозная проверка в чистом проекте

Помимо тестов репозитория, функциональность проверяется там, где её будут применять: CLI
ставится из рабочего дерева в изолированный каталог инструментов uv, чистый временный проект
получает свой `mise.toml`, `.env` и собственный Python-проект, `forge env up` готовит среду,
и через CLI — в оболочке с активированным mise — проходит полный цикл операции: модель,
changelog, накат, сверка, закрытие, отчёт — на общем экземпляре PostgreSQL workspace.
Прогон оформлен интеграционным тестом и идёт вместе с остальными. Навык `/forge` целиком
не прогоняется: установку плагина в харнес делает владелец; порождение беклогов навыком
проверено вручную реальным CLI `backlog` с шаблонами плагина.

## Risks / Trade-offs

- [Окно между применением ruleset и слиянием: PR со старым именем проверки не может слиться]
  → Владелец применяет ruleset непосредственно перед слиянием PR изменения; окно занимает
  минуты; остальным PR достаточно перезапуска проверок после слияния.
- [Нативный Liquibase и драйвер отличаются от прежде собиравшегося образа] → версии
  закреплены в `mise.toml` и в CLI; накат и откат исполняются настоящим Liquibase в
  интеграционных тестах локально и в CI.
- [Разрешение относительных `include` вне корня проекта] → search path равен корню проекта;
  интеграционный тест накатывает принятый `master.yaml` с записями `include`.
- [Тесты создают базы на общем сервере; упавший тест оставляет базу] → фикстура удаляет базу
  в `finally` с `DROP DATABASE … WITH (FORCE)`; оставшиеся базы узнаются по префиксу `t_`.
- [Драйвер требует сети при первой подготовке] → загрузка только в `forge env up`, контрольная
  сумма закреплена; файл можно положить в `.forge/lib/` заранее.
- [Агент больше не изолирован песочницей: CLI работает с правами пользователя хоста] →
  свойство отказа от песочницы, принятое вместе с tessera; перечень тестовых БД сохраняет
  границу наката, `forge` пишет только в `backlog/`, `.forge/` и корень принятого состояния.
- [В оболочке без активации mise нет `liquibase` и `forge`] → `forge env check` называет
  `mise install`; README требует активации mise или запуска через `mise x --`.
- [Номер в манифестах вносится вручную] → гейт релиза отказывает при расхождении; тест
  сверяет манифесты между собой.
- [Ссылки навыка на документы репозитория не работают внутри установленного плагина] →
  при переносе навыка ссылки заменяются называнием документов; документы в плагин не входят.
- [Правил терминологии в tessera нет] → коды `TERM-*` уходят из документов; единый язык
  остаётся в `docs/domain.md`.
- [Шаблоны читаются из плагина: подстроить шаблон под отдельный проект нельзя] → цена единого
  источника, принятая владельцем; изменение шаблона идёт предложением в репозиторий forge.
- [CLI один на машину: двум проектам нужны разные версии forge] → ограничение фиксируется
  в `README.md`; по-проектное закрепление версии — отдельное изменение.
- [Скрипт CI опирается на предустановленный PostgreSQL образа `ubuntu-latest`] → пароль задаётся
  через локальный сокет, служба запускается `systemctl`, затем `service`; смена образа
  проверяется первым прогоном workflow.
- [CLI `backlog` под ZCode не находит каталог поставки без `BACKLOG_HOME`] → навык `forge`
  перед вызовом сам задаёт `BACKLOG_HOME` каталогом кеша найденного плагина.

## Migration Plan

1. **До работы в ветке**: владелец устанавливает плагин tessera в харнес.
2. **Реализация изменения** в ветке: удаление kit'а и Docker, `mise.toml`, команды среды,
   шлюз в процессе, плагин, CI, документы, тесты.
3. **Сквозной прогон в чистом проекте** до PR: CLI из рабочего дерева, `forge env up` и полный
   цикл операции через CLI на общем экземпляре PostgreSQL (решение 14).
4. **PR**: проверки идут под новым именем job'а. До слияния владелец применяет ruleset ветки:
   `sh tools/github/apply-ruleset.sh .github/rulesets/main.json`.
5. **После слияния — рабочие места**: `mise install`; демон `postgres` общего набора
   (`mise daemons start postgres`; `mise run env-up` поднимает весь набор workspace);
   заполнить секреты в `.env` по `.env.example`; `forge env up`; `forge env check`;
   пересоздать ссылку `.zcode/skills/forge` на каталог навыка плагина.
6. **Целевые проекты с прежней поставкой**: migrируют по кейсу 12 — удалить файлы поставки
   и блоки, выгрузить данные целевой БД клиентом, поставить плагин и CLI, восстановить данные
   в базу на общем экземпляре.
7. **Откат**: обратное слияние PR; имя проверки возвращается, владелец повторно применяет
   ruleset. Данные целевой БД репозитория разработки не переносятся: схему восстанавливает
   накат принятых changelog, принятое состояние `.forge/db` лежит вне индекса и не затрагивается.
