# Spec Delta

## MODIFIED Requirements

### Requirement: Неподдерживаемые изменения отклоняются
Смена типа или его параметров, смена итоговой допустимости NULL, смена первичного ключа, а также
появление или снятие `generated` у существующей колонки MUST отклоняться кодом `1` с перечнем всех
таких изменений. Удаление колонки первичного ключа SHALL отклоняться как смена первичного ключа.
Переименование SHALL распознаваться как удаление с добавлением. Changelog при отказе MUST NOT
записываться, а прежний файл `--out` SHALL удаляться.

#### Scenario: Удалённая колонка
- **WHEN** в модели попытки нет колонки `id`, входящей в первичный ключ таблицы `customer` принятой модели
- **THEN** команда возвращает код `1`, перечень содержит `primary_key_changed` для `customer`, а файла changelog нет

#### Scenario: Несколько неаддитивных изменений
- **WHEN** модель попытки меняет тип одной колонки и первичный ключ другой таблицы
- **THEN** перечень содержит оба изменения

#### Scenario: Переименование колонки
- **WHEN** модель попытки содержит колонку `mail` вместо колонки `email` принятой модели с тем же типом
- **THEN** команда возвращает код `0`, changelog удаляет `email` и добавляет `mail`

#### Scenario: Генерация значения у существующей колонки
- **WHEN** колонка `customer.id` принятой модели не имеет `generated`, а в модели попытки имеет `generated: identity`
- **THEN** команда возвращает код `1`, перечень содержит `column_generated_changed` для `customer.id`, а файла changelog нет

#### Scenario: Снятие генерации значения
- **WHEN** колонка `customer.id` принятой модели имеет `generated: identity`, а в модели попытки — нет
- **THEN** перечень содержит `column_generated_changed` для `customer.id`

### Requirement: Changeset однозначно идентифицирован
Каждый changeset MUST содержать одну таблицу, одну колонку либо одно ограничение — внешний ключ,
набор уникальности или перечень значений, иметь `id` вида `<штамп>-<NN>` с номером по порядку
от `01`, `author: forge` и `logicalFilePath` `db/changelog/<штамп>.yaml` независимо от корня
принятого состояния. Штамп SHALL браться из `subject` беклога операции и соответствовать шаблону
`YYYYMMDD-HHMMSS`.

#### Scenario: Идентичность changeset
- **WHEN** беклог операции имеет `subject: "20261017-153000"`, и строятся два changeset
- **THEN** их `id` — `20261017-153000-01` и `20261017-153000-02`, а `logicalFilePath` у обоих `db/changelog/20261017-153000.yaml`

#### Scenario: Штамп не по шаблону
- **WHEN** `subject` беклога операции не соответствует шаблону штампа либо беклога нет
- **THEN** команда возвращает код `2`, changelog не записан

#### Scenario: Логический путь не зависит от корня
- **WHEN** `FORGE_ACCEPTED_DIR=.forge/db`, а беклог операции имеет `subject: "20261017-153000"`
- **THEN** `logicalFilePath` changeset — `db/changelog/20261017-153000.yaml`

#### Scenario: Ограничение — отдельный changeset
- **WHEN** модель попытки создаёт таблицу `invoice` с одним FK и одним набором `unique`
- **THEN** changelog содержит changeset создания `invoice`, отдельный changeset набора уникальности и отдельный changeset внешнего ключа

#### Scenario: Перечень — отдельный changeset
- **WHEN** модель попытки создаёт таблицу `event` с колонкой `source`, у которой `check: [collector, manual]`
- **THEN** changelog содержит changeset создания `event` и отдельный changeset перечня `source`, а ответ называет его видом `add_check` с именем ограничения

### Requirement: Схема после наката соответствует модели
Накат changelog MUST создавать колонки с типами PostgreSQL по таблице отображения формата,
NOT NULL по итоговой допустимости NULL, генерацию значения `GENERATED BY DEFAULT AS IDENTITY`
у колонок с `generated: identity` и первичный ключ `pk_<таблица>` с колонками в порядке
`primary_key` модели.

#### Scenario: Составной ключ в порядке модели
- **WHEN** таблица объявляет колонки `line_no`, `invoice_id` и `primary_key: [invoice_id, line_no]`
- **THEN** после наката ограничение `pk_<таблица>` содержит колонки в порядке `invoice_id`, `line_no`

#### Scenario: Типы PostgreSQL
- **WHEN** накатан changelog модели со всеми десятью типами формата
- **THEN** фактические типы колонок совпадают с таблицей отображения `docs/model-format.md`

#### Scenario: Ключ с генерацией значения
- **WHEN** накатан changelog таблицы `customer` с ключом `id bigint` и `generated: identity`
- **THEN** колонка `customer.id` в БД — identity `BY DEFAULT`, вставка без `id` получает значение от БД, а вставка с явным `id` принимается

#### Scenario: Новая колонка с генерацией в таблице со строками
- **WHEN** модель попытки добавляет колонку `seq_no` с `generated: identity` в таблицу, где уже есть строки
- **THEN** накат проходит, и каждая существующая строка получает значение `seq_no` от БД

### Requirement: Changeset удаления несёт откат по принятой модели
Каждый changeset удаления MUST содержать явный откат, восстанавливающий структуру объекта
по принятой модели: таблицу с колонками, типами, NOT NULL, генерацией значения и первичным ключом
`pk_<таблица>`, колонку — с типом, NOT NULL и генерацией значения. Данные удалённого объекта откат
SHALL NOT восстанавливать.

#### Scenario: Откат удаления таблицы через Liquibase
- **WHEN** накатан changelog, удаливший таблицу `invoice_line` с первичным ключом `[invoice_id, line_no]`, и выполнен его откат Liquibase
- **THEN** таблица `invoice_line` есть в схеме с колонками и типами принятой модели и ключом `pk_invoice_line` по `invoice_id, line_no`

#### Scenario: Частичный накат с удалением
- **WHEN** changelog удаляет колонку и добавляет таблицу, а Liquibase записал в журнал только первый changeset
- **THEN** откат снимает ровно один changeset, и удалённая колонка восстановлена

#### Scenario: Откат удаления таблицы с генерацией значения
- **WHEN** откатывается попытка, удалившая таблицу `customer`, у которой `id` имеет `generated: identity`
- **THEN** после отката колонка `customer.id` снова identity `BY DEFAULT`

### Requirement: Ограничения отождествляются по содержимому
`forge generate` MUST сравнивать внешние ключи принятой модели и модели попытки по колонкам FK,
целевой таблице и колонкам цели, наборы уникальности — по составу колонок, перечни значений —
по колонке и множеству значений. Новое ограничение SHALL давать changeset добавления,
исчезнувшее — changeset удаления; изменение ограничения MUST выражаться удалением прежнего
и добавлением нового.

#### Scenario: Новый внешний ключ существующей таблицы
- **WHEN** модель попытки добавляет FK `invoice.customer_id` → `customer.id` к таблицам принятой модели
- **THEN** changelog содержит один changeset добавления этого FK и не трогает остальные объекты

#### Scenario: Перестановка наборов
- **WHEN** модель попытки отличается от принятой только порядком элементов `unique` и `foreign_keys`
- **THEN** changelog не содержит ни одного changeset

#### Scenario: Смена цели внешнего ключа
- **WHEN** FK таблицы `invoice` в модели попытки ссылается на `customer.email` вместо `customer.id`
- **THEN** changelog содержит changeset удаления прежнего FK и changeset добавления нового

#### Scenario: Перестановка значений перечня
- **WHEN** модель попытки отличается от принятой только порядком значений `check` колонки `event.source`
- **THEN** changelog не содержит ни одного changeset

#### Scenario: Расширение перечня
- **WHEN** перечень `event.source` в модели попытки — `[collector, manual, import]`, а в принятой — `[collector, manual]`
- **THEN** changelog содержит changeset удаления прежнего перечня вида `drop_check` и changeset добавления нового вида `add_check`

#### Scenario: Перечень у новой колонки существующей таблицы
- **WHEN** модель попытки добавляет в таблицу `event` колонку `channel` с `check: [web, api]`
- **THEN** changeset добавления колонки `channel` идёт раньше changeset её перечня

### Requirement: Имя ограничения вычисляется из содержимого
Имя внешнего ключа MUST быть `fk_<таблица>_<hash8>`, имя набора уникальности —
`uq_<таблица>_<hash8>`, имя перечня значений — `ck_<таблица>_<hash8>`, где `hash8` — восемь
шестнадцатеричных знаков хеша содержимого ограничения. Имя таблицы SHALL обрезаться так, чтобы
имя ограничения не превышало 63 символов. Одинаковое содержимое MUST давать одинаковое имя
в любой модели.

#### Scenario: Имя не зависит от порядка
- **WHEN** один и тот же FK стоит первым в одной модели и вторым в другой
- **THEN** имя его ограничения в обоих changelog одинаково

#### Scenario: Длинное имя таблицы
- **WHEN** имя таблицы состоит из 60 символов, и у неё есть набор уникальности
- **THEN** имя ограничения не длиннее 63 символов и заканчивается восемью шестнадцатеричными знаками

#### Scenario: Имя перечня не зависит от порядка значений
- **WHEN** перечень `event.source` записан как `[collector, manual]` в одной модели и как `[manual, collector]` в другой
- **THEN** имя ограничения `ck_event_<hash8>` в обоих changelog одинаково

### Requirement: Порядок changeset учитывает ограничения
Changeset MUST идти группами: удаление внешних ключей, удаление наборов уникальности, удаление
перечней значений, удаление таблиц, удаление колонок, создание таблиц, добавление колонок,
добавление наборов уникальности, добавление перечней значений, добавление внешних ключей.
Внутри группы порядок SHALL следовать модели, из которой взят объект.

#### Scenario: Ссылка на таблицу ниже по модели
- **WHEN** модель попытки создаёт `invoice` раньше `customer`, а `invoice` ссылается на `customer`
- **THEN** changeset внешнего ключа идёт после создания обеих таблиц, и накат проходит

#### Scenario: Внешний ключ на новый набор уникальности
- **WHEN** модель попытки добавляет `unique: [[email]]` к `customer` и FK на `customer.email`
- **THEN** changeset набора уникальности идёт раньше changeset внешнего ключа

#### Scenario: Удаление колонки с перечнем
- **WHEN** модель попытки удаляет колонку `event.source`, у которой в принятой модели был `check`
- **THEN** changeset удаления перечня идёт раньше changeset удаления колонки

### Requirement: Удаление таблицы снимает связанные внешние ключи отдельно
Внешние ключи удаляемой таблицы и внешние ключи других таблиц на неё MUST удаляться отдельными
changeset до удаления таблицы. Откат удаления таблицы SHALL восстанавливать таблицу, первичный
ключ, её наборы уникальности и перечни значений; внешние ключи MUST восстанавливаться откатом
своих changeset.

#### Scenario: Удаление таблицы со ссылкой
- **WHEN** модель попытки удаляет таблицы `invoice` и `customer`, где `invoice` ссылается на `customer`
- **THEN** changeset удаления FK `invoice` идёт раньше changeset удаления обеих таблиц

#### Scenario: Откат удаления таблицы со связями
- **WHEN** откатывается попытка, удалившая `invoice` с FK на `customer` и набором `unique`
- **THEN** после отката таблица `invoice`, её набор уникальности и FK на `customer` есть в схеме

#### Scenario: Откат удаления таблицы с перечнем
- **WHEN** откатывается попытка, удалившая таблицу `event` с перечнем `source`
- **THEN** после отката ограничение перечня `ck_event_<hash8>` есть в схеме

### Requirement: Удаление ограничения откатывается и не требует согласия
Changeset удаления внешнего ключа, набора уникальности или перечня значений MUST содержать откат,
восстанавливающий ограничение по принятой модели. Удаление ограничения SHALL NOT требовать
`allow_drop` в режиме `auto` и SHALL NOT считаться удалением данных.

#### Scenario: Удаление FK в auto без согласия
- **WHEN** беклог операции имеет `mode: auto` и `allow_drop: false`, а модель попытки только убирает FK
- **THEN** команда возвращает код `0`, и changelog содержит changeset удаления FK с откатом

#### Scenario: Удаление колонки из набора
- **WHEN** модель попытки удаляет колонку `customer.email` и набор `unique: [[email]]`
- **THEN** changeset удаления набора уникальности идёт раньше changeset удаления колонки

#### Scenario: Снятие перечня в auto без согласия
- **WHEN** беклог операции имеет `mode: auto` и `allow_drop: false`, а модель попытки только убирает `check` у колонки `event.source`
- **THEN** команда возвращает код `0`, и changelog содержит changeset удаления перечня с откатом

### Requirement: Схема после наката содержит ограничения модели
Накат changelog MUST создавать внешние ключи с колонками в порядке FK, целевой таблицей
и колонками цели в парном порядке, с действием `NO ACTION`, ограничения уникальности
с колонками набора и ограничения `CHECK`, допускающие в колонке только значения перечня и NULL.

#### Scenario: Составной внешний ключ
- **WHEN** накатан FK `[invoice_id, line_no]` → `invoice_line.[invoice_id, line_no]`
- **THEN** ограничение в БД связывает колонки попарно в этом порядке

#### Scenario: Значение вне перечня
- **WHEN** накатан перечень `event.source` `[collector, manual]`, и в `event` вставляется строка с `source = 'robot'`
- **THEN** БД отклоняет вставку нарушением ограничения `ck_event_<hash8>`

#### Scenario: Перечни для всех допустимых типов
- **WHEN** накатан changelog с перечнями у колонок `string`, `text`, `integer` и `bigint`
- **THEN** каждое ограничение есть в БД и пропускает только значения своего перечня и NULL

### Requirement: Возврат ограничений подтверждается проверкой
После отката `forge rollback` MUST проверять по вычисленному имени, что ограничений, которые
changelog попытки добавляет, нет в схеме (`foreign_key_absent`, `unique_absent`, `check_absent`),
а ограничения, которые он удаляет, есть (`foreign_key_present`, `unique_present`, `check_present`).
Непройденная проверка SHALL давать код `1`.

#### Scenario: Добавленный FK снят
- **WHEN** откатывается попытка, добавившая FK
- **THEN** `rollback.json` содержит пройденную проверку `foreign_key_absent` с именем ограничения

#### Scenario: Удалённый набор не восстановлен
- **WHEN** после отката попытки, удалившей набор уникальности, ограничения в схеме нет
- **THEN** проверка `unique_present` не пройдена, команда возвращает код `1`

#### Scenario: Добавленный перечень снят
- **WHEN** откатывается попытка, добавившая перечень `event.source`
- **THEN** `rollback.json` содержит пройденную проверку `check_absent` с именем `ck_event_<hash8>`

#### Scenario: Удалённый перечень восстановлен
- **WHEN** откатывается попытка, расширившая перечень `event.source`
- **THEN** `rollback.json` содержит пройденную проверку `check_absent` нового перечня и `check_present` прежнего

### Requirement: Изменения модели не ломают принятый seed
`forge generate` MUST проверять модель попытки против принятого seed и при конфликте возвращать
`1` с `changelog: null` и перечнем `seed_conflict`. Конфликты:
- удаление таблицы принятого seed;
- новая колонка NOT NULL в таблице с seed-строками;
- новый FK или набор `unique`, которому строки принятого seed не отвечают;
- новый или изменённый перечень значений, которому строки принятого seed не отвечают.

Нет `<корень>/seed.yaml` — конфликтов нет.

#### Scenario: Удаление справочника
- **WHEN** модель попытки удаляет таблицу `order_status`, а она есть в принятом seed
- **THEN** команда возвращает `1`, `seed_conflict` называет `order_status` и вид `seeded_table_dropped`

#### Scenario: Новая обязательная колонка
- **WHEN** модель попытки добавляет колонку `sort_order` с `nullable: false` в `order_status`, у которой в принятом seed есть строки
- **THEN** команда возвращает `1`, `seed_conflict` называет колонку и вид `not_null_column_added`

#### Scenario: Обязательная колонка в пустом справочнике
- **WHEN** таблица есть в принятом seed с `rows: []`, а модель добавляет в неё колонку NOT NULL
- **THEN** конфликта нет

#### Scenario: Новый unique, которому seed не отвечает
- **WHEN** модель попытки добавляет набор `unique` `[title]`, а две строки принятого seed имеют одинаковый `title`
- **THEN** команда возвращает `1`, `seed_conflict` называет набор и вид `unique_violated_by_seed`

#### Scenario: Удаление колонки справочника
- **WHEN** модель попытки удаляет колонку `order_status.color`
- **THEN** конфликта нет, changelog строится как обычно

#### Scenario: Суженный перечень, которому seed не отвечает
- **WHEN** модель попытки задаёт `check: [draft, paid]` колонке `order_status.code`, а в принятом seed есть строка с `code: cancelled`
- **THEN** команда возвращает `1`, `seed_conflict` называет колонку `code` и вид `check_violated_by_seed`

#### Scenario: Новая колонка с генерацией в справочнике со строками
- **WHEN** модель попытки добавляет колонку `seq_no` с `generated: identity` в `order_status`, у которой в принятом seed есть строки
- **THEN** команда возвращает `1`, `seed_conflict` называет колонку и вид `not_null_column_added`
