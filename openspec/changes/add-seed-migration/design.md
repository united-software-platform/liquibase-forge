# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/forge-seed-migration/spec.md` и дельте
`specs/forge-migration/spec.md`. Формат seed, нормализация значений и `forge validate-seed` —
изменение `add-seed-format`.

Что есть сейчас:

- **Построение changelog модели.** `forge generate` строит `Changelog` из разницы моделей
  (`migration/domain/model_diff.py`). `liquibase_changelog.py` отрисовывает его в YAML с явными
  `rollback` у changeset удаления. Идентичность changeset и проверку `drop_not_allowed` по беклогу
  операции делает `migration/application`.
- **Накат и откат.** `forge apply` накатывает любой changelog через шлюз и от его содержимого
  не зависит. `forge rollback` снимает `k` changeset командой `rollback-count`. Затем проверяет
  возврат по сводке `ChangelogSummary`: её строит `_summary()` из блоков `changes` и сейчас знает
  только изменения структуры.
- **Запасной путь.** Пересоздаёт БД и накатывает принятый `master.yaml`. Changelog данных,
  принятые в `master.yaml`, накатятся там тем же путём.

## Goals / Non-Goals

**Goals:**

- Changelog данных, который накатывается существующими `forge apply` и шлюзом без изменений.
- Явный и проверяемый откат данных.
- Отказ до наката для всего, что заведомо не исполнится.

**Non-Goals:**

- Сверка строк после наката — изменение `add-seed-reconciliation`.
- Шаблоны беклогов, принятие `seed.yaml` и согласование с операцией модели — изменение
  `add-seed-operation`.
- Изменение PK строки: смена PK — это удаление старой строки и вставка новой.

## Decisions

### Отдельная команда `forge generate-seed`, а не ключ `forge generate`

Входы, проверки и коды отказа у двух changelog разные. Отдельная команда — отдельный сценарий
использования (CLAR-007), и `forge generate` остаётся неизменным. Общие части переиспользуются:
идентичность changeset, чтение беклога операции, проверка `allow_drop`, запись и удаление файла
`--out`.

### Порядок «вставки → изменения → удаления» вместо Q11

В Q11 был порядок «удаления → изменения → вставки». На типовом сценарии он не работает: вывести
строку справочника и перевести ссылки зависимых строк на новую. Удаление старой строки раньше,
чем изменение ссылок, нарушает FK.

При новом порядке ссылки всегда целы:

- вставка ссылается только на строки итогового seed, а они уже есть или вставлены раньше
  в топологическом порядке;
- изменение ссылается на строки итогового seed, все они существуют после вставок;
- на удаляемые строки итоговый seed не ссылается (это проверено `forge validate-seed`), а прежние
  ссылки к моменту удаления сняты изменениями.

Цена — конфликты набора `unique`: новое значение может совпасть со значением строки, которая
изменится или удалится позже. Ни один линейный порядок не решает все случаи. Поэтому такие
изменения отклоняются кодом `1` с перечнем `unsupported`, а владелец разносит их по двум
операциям: сначала освободить значение, затем занять его.

Вторая цена — ключи-наборы. Внешний ключ может вести на набор `unique`, а не на PK. Тогда
изменение значения набора и перевод ссылок на него не выполнить ни в каком порядке: пока строки
ссылаются на прежнее значение, его нельзя изменить, а вставка со ссылкой на новое значение идёт
раньше изменений. Такие изменения отклоняются кодом `referenced_key_changed`, если прежнее
значение нужно ссылающейся строке принятого seed или новое занимает вставляемая или изменяемая
строка. Правило берёт перестраховкой и отказывает и в случаях, которые исполнились бы при удачном
порядке строк, зато оно простое и проверяется по двум seed без моделирования порядка. Ссылок
по PK правило не касается: смена PK — удаление и вставка.

Альтернатива — временные значения или отложенные ограничения — отклонена: формат не описывает
`DEFERRABLE`, а временные значения видны в журнале и усложняют откат.

### Топологический порядок строк и группировка в changeset

Строки сортируются по графу ссылок FK отдельно для вставок (от целевых строк) и удалений
(от зависимых). При равенстве решают порядок таблиц и строк в seed: для удалений — в принятом
seed, для вставок и изменений — в seed попытки. Соседние строки одной таблицы и вида
объединяются в changeset.

Группировка по строкам, а не по таблицам целиком, корректна и при цикле на уровне таблиц
без цикла строк (A → B → A): таблица тогда даёт несколько changeset.

### Одна строка — одно действие Liquibase с условием на PK

- `insert` — по действию на строку.
- `update` и `delete` — по действию на строку с `where` на все колонки PK.
- Изменение пишет только колонки с отличающимися значениями.

Так откат и проверка возврата адресуют строку тем же условием, что прямое действие.

### Типизированные литералы через `valueComputed`

Каждое значение пишется как `valueComputed: "'<текст>'::<тип PostgreSQL>"`:

- текст — нормализованная форма значения, кавычки удваиваются;
- NULL — `valueComputed: "NULL"`;
- тип PostgreSQL — по той же таблице отображения, что в changelog модели.

Условия `where` собираются из тех же литералов.

Почему не `value`/`valueNumeric`/`valueDate`: Liquibase сам переводит их в литерал, и для
`timestamptz` со смещением, `numeric` с точностью и `uuid` результат зависит от версии Liquibase.
Явный литерал с приведением однозначен. Интеграционный тест накатывает строку всех десяти типов
и читает её обратно.

### Проверка возврата строк из changelog попытки

`ChangelogSummary` получает перечни строк, собранные из действий данных:

- вставки — таблица и `where` PK;
- изменения — `where` PK и литералы прежних значений из `rollback`;
- удаления — `where` PK и литералы всех значений из `rollback`.

Проверки выполняются одним запросом на строку:
`SELECT count(*) FROM <таблица> WHERE <where PK> AND <колонка> IS NOT DISTINCT FROM <литерал> …`.
Ожидаемое число — `0` для `row_absent` и `1` для `row_present`/`row_restored`.

Модель и seed для проверки не нужны: всё берётся из changelog попытки, как и для структуры.
Changelog исполняется в той же БД целиком, так что его условия — не новый источник доверия.

## Risks / Trade-offs

- [Отказ `unsupported` заставляет делить изменение на две операции] → случаи редкие (обмен
  или повторное использование значений `unique`, изменение ключа-набора, на который ссылаются). Ответ называет строки и набор.
- [Строка с символом NUL проходит формат seed, но PostgreSQL её отвергает] → накат кончается
  ошибкой Liquibase, попытка неуспешна с диагностикой. Запрет NUL в формате — кандидат в правку
  формата.
- [Большой справочник даёт длинный changelog] → справочные данные малы по природе. Ограничений
  размера в v1 нет, это записывается в ограничения `docs/seed-migration.md`.
- [Строки рабочей БД, не принадлежащие seed, ломают вставку по PK] → допущение Q20: таблица,
  впервые попадающая в seed, пуста. Записывается в ограничения.
- [Откат через `rollback-count` для данных зависит от явных блоков] → блок есть у каждого
  changeset (требование), тест проверяет откат каждого вида на `lbfr-db-test`.

## Migration Plan

Миграции нет: команда новая, `forge rollback` лишь дополняется. Сводка changelog модели не
меняется, проверки строк для неё не появляются.
