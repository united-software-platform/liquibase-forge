# Design

## Context

Мотивация — в `proposal.md`, раздел Why.

- `BuildReportUseCase` уже знает путь беклога операции и пути беклогов начатых попыток
  (`backlogs` в `BuildReportOutput`), статус операции и принятые файлы. Поле `commit` отчёта
  собирает `report.py`: при `success` — три файла корня принятого состояния, иначе `null`.
- Артефакты попыток (`model.yaml`, `changelog.yaml`, `apply.json`, `reconcile.json`,
  `rollback.json`) лежат в `attempt-N/` внутри каталога операции, поэтому каталог операции
  покрывает их целиком.
- Каталог `.forge/` создают два независимых исполнителя: `RunnerLiquibaseGateway` в контейнере
  агента (файл запроса) и `tools/liquibase/gateway.py` на хосте (файл результата). Шлюз —
  самостоятельный скрипт на стандартной библиотеке, пакет `forge` он не импортирует.
- Шаблоны `forge-model` и `forge-apply` называют пути следа литералами `backlog/...`, а
  `trail_root()` читает `BACKLOG_ROOT`. Перенос корня следа поэтому ломает ссылки в беклогах.

## Goals / Non-Goals

**Goals:**

- Перечень файлов для коммита собирается в одном месте и одинаков для отчёта и навыка.
- Файлы обмена скрыты от git в любом проекте без правки его `.gitignore`.

**Non-Goals:**

- Коммит силами forge или навыка.
- Поддержка `BACKLOG_ROOT` для операций forge — фиксируется ограничением.
- Перечисление отдельных файлов внутри каталогов следа: каталог коммитится целиком.

## Decisions

### Перечень для коммита строит сценарий отчёта

`BuildReportOutput` получает поле `commit_files: tuple[str, ...] | None`. Сценарий заполняет его
только для статусов `success` и `failure`: при `success` — файлы корня принятого состояния, затем
каталог операции, затем каталоги беклогов попыток в порядке номеров; при `failure` — только
каталоги следа. Каталог — родитель пути беклога с завершающим `/`, путь берётся в том виде,
в котором записан в беклоге либо передан в `--operation`.

Альтернатива — собирать перечень в `report.py`. Отклонена: решение «закрыта ли операция» —
правило приложения, а не форма ответа CLI; навыку нужен тот же перечень, что и отчёту.

`report.py` отдаёт `commit: {"files": [...], "hint": ...}` при непустом перечне. Подсказка
различает исход: при `success` — принятое состояние и след, при `failure` — только след,
объясняющий, почему схема не изменилась.

### Навык берёт перечень из отчёта

Шаг 6 навыка возвращает LLM `commit.files` отчёта при любом закрытом статусе. Навык путей
не вычисляет — иначе перечень разошёлся бы с отчётом.

### `.forge/.gitignore` создаётся рядом с каждой записью обмена

Функция подготовки каталога создаёт `.forge/` и пишет `.gitignore` с комментарием и строкой `*`,
только если файла нет. Она вызывается перед записью файла запроса в `RunnerLiquibaseGateway`
и перед записью результата в `write_result` шлюза. В шлюзе функция своя, на стандартной
библиотеке: импорт пакета `forge` на хосте недоступен.

Альтернатива — дописывать `.forge/` в `.gitignore` проекта. Отклонена: перечень игнорируемых путей
принадлежит проекту, а правка чужого файла скрыла бы прежнее содержимое — тот же довод, по
которому плагин `formular` только печатает рекомендацию.

`.gitignore` со строкой `*` скрывает и сам себя: каталог не появляется в `git status` даже
служебным файлом.

### Ограничение корня следа — документацией, без кода

`BACKLOG_ROOT` для forge не поддерживается: шаблоны порождают пути `backlog/...`. Проверку
в коде (`forge status` отклоняет непустой `BACKLOG_ROOT`) не вводим: переменная принадлежит
плагину `formular` и может быть задана для других операций проекта.

## Risks / Trade-offs

- [Потребитель отчёта считал `commit is null` признаком неудачи] → признак исхода —
  `operation.status`; изменение названо в proposal как совместимостное.
- [Каталог следа содержит `apply.json` и `rollback.json` с выводом Liquibase и адресом тестовой БД] →
  учётные данные в файл запроса не передаются по требованию шлюза; что их нет и в результатах,
  проверяется задачей реализации до того, как README назовёт след безопасным для коммита.
- [В целевом проекте владелец уже добавил `backlog/*` по рекомендации плагина] → отчёт всё равно
  называет каталоги; README описывает, что строку нужно убрать, чтобы след коммитился.

## Migration Plan

Изменения обратно совместимы по входу: шаблоны и беклоги не меняются. Каталоги `.forge/` уже
существующих установок получают `.gitignore` при следующем запросе к шлюзу.
