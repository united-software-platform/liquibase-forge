# Design

## Context

Мотивация — в `proposal.md`. Все сведения для новых текстов уже есть в справочниках:

- поддерживаемые изменения модели и отказ `forge generate` с `non_additive` — `docs/migration.md`,
  раздел «Неподдерживаемые изменения»;
- состав модели, типы, наборы уникальности и FK — `docs/model-format.md`;
- статусы операции и закрытие — `docs/operation.md`;
- раскладка принятого состояния и `logicalFilePath` — `docs/operation.md`, «Принятое состояние»,
  и `docs/migration.md`, «Идентичность changeset».

Задача 2.4 шаблона `forge-apply.md` при отказе `non_additive` правит модель и возвращается к 2.3:
агент сам убирает неподдерживаемое изменение, и операция может закончиться успехом, не выполнив
намерение в части смены типа. Это поведение и объясняет кейс 9.

## Goals / Non-Goals

**Goals:**

- Каждое новое утверждение в README и кейсах опирается на справочник или на проверку на стенде.
- Тексты следуют норме документов проекта: роли и голос — DGN-001, DGN-009; каркас кейса —
  DGN-006; норма называется кодом, а не пересказом, — DGN-010.

**Non-Goals:**

- Менять поведение forge, в том числе добавлять команду отказа от операции.
- Писать руководство по Liquibase: кейс 10 показывает одну команду и условия, при которых она
  корректна.

## Decisions

### Возможности модели — одно предложение в шаге 4, а не перечень типов

Шаг 4 называет, что умеет модель, и ссылается на `docs/model-format.md`. Перечень типов уже есть
в справочнике, и копия в README разошлась бы с ним (DGN-011 по духу). Второй пример намерения
со ссылкой на таблицу показывает связи, сделанные в LBFR-015.

Альтернатива — отдельный кейс «Хочу связать таблицы». Отклонена: связь — часть основного пути
построения модели, а не задача за его пределами (DGN-001).

### Кейс 9 говорит, что делать вместо смены типа

Смена типа, NULL и первичного ключа не поддерживается. Кейс предлагает выразить её явно:
- удалить колонку и добавить новую — данные колонки теряются, в `auto` нужен `--allow-drop`;
- либо добавить колонку с другим именем и оставить прежнюю.

Кейс предупреждает: агент, получив отказ `non_additive`, правит модель сам, поэтому в итоговом
отчёте проверяю, что намерение выполнено, а не только статус `success`.

### Кейс 10 проверяется на стенде до записи

Команду наката принятого `master.yaml` своим Liquibase кейс приводит только после прогона
на стенде: образ `lbfr-liquibase`, новая БД на сервере `lbfr-db-test`, `--changelog-file`
относительно корня проекта. Прогон должен подтвердить, что:

- `include` с `relativeToChangelogFile` находит файлы операций;
- записи `databasechangelog` получают `filename` из `logicalFilePath`, то есть
  `db/changelog/<штамп>.yaml` при любом `FORGE_ACCEPTED_DIR`;
- повторный накат ничего не меняет.

Если прогон покажет другое поведение, кейс пишется по факту, а расхождение со справочником
выносится владельцу до правки.

Кейс называет условия: БД приложения управляется только этими changelog'ами, а удаления в них
теряют данные. Накат вне forge — ответственность владельца: гейты и перечень тестовых БД
к нему не применяются.

### Ограничение «нельзя бросить операцию» — в README, команда — отдельной задачей

Команда отказа меняет статусы операции, CLI и шаблоны — это новая возможность, а не правка
документа. В 0.2.0 она не входит: ограничение называется явно по DOC-020, а команда уходит
в задачу LBFR-022.

## Risks / Trade-offs

- [Кейс 10 читают как разрешение катить на production] → кейс называет накат своим Liquibase
  вне forge, условие «схемой управляют только эти changelog'и» и потерю данных при удалениях.
- [Ограничение про открытую операцию без обходного пути] → пункт называет единственный выход —
  довести операцию до закрытия — и ссылается на задачу LBFR-022, когда она будет создана.
- [Незакоммиченные правки LBFR-018 в тех же файлах] → по GIT-020 сначала коммит работы
  `prepare-release-0-2-0`, затем правки этого change.

## Migration Plan

Не требуется: правятся только документы.

После архивации этого change работа продолжается выпуском 0.2.0 по порядку из `tasks.md`
change `prepare-release-0-2-0`: PR `release/v0.2.0` → `main`, запуск `release` с разрядом
`minor`, проверка релиза и его текст.
