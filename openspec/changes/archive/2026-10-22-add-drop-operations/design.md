# Design

## Context

Мотивация — в proposal.md, требования — в дельтах спецификаций. Текущее устройство, от которого
отталкивается решение:

- `AdditiveDiff` (`migration/domain/additive_diff.py`) собирает все неаддитивные изменения,
  включая `table_removed` и `column_removed`, и бросает `NonAdditiveChangeError`; сценарий
  `GenerateChangelogUseCase` превращает его в ответ с кодом `1` и полем `non_additive`.
- `SchemaChange = CreateTable | AddColumn`; рендер `liquibase_changelog.py` не пишет блоков
  `rollback`: откат `createTable`/`addColumn` Liquibase выводит сам.
- `ChangelogSummary` перечисляет только добавляемые таблицы и колонки; на нём построены проверки
  возврата `table_absent`/`column_absent` в `RollbackAttemptUseCase`.
- Режим операции читают только `operation/infrastructure/frontmatter.py` и представление
  `views.py` контекста «Операция». `OperationRecordReader` контекста «Миграция» знает штамп,
  вердикты и каталоги попыток, но не режим.
- `forge report` читает результаты попытки через `AttemptResultsReaderInterface`
  (`reconcile.json`, `rollback.json`), changelog не читает.

## Goals / Non-Goals

**Goals:**

- Удаления — штатные изменения схемы, проходящие тот же цикл «накат → сверка → откат», что
  и добавления, с откатом Liquibase без запасного пути.
- Решение о допустимости удаления в `auto` принимает CLI, а не агент.

**Non-Goals:**

- Восстановление данных при откате; перенос данных при переименовании.
- Смена типа, NULL и первичного ключа — остаётся отказом `1`.
- Удаления с учётом внешних ключей: их ещё нет в модели, это LBFR-015.

## Decisions

### Diff: `ModelDiff` вместо `AdditiveDiff`

Доменный сервис переименовывается в `ModelDiff`, `NonAdditiveChange`/`NonAdditiveChangeError` —
в `UnsupportedChange`/`UnsupportedChangeError`. `SchemaChange` расширяется типами `DropTable(table:
Table)` и `DropColumn(table: TableName, column: Column, nullable: bool)`: они несут принятые
определения объекта, из которых рендер строит блок `rollback`. Удалённая колонка, входящая
в первичный ключ принятой таблицы, не даёт `DropColumn`: изменение PK уже даёт
`primary_key_changed`, и `column_removed` в этом случае не порождается.

Альтернатива — оставить имена и только убрать коды: отвергнута, потому что `AdditiveDiff`,
выдающий удаления, вводит читателя в заблуждение (DDD-001). JSON-поле `non_additive` ответа
команды не переименовывается — это контракт, и смена имени ничего не даёт пользователю.

### Порядок и нумерация

`ModelDiff.between` возвращает сначала `DropTable` в порядке принятой модели, затем `DropColumn`
по таблицам и колонкам принятой модели, затем добавления в прежнем порядке. `Changelog` нумерует
`id` по порядку, поэтому нумерация сквозная без изменений в `Changelog`. Удаления раньше
добавлений, чтобы освобождённые имена и будущие FK (LBFR-015) не зависели от порядка внутри
таблицы; Liquibase откатывает changeset в обратном порядке, то есть сначала снимает добавления,
затем восстанавливает удалённое.

### Явный блок `rollback`

`dropTable` рендерится с `rollback: [createTable, addPrimaryKey]` — теми же структурами, что
и создание таблицы, по принятому определению. `dropColumn` — с `rollback: [addColumn]`.
Общий код построения `createTable`/`addColumn` переиспользуется рендером. Альтернатива —
не писать откат и уходить на запасной путь пересоздания БД — отвергнута: запасной путь
удаляет всю тестовую БД ради одного changeset и делает штатный исход аварийным.

### Согласие на удаления: проверка в `forge generate`

`OperationRecord` получает поля `mode` и `allow_drop`; `OperationRecordReader` читает их
из фронтматтера, отсутствие `allow_drop` даёт `False`. После построения diff сценарий проверяет:
`mode == "auto"`, `allow_drop` ложно, а среди изменений есть удаления → исключение
`DropNotAllowedError` с перечнем удаляемых объектов, прежний `--out` удаляется. Команда
превращает его в `environment_error("drop_not_allowed", …)` с кодом `2`: по правилу шаблонов
код `2` останавливает операцию `forge stop` и не расходует попытку.

Альтернативы:

- гейт 3.1 агента по ответу `generate` — отвергнута: развилку решает CLI (`docs/architecture.md`,
  «Принцип разделения»);
- код `1` — отвергнута: шаблон предписывает при отказе `generate` править модель, и агент
  вернул бы удалённый объект в модель вопреки намерению.

Проверка идёт после проверки модели и неподдерживаемых изменений: если модель некорректна,
агенту нужен перечень нарушений, а не остановка операции.

Сообщение отказа называет, как продолжить с согласием: `/forge --mode auto --allow-drop`. Оно
попадает в `stop_reason` и в диагностику, которую навык возвращает LLM.

### Согласие при продолжении

Отказ `drop_not_allowed` останавливает операцию, а остановленную операцию без подтверждённой
попытки `forge close` не закрывает. Поэтому согласие должно даваться той же операции, иначе
выхода нет. `forge resume --operation <беклог> --allow-drop` для остановленной операции в `auto`
переводит её в `running` и пишет `allow_drop: true` в беклог операции и в беклоги попыток
из `backlog.attempt_N`; строка заменяется или, в беклоге прежнего шаблона, вставляется после
`mode`. Остальной текст беклогов не меняется. Согласие только даётся: ключа для `false` нет.

Решение принимает доменная операция `Operation.grant_drop()`: допустимо только в статусе
`stopped` и режиме `auto`, повтор ничего не меняет. Запись строк — в
`FrontmatterOperationWriteRepository`, рядом с записью `status` и `stop_reason`.

Навык при открытой остановленной операции в `auto` и ключе `--allow-drop` вызывает
`forge resume --allow-drop` вместо простого `forge resume`. Для операции `running` ключ
не принимается: её попытка исполняется, и менять условия посреди неё нельзя. Для операции
`interactive` ключ не нужен — удаления там разрешены, — навык сообщает об этом и продолжает.

Шаблон `forge-model` 1.2.0 в задачах порождения попыток выбирает `--flag allow-drop` или
`--no-flag allow-drop` по значению `allow_drop` во фронтматтере беклога операции, а не вшивает
флаг при порождении: иначе попытки после согласия получили бы `allow_drop: false`. Агент читает
значение, а не решает развилку, — это совместимо с принципом разделения. Шаблон ещё не выпущен,
поэтому правка остаётся в версии 1.2.0.

Альтернативы:

- закрыть операцию и начать новую с ключом — отвергнута: остановленную операцию без подтверждённой
  попытки `forge close` не закрывает, а принудительное закрытие ломает правило исходов закрытия;
- не останавливать операцию на `drop_not_allowed` — отвергнута: код `2` по правилу шаблонов
  останавливает операцию, а код `1` заставил бы агента вернуть удалённый объект в модель;
- разрешить ключ и для `running` — отвергнута: согласие менялось бы посреди исполняемой попытки.

### Признак в шаблонах и навыке

`forge-model` 1.2.0 принимает флаг `allow-drop` и пишет `allow_drop: true|false` во фронтматтер;
задачи порождения попыток передают `--flag allow-drop`/`--no-flag allow-drop`. `forge-apply`
1.3.0 пишет тот же признак в свой фронтматтер. Стоп-знак 3.1 предписывает показать перечень
удалений из ответа `forge generate` (виды `drop_table`, `drop_column`) с предупреждением о потере
данных; условие гейта 3.1 больше не говорит «только добавляющие изменения». Навык проверяет
сочетание `--allow-drop` и `--mode auto` до `backlog generate`; при открытой операции ключ
действует по решению «Согласие при продолжении».

### Проверка возврата

`ChangelogSummary` получает `dropped_tables` и `dropped_columns`; читатель распознаёт
`dropTable` и `dropColumn`. `RollbackAttemptUseCase._verify` добавляет `table_present`
и `column_present` через существующий `SchemaProbeInterface`. На запасном пути проверки те же:
принятый `master.yaml` восстанавливает удалённое, так как оно есть в принятом состоянии.

### `allow_drop` и `destructive` в контексте «Операция»

Доменная `Operation` получает `allow_drop`, `frontmatter.py` читает его с умолчанием `False`,
`views.py` выдаёт рядом с `mode` в `forge status` и `forge report`. Перечень `destructive`
строит отчёт: `AttemptResultsReaderInterface` получает операцию `destructive(changelog: str) ->
tuple[DestructiveChange, ...]`, реализация в `attempt_results.py` читает YAML changelog и выбирает
`dropTable`/`dropColumn`. Контекст «Операция» не импортирует читатель миграции (CLAR-023):
формат changelog знает его собственная инфраструктура. Нет файла — пустой перечень.

## Risks / Trade-offs

- [Удаление теряет данные тестовой БД, откат возвращает только структуру] → предупреждение
  на стоп-знаке, согласие в `auto` и перечень `destructive` в отчёте.
- [Удаление в принятом changelog навсегда остаётся в `master.yaml`; при переносе в рабочую БД
  оно удалит данные] → `destructive` в отчёте делает удаления видимыми при ревью коммита;
  ограничение «только тестовая БД» в документах сохраняется.
- [Двойное знание формата changelog: рендер миграции и читатель отчёта] → читатель отчёта
  распознаёт только две формы `dropTable`/`dropColumn`, тест сверяет его с выводом рендера.
- [Восстановленная колонка оказывается в конце таблицы] → порядок колонок не сравнивается
  ни сверкой, ни diff, на модель это не влияет.
- [Беклоги прежних шаблонов в `auto` не смогут удалять без согласия] → согласие даётся
  при продолжении: `forge resume --allow-drop` вставляет строку `allow_drop: true` после `mode`.
- [Согласие, данное посреди операции, расходится с уже порождёнными беклогами попыток] →
  `forge resume --allow-drop` пишет его во все порождённые беклоги, а следующие попытки
  порождаются по значению фронтматтера беклога операции.

## Migration Plan

Миграции данных нет. Открытые операции на прежних шаблонах продолжают исполняться: отсутствие
`allow_drop` читается как `false`, остальное поведение не меняется. Откат изменения — возврат
кода и шаблонов; принятые changelog с удалениями остаются корректными changelog Liquibase.
