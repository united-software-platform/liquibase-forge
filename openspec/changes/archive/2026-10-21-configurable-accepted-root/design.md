# Design

## Context

Мотивация — в `proposal.md`, раздел Why. Корень принятого состояния сейчас зашит в четырёх местах:

- `ACCEPTED_ROOT = Path("db")` в `src/forge/cli/commands/close.py`, его импортирует `report.py`;
- умолчание `root: Path = Path("db")` у `FileAcceptedState`;
- `ACCEPTED_MASTER = "db/changelog/master.yaml"` в сценарии отката — запасной путь накатывает
  принятый `master.yaml` после пересоздания БД;
- литерал `--accepted db/model.yaml` в задаче 2.4 шаблона `templates/forge-apply.md`.

`logicalFilePath` changeset строит доменный штамп (`src/forge/migration/domain/stamp.py`)
как `db/changelog/<штамп>.yaml`, и этот путь уже записан в журнале `databasechangelog`.

Шлюз Liquibase принимает changelog только относительным путём внутри корня проекта
(`resolve_changelog` в `tools/liquibase/gateway.py`): абсолютный путь и выход за корень
он отклоняет. Каталог `.forge/` уже игнорируется git и служит обменом со шлюзом; шлюз его
не чистит.

Настройки окружения читает `EnvironmentSettings` (`src/forge/shared/infrastructure/settings.py`)
из `os.environ`, ошибки настроек — `SettingsUnavailableError`, которую CLI переводит в код `2`.

## Goals / Non-Goals

**Goals:**

- Один источник корня принятого состояния для всех команд, читающих или пишущих его.
- Поведение без переменной совпадает с нынешним — целевые проекты не замечают изменения.
- Неверное значение обнаруживается до записи, а не после.

**Non-Goals:**

- Механизм поставки forge в целевой проект.
- Перенос уже принятых файлов при смене значения переменной: смена корня в работающем проекте —
  ручное действие владельца.
- Ключ командной строки для корня у `close`, `report`, `rollback`: корень — свойство окружения
  проекта, а не отдельного вызова.

## Decisions

### Корень читается из настроек окружения, а не передаётся каждой команде

`EnvironmentSettings` получает метод `accepted_root()`: читает `FORGE_ACCEPTED_DIR`, при пустом
или незаданном значении возвращает `Path("db")`, иначе проверяет значение и возвращает
нормализованный относительный путь. Абсолютный путь или путь, выходящий за корень проекта после
нормализации, — `SettingsUnavailableError` с именем переменной.

Альтернатива — ключ `--accepted-root` у каждой команды. Отклонена: путь пришлось бы повторять
в шаблонах беклогов, то есть вернуть литерал, ради удаления которого change и затеян.

Проверка «внутри проекта» совпадает с правилом шлюза: корень, который шлюз отклонил бы на запасном
пути отката, отклоняется ещё при `forge status`.

### Литералы корня удаляются, умолчания конструкторов исчезают

`FileAcceptedState` получает корень обязательным аргументом, `ACCEPTED_ROOT` и `ACCEPTED_MASTER`
удаляются. `close`, `report` и `rollback` строят пути от `settings.accepted_root()` при сборке
сценария. Так в коде не остаётся второго места, где корень мог бы разойтись с настройкой.

Сценарий отката продолжает принимать путь `master.yaml` аргументом — меняется только источник
значения в `build_use_case`.

### `--accepted` у `generate` остаётся, но становится необязательным

Явный `--accepted` сохраняет тестам и ручным вызовам возможность указать произвольную модель.
Без него CLI берёт `<корень>/model.yaml`. Шаблон `forge-apply` ключ больше не передаёт и получает
новую версию `1.2.0`; порождённые ранее беклоги с литералом остаются исполнимыми, потому что ключ
по-прежнему принимается.

### `logicalFilePath` не зависит от физического корня

Доменный штамп по-прежнему строит `db/changelog/<штамп>.yaml`. Альтернатива — производить логический
путь от корня — отклонена: журнал `databasechangelog` в разработке и в поставке разошёлся бы,
а смена корня в работающем проекте сделала бы уже накатанные changeset «чужими» для Liquibase.

`include` в `master.yaml` уже задан с `relativeToChangelogFile: true`, поэтому физическое
расположение файлов на накат не влияет, а идентичность changeset определяет `logicalFilePath`.

### Проверка `accepted` в `forge status`

`EnvironmentProbe` добавляет четвёртую проверку `accepted`: `passed: true` и `detail` с итоговым
путём при корректном значении, `passed: false` и текст ошибки настройки при некорректном.
Существование каталога не проверяется: до первого `forge close` корня нет, и это нормальное
состояние.

Уточнение решения «всегда passed»: проверка всегда пройдена для корректного значения, а
некорректное — ошибка окружения наравне с другими проверками, иначе `status` пропустил бы
конфигурацию, на которой `close` упадёт.

### Страховка `.gitignore` и значение для репозитория разработки

`/db/` в `.gitignore` с якорем `/` исключает только каталог корня проекта, а не любые `db/`
в дереве. В `.env` репозитория разработки владелец задаёт `FORGE_ACCEPTED_DIR=.forge/db`:
`.env` не коммитится, поэтому правку `.env` change фиксирует в README и задачах, а не в коде.

## Risks / Trade-offs

- [Владелец меняет `FORGE_ACCEPTED_DIR` в проекте с уже принятым состоянием — новые операции
  начинаются с пустой принятой модели и строят changelog создания существующих таблиц] →
  `forge status` называет итоговый корень; README описывает смену корня как перенос каталога
  вручную.
- [`.forge/db` в разработке накапливает принятые операции, а тестовая БД — их таблицы] →
  ожидаемо для проверочной среды; чистка — удаление `.forge/db` и пересоздание тестовой БД.
- [`.gitignore` репозитория попадёт в будущую поставку и скроет `db/` в целевом проекте] →
  ограничение зафиксировано в README и `docs/architecture.md`; механизм поставки должен его учесть.
- [Порождённые до change беклоги попыток передают `--accepted db/model.yaml` при корне `.forge/db`] →
  в репозитории разработки открытых операций нет; в целевом проекте корень по умолчанию `db`,
  и литерал совпадает с ним.

## Migration Plan

1. Реализация и тесты; при незаданной переменной поведение прежнее.
2. В `.env` репозитория разработки — `FORGE_ACCEPTED_DIR=.forge/db` (`make forge-env-sync`
   допишет `db`, значение владелец меняет вручную).
3. Откат change — возврат кода; файлы в `.forge/db` при этом не используются и удаляются вручную.
