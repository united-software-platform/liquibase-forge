# Design

## Context

- Агент работает в контейнере `claude` из образа kit'а: там есть Python 3.12 и `uv`, но нет
  `docker`, `make`, JRE и Liquibase. Docker-сокета у агента нет намеренно.
- На хосте работает раннер `tools/host-runner/runner.py`: по HTTP он выполняет одну цель `make`
  из белого списка, без параметров. `make` при ошибке рецепта возвращает `2` независимо от кода
  команды, а клиент `call.sh` сводит любой ненулевой исход к `1`.
- `docker-compose.yml`, `Makefile`, `.env.example` и `runner.py` — файлы поставки kit'а
  с контрольными суммами в `.sdd-kit-manifest.json`. Сервис `claude` получает `.env` через
  `env_file` и подключён к сети `default`.
- Мотивация — в [proposal.md](./proposal.md), контракт шлюза — в
  [specs/forge-liquibase-gateway/spec.md](./specs/forge-liquibase-gateway/spec.md).

## Goals / Non-Goals

**Goals:**

- Агент из своего контейнера запускает тесты, подключается к обеим БД и исполняет накат и откат
  Liquibase через раннер.
- Правки файлов kit'а минимальны и перечислены в README.

**Non-Goals:**

- Клиент шлюза на стороне `forge` (запись запроса, вызов раннера, разбор результата) — change
  `forge-migration`. Здесь шлюз проверяется своими тестами и ручным прогоном через раннер.
- Пайплайн CI.
- Поддержка в kit'е дополнительного белого списка из `.env` (`AGENT_RUNNER_EXTRA_TARGETS`) —
  отдельная задача в репозитории kit'а.

## Decisions

### Каркас пакета по контекстам

`src/forge/<контекст>/{domain,application,infrastructure}` для `modeling`, `migration`,
`reconciliation`, `operation` и общий `src/forge/cli/` (CLAR-022). Точка входа
`[project.scripts] forge = "forge.cli.main:main"`. В этом change CLI знает только общий
JSON-контракт: без команды или с неизвестной командой печатает в stdout один JSON-объект
с ошибкой и возвращает `2`. Предметные команды добавляют следующие change.

Зависимости: `PyYAML`, `psycopg[binary]` 3. Для разработки: `pytest`, `ruff`, `mypy`. В `mypy`
включён `strict`, в `ruff` — lint и format. Альтернатива `click`/`typer` отклонена: контракт
сводится к JSON в stdout, лишняя зависимость не окупается.

### Compose инструмента подключается из файла kit'а

Окружение kit'а и инструмент lbfr описаны разными файлами Compose. Файл kit'а
`docker-compose.yml` описывает сервис агента `claude`, файл инструмента
`docker/lbfr/docker-compose.yaml` — сервисы lbfr. Файл kit'а подключает файл инструмента
секцией `include:` в длинной форме:

```yaml
include:
  - path: docker/lbfr/docker-compose.yaml
    project_directory: .
```

`project_directory: .` — корень проекта: относительные пути файла инструмента (контекст сборки,
монтирование проекта) и подстановки из `.env` отсчитываются от корня. Файл инструмента содержит:

| Сервис | Образ | Назначение | Особенности |
|--------|-------|------------|-------------|
| `lbfr-db` | `${LBFR_POSTGRES_IMAGE}` | Целевая БД операций | Том `lbfr-db-data`, `healthcheck`, `restart: unless-stopped` |
| `lbfr-db-test` | `${LBFR_POSTGRES_IMAGE}` | БД интеграционных тестов | Данные в `tmpfs`, `healthcheck`, `restart: unless-stopped` |
| `lbfr-liquibase` | `${LBFR_LIQUIBASE_IMAGE}`, собирается из `docker/liquibase/Dockerfile` | Одноразовый запуск Liquibase | Профиль `tools`, `restart: "no"`, проект смонтирован только на чтение в `/liquibase/changelog` |

Порты на хост не публикуются (DOCK-008): агент и Liquibase обращаются к БД по сети Compose.
`environment` берётся из `.env` (DOCK-009). Альтернатива — переименовать файл kit'а — отклонена
в Q13: она ломает отслеживание манифестом.

### Отступления от DOCK-011

DOCK-011 требует, чтобы файл Compose назывался строго `docker-compose.yaml` и лежал в корне
проекта. Обоим требованиям не отвечает ни один из двух файлов:

| Файл | Имя | Расположение | Причина отступления |
|------|-----|--------------|---------------------|
| `docker-compose.yml` (kit) | Нарушает: краткая форма `.yml` прямо запрещена | Соответствует | Имя задано поставкой kit'а; переименование отклонено в Q13, потому что ломает отслеживание файла `.sdd-kit-manifest.json` |
| `docker/lbfr/docker-compose.yaml` (lbfr) | Соответствует | Нарушает: подкаталог | В корне уже лежит файл kit'а, а два файла из перечня автопоиска Compose дают предупреждение при каждом вызове, и выбор файла зависит от порядка имён |

Оба отступления осознанные. Правилу целиком отвечает единственный `docker-compose.yaml` в корне,
но для этого нужно переименовать файл kit'а — в проекте или в самой поставке. Это решение
за пределами change.

Альтернатива — два независимых проекта Compose без `include:` — отклонена: агенту нужна общая
с БД сеть, а это либо правка сетей сервиса `claude` в файле kit'а, либо внешняя сеть kit'а
по имени, зависящему от каталога проекта.

Данные `lbfr-db-test` живут в `tmpfs`: каждый тест всё равно создаёт свою БД, и пересоздание
контейнера даёт чистый сервер без отдельной цели очистки.

### Две сети у БД

`lbfr-db` и `lbfr-db-test` подключены к `lbfr-net` (DOCK-003) и к `default`, а `lbfr-liquibase` —
только к `lbfr-net`. Сервис `claude` объявлен в файле kit'а, и подключаемый файл не может
переопределить его сети. Поэтому БД сами выходят в сеть `default`, общую для проекта Compose.

### Шлюз — stdlib-скрипт Python на хосте

`tools/liquibase/gateway.py <действие>` вызывается рецептами `make liquibase-update`
и `make liquibase-rollback`. Скрипт:

1. Удаляет прежний `.forge/liquibase-result.json`.
1. Читает `.forge/liquibase-request.json` и проверяет состав, путь changelog, совпадение действия
   с аргументом и перечень `FORGE_TEST_DB_ALLOWLIST`.
1. Выбирает учётные данные по хосту запроса: `FORGE_DB_HOST` даёт `FORGE_DB_USER`
   и `FORGE_DB_PASSWORD`, `FORGE_TEST_DB_HOST` — `FORGE_TEST_DB_*`. Хост, не совпавший ни с одним
   из них, даёт отказ `2`. Окружение скрипту готовит рецепт цели: он загружает `.env`
   (`set -a && . ./.env`), поэтому правка `.env` действует без перезапуска раннера.
1. Запускает `docker compose run --rm -T` сервиса `lbfr-liquibase`. Адрес JDBC и учётные данные
   передаются переменными `LIQUIBASE_COMMAND_*` через `-e`, changelog — путём относительно корня
   проекта. Корень смонтирован в `/liquibase/changelog`, штатную точку образа: для неё точка входа
   образа сама переходит в этот каталог и ставит `--search-path=.`.
1. Пишет результат: `request_id`, `action`, `exit_code`, `stdout`, `stderr`.

Скрипт на Python, а не на shell: JSON без `jq` не разобрать, а чистые функции проверки
тестируются `pytest` в контейнере агента без хоста. Нужен только `python3` хоста, который уже
требуется раннеру. Логика живёт в скрипте, а не в рецепте, чтобы цели укладывались в MAKE-001.

### Истинный код исхода — в файле результата

Скрипт завершается с кодом исхода, но `make` и `call.sh` его искажают: `make` превращает любую
ошибку в `2`, `call.sh` — в `1`. Поэтому потребитель шлюза опирается только на файл результата
с совпавшим `request_id`. Нет файла или чужой `request_id` — ошибка окружения.

### Белый список раннера

В `ALLOWED_TARGETS` добавляются `liquibase-update` и `liquibase-rollback`, комментарий
константы дополняется основанием. Цели не ждут терминала и завершаются сами, поэтому
однопоточному раннеру они не мешают.

### Подготовка окружения целями make

Хостовые шаги подготовки — тоже цели `make` из белого списка раннера. Их логика вынесена
в скрипты `tools/forge-env/` (MAKE-002), и повторный запуск каждой цели безопасен:

| Цель | Скрипт | Действие |
|------|--------|----------|
| `forge-env-sync` | `sync-env.sh` | Дописывает в `.env` недостающие `FORGE_*` и `LBFR_*` из `.env.example`, заданные значения не трогает |
| `forge-env-check` | `check.sh` | Проверяет Compose 2.20+ и наличие четырёх сервисов в `config --services` при обоих профилях |
| `forge-env-up` | `up.sh` | `pull` образа БД, сборка `lbfr-liquibase`, `up -d --wait` обеих БД, `lbfr-liquibase --version` |

Вручную на хосте остаётся только запуск раннера. Пока его нет, агенту на хосте ничего
не доступно. Альтернатива — набор команд в README для ручного выполнения — отклонена:
каждый шаг тогда требует участия пользователя, а вывод нужно пересылать агенту.

### Тестовая БД на тест

Фикстура `pytest` в `tests/conftest.py` подключается к `lbfr-db-test` по `FORGE_TEST_DB_*`,
создаёт БД `t_<uuid>` и удаляет её после теста (`DROP DATABASE … WITH (FORCE)`). Тесты с БД
помечены маркером `integration`. Если `FORGE_TEST_DB_HOST` не задан, они пропускаются
с явной причиной. Если задан, но сервер недоступен, тест падает: недоступная среда не должна
выглядеть зелёным прогоном.

### Версии образов

`LBFR_POSTGRES_IMAGE=postgres:17.11` — последний патч PostgreSQL 17 на момент реализации.

Liquibase — последний стабильный выпуск `5.0.4`. Начиная с 5.0 официальный образ не содержит
драйверов БД, поэтому `lbfr-liquibase` собирается из собственного `docker/liquibase/Dockerfile`:

```dockerfile
ARG LIQUIBASE_BASE_IMAGE
FROM ${LIQUIBASE_BASE_IMAGE}
ARG POSTGRESQL_DRIVER_VERSION
RUN lpm update && lpm add "postgresql@${POSTGRESQL_DRIVER_VERSION}" --global
```

Версии задают переменные `.env`:

| Переменная | Значение | Назначение |
|------------|----------|------------|
| `LBFR_LIQUIBASE_BASE_IMAGE` | `liquibase/liquibase:5.0.4` | Базовый образ, аргумент сборки |
| `LBFR_LIQUIBASE_POSTGRESQL_DRIVER` | `42.7.13` | Версия JDBC-драйвера для `lpm`, аргумент сборки |
| `LBFR_LIQUIBASE_IMAGE` | `lbfr-liquibase:5.0.4-pg42.7.13` | Имя собранного образа |

Имя образа включает обе версии: после смены версии в `.env` Compose не найдёт образ с новым
именем и соберёт его заново, а не запустит старый. `lpm update` обновляет перечень пакетов
перед установкой, чтобы закреплённая версия драйвера была известна `lpm`. Образ работает
от пользователя `liquibase` базового образа, не от `root` (DOCK-012).

Отклонённые варианты:

- Liquibase `4.33.0`, последний выпуск 4.x с драйвером в образе. Сборки нет, но ветка 4.x больше
  не развивается, и переход на 5.x всё равно предстоит.
- Образ `5.0.4` с драйвером, смонтированным в `/liquibase/lib`. Сборки нет, но JDBC-архив
  приходится хранить или загружать отдельно, вне Compose.

## Risks / Trade-offs

- [`include:` не подключил файл инструмента или пути в нём разрешились не от корня] →
  `make forge-env-check` проверяет `docker compose config --services`: в выводе должны быть
  `claude`, `lbfr-db`, `lbfr-db-test`, `lbfr-liquibase`.
- [Для `include:` нужен Docker Compose 2.20 или новее] → Требование указывается в README,
  версия проверяется той же задачей.
- [Переустановка kit'а даёт конфликт по sha256 в четырёх файлах] → README перечисляет
  каждое отличие от поставки и его основание.
- [`env_file` kit'а передаёт агенту и пароли БД] → БД только тестовые, пароли не секретны
  за пределами машины. `.env` не коммитится.
- [Первый запуск загружает и собирает образ Liquibase дольше обычного] → Предел раннера 900 с
  этого хватает. README предписывает заранее выполнить `docker compose pull` и
  `docker compose --profile tools build lbfr-liquibase`.
- [Сборка образа обращается к сети: `lpm` загружает драйвер] → Сборка выполняется один раз
  на хосте. Если закреплённой версии драйвера нет в перечне `lpm`, сборка падает с явной
  ошибкой, и версия в `.env` меняется на доступную из `lpm search postgresql`.
- [Liquibase 5.x распространяется под лицензией FSL, а не Apache 2.0] → FSL ограничивает только
  конкурирующее коммерческое использование. Forge — внутренний инструмент проекта, ограничение
  его не касается.
- [Сессия агента читает `.env` только при старте] → README предписывает перезапускать сессию
  после правки `.env`. Цели шлюза загружают `.env` сами, а раннер перезапускается только после
  смены `AGENT_RUNNER_*` или белого списка.

## Migration Plan

1. Перезапустить раннер на хосте: в белом списке появились новые цели.
1. Через раннер выполнить `make forge-env-sync`, `make forge-env-check` и `make forge-env-up`.
   Поднимутся `lbfr-db` и `lbfr-db-test`. Сервисы `claude` и `lbfr-liquibase` стоят
   под профилями и не стартуют.
1. Перезапустить сессию агента, чтобы в её окружении появились `FORGE_*`.

Откат — удалить `include:` из `docker-compose.yml` и выполнить `docker compose down -v` для
проектных сервисов. Принятого состояния у change нет.
