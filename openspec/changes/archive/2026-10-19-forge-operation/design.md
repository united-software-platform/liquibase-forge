# Design

## Context

Мотивация — в proposal.md. Требования:

- `specs/forge-operation-commands/spec.md` — новые команды;
- `specs/forge-operation/spec.md` — изменения в потоке операции.

Исходное состояние:

- **Команды шагов попытки.** `forge validate`, `generate`, `apply`, `reconcile`, `rollback`
  работают и проверены на `lbfr-db-test`.
- **Общее ядро `forge.shared`.** Даёт адрес и перечень тестовых БД, настройки `FORGE_DB_*`,
  подключение к PostgreSQL и запись JSON.
- **Раннер пока в Миграции.** `RunnerSettings`, `call_runner` и `runner_settings` лежат
  в `migration/infrastructure`.
- **Шаблоны `templates/forge-model.md` и `templates/forge-apply.md` версии 1.0.0.**
  - Принимаются `backlog check-template` плагина `backlog@formular` 1.3.0.
  - Статус `stopped` агент пишет во фронтматтер руками.
  - Блока `trail` нет.
  - `forge generate` вызывается без `--operation`, хотя тот обязателен с change 2.
- **Порождение беклога.** Плагин вырезает заголовочный комментарий шаблона, так что беклог
  начинается с `---` фронтматтера. Носитель порядка — навык `/backlog:backlog-run`,
  его путь в беклоге — значение `runner`.
- **Исполняемый файл `backlog`** лежит в `bin/` плагина. В `PATH` он появляется в сессии,
  начатой после установки плагина.
- **Каталоги.** `backlog/*` уже в `.gitignore`. Каталога `db/` ещё нет.

## Goals / Non-Goals

**Goals:**

- Статус операции меняет только CLI. Агент не правит фронтматтер руками, кроме значений,
  которые задачи шаблона прямо предписывают записать: подтверждения, решения гейтов, вердикты,
  пути беклогов попыток.
- Закрытие детерминированно решает исход по фронтматтеру и результатам отката, а принятие
  в `db/` повторяемо.
- Навык — единственная точка входа LLM, и одновременно открыта не больше одной операции.

**Non-Goals:**

- Коммит `db/` — его делает владелец (Q44).
- Параллельные операции и выбор между ними.
- Упаковка Liquibase Forge в плагин (Q11).
- Отмена закрытой операции и откат принятого состояния.

## Decisions

### Агрегат операции и CQRS

| Слой | Компонент | Роль |
|------|-----------|------|
| Домен | `OperationStatus` | `running`, `stopped`, `success`, `failure` |
| Домен | `Attempt` | Объект-значение: номер, вердикт, путь беклога попытки, каталог попытки |
| Домен | `Operation` | Корень агрегата: путь беклога, штамп, намерение, режим, статус, причина остановки, три попытки. Операции `stop(reason)`, `resume()`, `close(rollbacks)`; свойства `confirmed_attempt` и `used_attempts` |
| Домен | `CloseOutcome` | Исход закрытия: принятая попытка либо `failure` |
| Домен | `OperationWriteRepositoryInterface` | Контракт записи (CQRS-001): `save(operation)` |
| Домен | `OperationFactory` | Восстанавливает агрегат из модели чтения (DDD-023) |
| Приложение | `OperationReadRepositoryInterface`, `OperationRecord` | Контракт и модель чтения (CQRS-003): запись по пути беклога, перечень открытых операций следа |
| Приложение | сценарии `GetStatus`, `StopOperation`, `ResumeOperation`, `CloseOperation`, `BuildReport` | Пять команд; сценарии-команды читают через контракт чтения, а пишут через контракт записи (CQRS-005) |
| Приложение | `EnvironmentProbeInterface`, `AcceptedStateInterface`, `AttemptResultsReaderInterface` | Проверка среды, принятие в `db/`, чтение `reconcile.json` и `rollback.json` |
| Инфраструктура | `FrontmatterOperationReadRepository`, `FrontmatterOperationWriteRepository`, `EnvironmentProbe`, `FileAcceptedState`, `JsonAttemptResultsReader` | Реализации |

Правила агрегата:

- **`stop`.** Допустим из `running` и `stopped`; повторная остановка заменяет причину.
- **`resume`.** Допустим только из `stopped`.
- **`close`.**
  - Есть подтверждённая попытка — исход `success` с её номером.
  - Все три попытки `failure`, и откат каждой подтверждён — исход `failure`.
  - Иначе `OperationNotClosableError` с причиной.
  - Закрывать можно только из `running`.
- **Закрытая операция.** `stop` и `resume` бросают `OperationClosedError`. Повторный `close`
  закрытой операции — не ошибка: команда сообщает прежний исход.

### Фронтматтер: чтение целиком, запись построчно

- **Чтение.** Модель чтения берёт YAML между первыми двумя строками `---`.
- **Запись.** Контракт записи меняет только строки верхнего уровня `status:` и `stop_reason:`
  внутри фронтматтера.
  - Значение пишется как скаляр JSON, то есть допустимая строка YAML в двойных кавычках
    либо `null`.
  - Нет `stop_reason` (беклог по шаблону 1.0.0) — строка вставляется сразу после `status:`.
  - Остальной текст беклога остаётся побайтово прежним: отметки задач, значения, дописанные
    агентом, порядок ключей.

Альтернатива — перезаписать фронтматтер через `yaml.safe_dump`. Отклонена: дамп меняет кавычки,
порядок и переносы значений, которые записал плагин, и тогда `backlog lint` и чтение диффа
беклога владельцем перестают совпадать с порождённым.

### Шаблоны версии 1.1.0

`forge-model.md`:

- **Фронтматтер.**
  - Блок `trail` с `attempt_1..3: backlog/forge-model/{{subject}}/attempt-N` заполняется
    при порождении (Q35).
  - Поле `stop_reason: null`.
- **Преамбула.**
  - Отказ владельца, непройденный гейт и код `2` любой команды `forge` ведут к
    `forge stop --operation backlog/forge-model/{{subject}}/tasks.md --reason <причина>`
    и остановке исполнения (Q46).
  - Ручная запись `status: stopped` из шаблона уходит.
- **Задача 1.3.** Без изменений: `forge status --operation …` проверяет среду.

`forge-apply.md`:

- **Задача 2.4.** `forge generate … --operation {{parent}} --out …` (Q39).
- **Преамбула.** Та же фраза про код `2`, с `--operation {{parent}}`. Отказ на стоп-знаке
  тоже ведёт к `forge stop`.

Версия шаблона живёт в его первой строке (BKL-004): у обоих шаблонов она становится `1.1.0`.
Приёмка — `backlog check-template` для каждого по всем сочетаниям признаков (BKL-009).

### Миграция читает каталог попытки из `trail`

`FrontmatterOperationRecordReader` берёт `trail.attempt_N`, если блок есть. Иначе каталог
выводится по раскладке, как сейчас: так беклоги по шаблону 1.0.0 читаются и дальше. Контракт
`OperationRecordReaderInterface` не меняется.

### Раннер в общем ядре

`RunnerSettings`, `call_runner` и `runner_settings` переезжают в
`forge/shared/infrastructure/runner.py`: раннер — часть среды, его проверяет `forge status`.
`RunnerLiquibaseGateway` остаётся в Миграции и импортирует их из ядра. Тесты переезжают
в `tests/shared/` без правки утверждений.

### Проверка среды

`EnvironmentProbe` выполняет три проверки независимо и сообщает итог каждой:

| Проверка | Пройдена, если |
|----------|----------------|
| `database` | Подключение по `FORGE_DB_*` выполняет `SELECT 1` |
| `allowlist` | Целевая БД входит в непустой `FORGE_TEST_DB_ALLOWLIST` |
| `runner` | `AGENT_RUNNER_*` заданы и цель `help` отвечает успешно |

Не заданные переменные окружения — непройденная проверка с причиной, а не исключение.
Код `2` у `forge status` означает, что хотя бы одна проверка не пройдена.

### Поиск открытой операции

Корень следа — `BACKLOG_ROOT` либо `backlog` в текущем каталоге, как у плагина.

- **Просмотр.** Читаются фронтматтеры `<корень>/forge-model/*/tasks.md`; открытые — со статусом
  `running` или `stopped`.
- **Одна открытая** — её путь в ответе.
- **Ни одной** — `operation: null`.
- **Две и больше** — нарушение инварианта навыка, код `2` с перечнем путей.
- **Нечитаемые беклоги** пропускаются с предупреждением в stderr: след чужих экспериментов
  не должен блокировать новую операцию.

### Принятие в `db/`

`FileAcceptedState` с корнем `db/` в текущем каталоге:

1. Копирует `<каталог попытки>/model.yaml` в `db/model.yaml`.
1. Копирует `<каталог попытки>/changelog.yaml` в `db/changelog/<штамп>.yaml` побайтово:
   `logicalFilePath` в нём уже равен этому пути (Q27).
1. Дописывает в `db/changelog/master.yaml` элемент
   `include: {file: <штамп>.yaml, relativeToChangelogFile: true}`, если такого ещё нет.

Повторное принятие того же штампа ничего не меняет. Проверка шлюза «changelog внутри проекта»
выполняется: `master.yaml` и его `include` лежат в `db/`.

Пути принятых файлов попадают в ответ `forge close` и в отчёт.

### Отчёт

`forge report` — модель чтения без побочных эффектов:

- **Операция:** путь беклога, штамп, намерение, режим, статус, причина остановки.
- **Число использованных попыток** — попыток с записанным вердиктом.
- **Каждая попытка:**
  - номер, вердикт, путь беклога и каталог;
  - пути `model.yaml` и `changelog.yaml`;
  - вердикт и расхождения из `reconcile.json`, если файл есть;
  - `action`, число откатанных changeset и `verified` из `rollback.json`, если файл есть.
- **Принятое состояние при `success`:** `db/model.yaml`, `db/changelog/<штамп>.yaml`,
  `db/changelog/master.yaml` и подсказка «закоммитить эти файлы». Код и номер задачи для
  сообщения коммита подставляет владелец (GIT-010).
- **Перечень беклогов:** беклог операции и беклоги попыток.

Код `1` — только при `failure`, по контракту `architecture.md`. Для `running` и `stopped` отчёт
возвращает `0`: это ответ LLM на остановку (BR-014).

### Навык `forge`

`.claude/skills/forge/SKILL.md` — инструкция агенту, а не код. Аргументы: намерение
и `--mode interactive|auto`, по умолчанию `interactive`.

1. `forge status --latest`; код `2` — вернуть LLM диагностику среды и остановиться.
1. Если есть открытая операция:
   - новое намерение не принимается, и LLM получает об этом сообщение;
   - при статусе `stopped` — `forge resume`;
   - дальше шаг 4 с её беклогом.
1. Иначе — штамп `date -u +%Y%m%d-%H%M%S`, затем
   `backlog generate --operation forge-model --subject <штамп> --value intent=<намерение>`
   с `--flag auto` или `--no-flag auto`.
1. Загрузить `/backlog:backlog-run` и исполнить беклог операции.
1. Вернуть LLM вывод `forge report --operation <беклог>`.

Навык не правит фронтматтер сам и не принимает решений, которые принимает CLI.

### Документация

- **`docs/operation.md`** (новый): статусы и переходы, пять команд, поиск открытой операции,
  принятие в `db/`, отчёт, навык, шаблоны 1.1.0.
- **`docs/architecture.md`:** строки контракта `status`, `close`, `report`, новые строки `stop`
  и `resume`, ключ `--latest`. Версия 1.0.4.
- **`README.md`:** раздел «Использование» — вызов навыка и требование плагина `backlog@formular`.

### Приёмка

Критерий результата `BUSINESS-REQUIREMENTS.md` проверяется одной операцией через навык в режиме
`auto` на `lbfr-db`. Намерение — справочник клиентов из модели-примера.

- **Проверки:** статус `success`; `backlog verify` беклога операции и беклогов попыток — код `0`;
  сверка без расхождений; файлы `db/` и отчёт.
- **Итог приёмки** — первое принятое состояние проекта. Оставить его или удалить решает владелец.
  Схема в `lbfr-db` остаётся, и при удалении `db/` том `lbfr-db-data` нужно пересоздать.

## Risks / Trade-offs

- [`backlog` не в `PATH` в сессии, начатой до установки плагина] → навык проверяет `backlog --help`
  первым шагом и при отказе называет причину; README предписывает перезапуск сессии после
  установки.
- [Агент правит фронтматтер вне предписанных полей] → статус меняют только команды; шаблоны
  называют, какие поля пишет агент; `forge status` читает фронтматтер строго и на неизвестный
  статус отвечает кодом `2`.
- [Приёмка меняет `lbfr-db` и создаёт `db/`] → она выполняется после явного запуска `/opsx:apply`.
  Итог показывается владельцу до коммита, а при отказе от него пересоздаётся том.
- [Интерактивный режим и путь `failure` не проходят приёмку целиком] → переходы статусов,
  закрытие после трёх неудач и отчёт о неудаче покрыты модульными тестами и CLI-тестами
  на беклогах, порождённых плагином.

- [Плагин `formular` 1.3.0 оставляет текст выключенного условного блока, если в него вложен
  другой блок, а `check-template` этого не видит; обнаружено при приёмке в задаче 2.1
  `forge-apply.md`] → шаблоны проекта не вкладывают блоки друг в друга. Тест порождает все
  варианты шаблона попытки и проверяет, что текст чужой ветки не попал в беклог. Исправление
  плагина — отдельная задача в его репозитории.

## Migration Plan

- Беклоги по шаблонам 1.0.0 читаются и дальше: `trail` выводится по раскладке, `stop_reason`
  вставляется при первой остановке.
- Перенос раннера в общее ядро механический.
- Откат change — возврат шаблонов 1.0.0 и удаление модуля `operation` и навыка. Принятый `db/`
  остаётся файлами проекта.
