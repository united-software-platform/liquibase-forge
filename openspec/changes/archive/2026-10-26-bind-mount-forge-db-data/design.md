# Design

## Context

`docker/lbfr/docker-compose.yaml` подключается из `docker-compose.yml` секцией `include:`
с `project_directory: .`, поэтому относительный путь источника монтирования отсчитывается от корня
проекта — так уже монтируется проект в `lbfr-liquibase` (`.:/liquibase/changelog:ro`). Образ БД —
`LBFR_POSTGRES_IMAGE=postgres:17.11`, каталог данных `/var/lib/postgresql/data`. Точка входа образа,
запущенная от `root`, при инициализации меняет владельца каталога данных на пользователя `postgres`
(uid 999) и права на `0700`. Мотивация — в proposal.md, раздел Why; требования — в
`specs/forge-environment/spec.md`.

## Goals / Non-Goals

**Goals:**

- данные `lbfr-db` в `data/lbfr-db` проекта, без именованного тома;
- каталог создаётся до запуска контейнера и исключается из git в обоих репозиториях;
- перенос данных существующей установки описан кейсом.

**Non-Goals:**

- автоматический перенос данных из тома `lbfr-db-data`;
- запуск PostgreSQL под uid пользователя хоста;
- настройка пути каталога данных переменной `.env`;
- изменения `lbfr-db-test`.

## Decisions

### Фиксированный путь `./data/lbfr-db`

Путь задан в `docker/lbfr/docker-compose.yaml` литералом. Подкаталог `lbfr-db`, а не весь `data/`:
каталог `data/` может принадлежать самому проекту, а forge занимает в нём только своё имя — его же
исключает `.gitignore`.

Альтернатива — переменная `.env` (например `LBFR_DB_DATA_DIR`): потребовала бы правки
`.env.example`, `make forge-env-sync`, `make forge-env-check` и проверки значения, а запроса на
настройку пути нет. Переменную можно добавить позже без смены поведения по умолчанию.

### Короткий синтаксис монтирования и `mkdir -p` в `up.sh`

`- ./data/lbfr-db:/var/lib/postgresql/data` в коротком синтаксисе, как у `lbfr-liquibase`.
Compose при отсутствии источника создал бы его сам, но от имени демона — каталоги `data/`
и `data/lbfr-db` стали бы принадлежать `root`. Поэтому `tools/forge-env/up.sh` выполняет
`mkdir -p data/lbfr-db` перед `docker compose up`: `data/` остаётся во владении пользователя,
и в нём можно класть свои файлы. Шаг ставится после `preflight.sh`, чтобы отказ по конфликту имени
или порта не оставлял следов в проекте.

Длинный синтаксис с `bind.create_host_path: false` отвергнут: ручной `docker compose up` без
`make forge-env-up` падал бы на отсутствующем каталоге вместо того, чтобы подняться.

### Владелец данных — пользователь контейнера

PostgreSQL остаётся под штатным пользователем образа: содержимое `data/lbfr-db` принадлежит
uid 999 с правами `0700`. Запуск под uid хоста (`user: "${UID}:${GID}"`) потребовал бы двух новых
переменных окружения и расходится между Linux и Docker Desktop. Следствие — удалить или скопировать
каталог с хоста без `sudo` нельзя; кейсы документа делают это одноразовым контейнером образа
`LBFR_POSTGRES_IMAGE`, например:

```bash
docker run --rm -v "$PWD/data:/data" "$(sed -n 's/^LBFR_POSTGRES_IMAGE=//p' .env)" rm -rf /data/lbfr-db
```

### Исключение из git — строкой `/data/lbfr-db/`

Строка добавляется в блок forge `.gitignore` репозитория и в `install/blocks/gitignore` одним
текстом: `tests/delivery/test_blocks.py` требует их совпадения. В целевой проект строка приходит
повторной установкой forge — блок заменяется целиком по требованию поставки.

### Перенос данных — кейсом, а не кодом

Существующая установка после обновления поднимает `lbfr-db` на пустом `data/lbfr-db`. Перенос
описан кейсом документа кейсов: остановить `lbfr-db`, скопировать содержимое тома одноразовым
контейнером образа БД с сохранением владельца (`cp -a /from/. /to/`), поднять окружение, проверить
данные и удалить том. Автоматический перенос в `up.sh` пришлось бы строить на угадывании имени тома
(`<проект>_lbfr-db-data` зависит от имени Compose-проекта) и на решении, что делать при непустом
каталоге; цена ошибки — потеря данных. Кроме того, принятое состояние лежит в `db/` проекта,
и целевую БД можно собрать заново накатом без переноса.

## Risks / Trade-offs

- [Каталог `data/lbfr-db` недоступен пользователю хоста и агенту] → в git его нет, инструменты
  агента обходят игнорируемые пути; удаление и копирование описаны через одноразовый контейнер.
- [Liquibase монтирует весь проект (`.:/liquibase/changelog:ro`) и может наткнуться на нечитаемый
  каталог] → Liquibase читает changelog по заданным путям `db/`, не обходя весь проект;
  интеграционный прогон наката и отката при наполненном `data/lbfr-db` подтверждает это.
- [Обновление образа на PostgreSQL 18+ меняет штатный `PGDATA` на `/var/lib/postgresql/<версия>/docker`]
  → при смене мажорной версии образа точка монтирования пересматривается; сейчас образ 17.11.
- [Пользователь обновил forge и не заметил пустую БД] → кейс переноса и упоминание в описании
  выпуска; прежний том Docker не удаляется и остаётся источником для переноса.
- [Bind-монтирование на Docker Desktop (macOS, Windows) медленнее тома] → для БД разработки
  приемлемо; при необходимости владелец вернёт том правкой вне поставки.

## Migration Plan

1. Обновить forge в проекте повторной установкой: приходят новый `docker/lbfr/docker-compose.yaml`,
   `tools/forge-env/up.sh` и блок `.gitignore`.
1. Выполнить кейс переноса данных либо принять пустую БД и накатить принятое состояние заново.
1. После проверки удалить том `<проект>_lbfr-db-data`.

Откат: вернуть прежнюю версию forge — `lbfr-db` снова смонтирует том, данные которого не удалялись.
