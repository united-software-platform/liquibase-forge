# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/forge-seed-data/spec.md`.

Что есть сейчас:

- Контекст «Моделирование» (`src/forge/modeling/`) читает `model.yaml` разборщиком
  `YamlModelDraftReader`. Разборщик получает дерево узлов `SafeLoader`, сам обходит его, видит
  повторные ключи и строит путь нарушения вида `tables[0].columns[1].length`. Структурные
  нарушения ловит разборщик, смысловые — `DataModelFactory`. Нарушение — `Violation(path, code, message)`.
- Контексты «Миграция» и «Сверка» зависят от доменных объектов модели (`DataModel`, `Table`,
  `ColumnType`) и загружают модель сценарием `LoadModelUseCase`. Модель от них не зависит.
- Принятую модель без `--accepted` команда `forge generate` берёт из корня принятого состояния
  через `settings.accepted_root()`. Неверный `FORGE_ACCEPTED_DIR` даёт код `2` с видом
  `accepted_root_invalid`.

## Goals / Non-Goals

**Goals:**

- Формат seed и его проверка как самостоятельный контекст, на который опираются следующие три
  изменения: построение changelog данных, сверка строк, операция seed.
- Значения seed в нормализованной форме, пригодной для сравнения: повтор ключа, ссылка FK,
  а позже `update` и `value_mismatch` сравнивают одно и то же представление.
- Поведение `forge validate` и формат модели не меняются.

**Non-Goals:**

- Changelog данных, накат, откат и сверка строк — изменения `add-seed-migration`
  и `add-seed-reconciliation`.
- Шаблоны беклогов, ключи навыка и принятие `seed.yaml` — изменение `add-seed-operation`.
- Значения по умолчанию, генерация ключей, вычисляемые колонки: в модели их нет.

## Decisions

### Отдельный контекст «Наполнение» (`seeding`)

Seed — отдельное понятие со своим жизненным циклом. Оно меняется операцией seed, а не операцией
модели. Контекст `src/forge/seeding/` строится по слоям, как остальные (CLAR-022). Зависимость
на «Моделирование» идёт в одну сторону, по прецеденту «Миграции» и «Сверки»: домен seed читает
`DataModel` и `Table`, приложение загружает модель через `LoadModelUseCase`.

Альтернатива — поле `rows` у таблицы в `model.yaml` — отклонена: модель описывает структуру,
и changelog модели тогда пришлось бы учить отличать структуру от данных. Кроме того, это нарушает
решение «отдельная операция» (Q2).

### Общий обход узлов YAML выносится в `shared`

Seed нужен тот же разбор, что модели: повторные ключи, логический путь, вид значения, сообщение
о синтаксической ошибке со строкой и столбцом. Помощники обхода (теги, названия видов,
`get_single_node`, проверка состава полей и повторов) выносятся из `yaml_reader.py` модели
в `src/forge/shared/infrastructure/yaml_nodes.py`. Ответ `forge validate` не меняется,
это подтверждают существующие тесты модели.

Альтернативы отклонены:

- Импорт инфраструктуры модели из seed — связь контекстов через инфраструктуру, а не через
  контракт (CLAR-023).
- Копия обхода в seed — две копии правил разбора разойдутся при первой правке.

`Violation` и `join_path` используются из домена модели, как доменные объекты модели в «Миграции».
Отдельный тип нарушения seed с той же формой был бы вторым именем одного понятия (DDD-002).

### Значение хранится сырым до проверки по типу

Разборщик seed не приводит значения: каждое значение строки попадает в черновик как пара
«тег YAML + исходный текст скаляра». Тип колонки известен только по модели, и разборщик её
не видит.

Объект-значение `SeedValue` создаётся фабрикой домена по типу колонки (DDD-014) и несёт
нормализованную форму:

| Тип | Нормализованная форма |
|-----|------------------------|
| `integer`, `bigint` | целое |
| `boolean` | `true` / `false` |
| `string`, `text` | строка как есть |
| `decimal` | десятичное без лишних нулей дроби и без `+` |
| `date` | `YYYY-MM-DD` |
| `timestamp` | `YYYY-MM-DDTHH:MM:SS[.ffffff]` без хвостовых нулей дроби |
| `timestamp_tz` | тот же вид, приведённый к UTC с суффиксом `Z` |
| `uuid` | строка как есть, проверенная по шаблону |

Значения сравниваются только по нормализованной форме: `"1.50"` и `"1.5"` — один ключ,
`2026-01-01T03:00:00+03:00` и `2026-01-01T00:00:00Z` — один момент.

Даты без кавычек YAML помечает тегом `timestamp`. Поэтому для `date`, `timestamp` и `timestamp_tz`
принимаются теги `str` и `timestamp`, а разбирается исходный текст. Для `decimal` принимаются `str`
и `int`, для `string` и `text` — только `str`. Дробное число YAML и число без кавычек в строковой
колонке — `invalid_value`: неявное приведение спрятало бы потерю точности или ведущих нулей.

### Порядок проверки

Проверка идёт в три прохода, порядок нарушений устойчив:

1. **Структура** — разборщик: корень, поля таблиц, вид `rows` и строк, повторы ключей.
   Таблица со структурным нарушением дальше не проверяется.
1. **Таблицы и строки** в порядке документа:
   - имя таблицы и её повтор;
   - для каждой строки — колонки в порядке строки, затем пропущенные NOT NULL колонки в порядке
     модели;
   - повторы PK, затем повторы наборов `unique`.

   Строка, у которой нарушено хотя бы одно значение, в проверках ключей не участвует.
1. **Ссылки**:
   - по таблицам и FK в порядке документа: сначала `unseeded_reference_table`, затем
     `unresolved_reference` по строкам;
   - затем циклы.

Цикл ищется алгоритмом сильно связных компонент по графу «строка → строка цели FK». Ссылка
строки на себя ребром не считается. Нарушение `reference_cycle` ставится на первую строку
компоненты в порядке документа, сообщение перечисляет строки цикла.

### Команда и источник модели

`forge validate-seed` устроена как `forge validate`: подкоманда в `src/forge/cli/commands/`
и сценарий `ValidateSeedUseCase` с входным и выходным контрактами (CLAR-007..011). Модель
по умолчанию разрешается тем же путём, что в `forge generate`: `settings.accepted_root()/model.yaml`.
Нет файла — модель пуста (`version: 1`, `tables: []`).

Некорректная модель — код `2` с видом `model_invalid`, а не перечень её нарушений: чинить нужно
модель, это делает `forge validate`.

## Risks / Trade-offs

- [Вынос обхода YAML меняет код модели] → изменение чисто перемещающее: тесты
  `tests/modeling/` и `tests/cli/test_validate.py` прогоняются без правок до и после выноса.
- [Нормализация `timestamp_tz` в UTC теряет исходное смещение] → для PostgreSQL это не потеря:
  `timestamptz` хранит момент без смещения. Сверка следующего изменения сравнивает именно момент.
- [Цикл в длинном справочнике трудно прочесть] → сообщение перечисляет строки цикла их PK
  в порядке обхода.
- [Колонка без ключа означает NULL, опечатку в имени легко принять за пропуск] → опечатка
  даёт `unknown_column`. Если колонка NOT NULL, пропуск даёт ещё и `null_value`.
- [Seed проверяется по принятой модели, а операция модели может её поменять] → согласование
  принятого seed с моделью (`seed_conflict`) — в изменении `add-seed-operation`.

## Migration Plan

Миграции нет: формат и команда новые, существующие файлы и команды не меняются. Откат —
удаление подкоманды и контекста `seeding`; вынос `yaml_nodes.py` обратной правки не требует.
