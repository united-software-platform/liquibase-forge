# Proposal

## Why

Ветка `main` не защищена: в неё можно слить PR с красным `checks` и даже запушить напрямую. Классическую защиту
с обязательной проверкой в 0.2.0 не включили (LBFR-018) по одной причине: она отклоняет push релизного коммита
от `github-actions[bot]`. У нового коммита `Релиз vX.Y.Z` нет зелёной проверки, а `GITHUB_TOKEN` правило не обходит.
Задача #8 (LBFR-020) входит в выпуск 0.3.0.

## What Changes

- **Ruleset для `main`, описанный в репозитории** (`.github/rulesets/main.json`), включается на GitHub:
  - слияние только через PR, обязательных одобрений — 0;
  - обязательная проверка — job `checks` («Линтер, форматирование, типы, тесты, Makefile»,
    приложение GitHub Actions);
  - ветку не требуется подтягивать до свежего `main`;
  - force-push и удаление ветки запрещены.
- **Обход правил — только у ключа развёртывания (deploy key).** У администраторов обхода нет: слить
  в `main` PR с красным `checks` не может никто.
- **Релизный сценарий публикует коммит и тег через deploy key.** Шаг получения репозитория в `release.yml`
  берёт закрытый ключ из секрета `RELEASE_DEPLOY_KEY`, и `git push` идёт по SSH от имени ключа.
  GitHub Release по-прежнему создаётся через `GITHUB_TOKEN`.
- Push ключом развёртывания, в отличие от `GITHUB_TOKEN`, запускает workflow. Поэтому на релизном коммите
  в `main` впервые появится прогон `checks`.
- **Deploy key с правом записи и секрет `RELEASE_DEPLOY_KEY` заводятся на GitHub.** Закрытая часть ключа
  после этого нигде, кроме секрета, не хранится.
- **Тесты:**
  - обязательная проверка в ruleset называется так же, как job в `checks.yml`;
  - обходит правила только deploy key;
  - в ruleset есть правила PR, запрета force-push и удаления;
  - `release.yml` получает репозиторий с ключом из секрета.
- **`CONTRIBUTING.md`, раздел «Выпуск версии»:** защита `main`, ключ развёртывания, команды применения ruleset
  и замены ключа. Предусловие «`github-actions[bot]` должен иметь право push в `main`» заменяется.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `forge-checks`: новое требование — изменения попадают в `main` только через PR с пройденными проверками,
  force-push и удаление `main` запрещены, а описание правил лежит в репозитории.
- `forge-release`: новое требование — релизный коммит и тег публикуются в защищённую `main` единственным
  субъектом с обходом правил, ключом развёртывания релизного сценария.

## Impact

- **Новый файл** `.github/rulesets/main.json`.
- **Правки:**
  - `.github/workflows/release.yml` — шаг получения репозитория и комментарии;
  - `CONTRIBUTING.md` — «Выпуск версии» и «Устройство репозитория»;
  - тесты в `tests/release/`.
- **Настройки GitHub** (только по команде владельца):
  - ruleset `main`;
  - deploy key `release` с правом записи;
  - секрет Actions `RELEASE_DEPLOY_KEY`.
- **Порядок в выпуске 0.3.0:**
  - ключ и секрет заводятся до слияния PR выпуска;
  - ruleset включается до слияния, и PR выпуска сливается уже через защиту;
  - запуск `release` после слияния проверяет, что deploy key проходит защиту.
- **Зависимость от change `update-actions-node24`:** оба меняют шаг получения репозитория в `release.yml`.
  Этот change выполняется после него, поверх `actions/checkout@v7`.
