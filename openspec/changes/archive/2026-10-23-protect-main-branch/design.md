# Design

## Context

Что известно на 2026-10-23:

- **Репозиторий** `united-software-platform/liquibase-forge` публичный, владелец — организация на тарифе free.
  Rulesets для публичного репозитория доступны. У `main` нет ни ruleset'ов, ни классической защиты.
  Deploy key'ев и секретов Actions нет.
- **Проверка в PR** публикуется как check run «Линтер, форматирование, типы, тесты, Makefile». Это имя job'а
  `checks` в `checks.yml`, приложение `github-actions`, `integration_id` 15368. Из релизного сценария тот же
  job виден как «Проверки / Линтер, …», но защита смотрит на прогон PR.
- **Релизный коммит `Релиз v0.2.0`** опубликован через `GITHUB_TOKEN`, и прогонов `checks` на нём нет: push
  этим токеном workflow не запускает.
- **Публикация в `release.yml`:** `actions/checkout` с `GITHUB_TOKEN` по умолчанию, затем `git push origin HEAD`
  и `git push origin "v$NEXT"`, затем `gh release create` с `GH_TOKEN: secrets.GITHUB_TOKEN`.

Change `update-actions-node24` меняет в том же шаге версию `checkout` на `@v7`. Этот change применяется после него.

## Goals / Non-Goals

**Goals:**

- В `main` нельзя слить PR с красным `checks` и нельзя запушить напрямую. Это относится и к администраторам.
- Релизный сценарий проходит защиту без участия человека и без личных токенов.
- Правила защиты лежат в репозитории и сверяются тестом с `checks.yml`.

**Non-Goals:**

- Обязательные одобрения PR и CODEOWNERS: сопровождающий один, своё PR он одобрить не может.
- Ограничение способов слияния. Выпуск сливается merge-коммитом по договорённости, правилом это не закрепляется.
- Защита тегов `v*` и веток `release/*`.
- Автоматическое применение ruleset'а из CI. Применяет владелец командой из `CONTRIBUTING.md`.

## Decisions

**Ruleset, а не классическая защита ветки.** Классическая защита не умеет давать обход ключу развёртывания:
её исключения — люди, команды и приложения. Ruleset поддерживает обход для `DeployKey` и описывается JSON'ом,
который принимает REST API. Поэтому файл в репозитории — это ровно то, что уходит в
`POST /repos/{owner}/{repo}/rulesets`.

**Состав `.github/rulesets/main.json`:**

| Поле | Значение | Зачем |
|------|----------|-------|
| `target`, `conditions.ref_name.include` | `branch`, `~DEFAULT_BRANCH` | Правило следует за веткой по умолчанию, а не за строкой `main` |
| `enforcement` | `active` | Режим `evaluate` на free недоступен и защиты не даёт |
| `bypass_actors` | один: `DeployKey`, `bypass_mode: always` | Обходит только релизный сценарий |
| `pull_request` | `required_approving_review_count: 0`, остальные флаги `false` | Только PR, без одобрений |
| `required_status_checks` | контекст «Линтер, форматирование, типы, тесты, Makefile», `integration_id: 15368`, `strict_required_status_checks_policy: false` | Обязательна проверка именно от GitHub Actions. Подтягивать ветку до свежего `main` не нужно, иначе каждый релизный коммит заставлял бы обновлять ветку выпуска |
| `non_fast_forward`, `deletion` | без параметров | Запрет force-push и удаления |

Рассматривался вариант без правила `pull_request`, только с обязательной проверкой. Прямой push тогда
отклоняется лишь потому, что у нового коммита нет проверки. Это неявно, и владелец этот вариант отклонил.

**Deploy key вместо GitHub App и PAT (решение владельца).** Ключ с правом записи действует только в этом
репозитории, не привязан к личной учётной записи и не истекает. В отличие от `GITHUB_TOKEN`, push ключом
запускает workflow, поэтому на релизном коммите появится прогон `checks`. GitHub App потребовал бы приложения
в организации, созданного вручную, и дополнительного действия получения токена. PAT привязан к человеку,
истекает, а его обход через роль admin открыл бы администратору слияние с красным `checks`.

**Как ключ попадает в сценарий:**

- Перед получением репозитория стоит отдельный шаг «Гейт ключа развёртывания». Он завершается ошибкой,
  если `RELEASE_DEPLOY_KEY` пуст.
  - Без гейта `actions/checkout` молча взял бы `GITHUB_TOKEN`, и сценарий упал бы только на push. Коммит
    при этом остался бы локальным, и в публикацию ничего бы не ушло, но причина ошибки была бы непонятна.
  - Секрет передаётся через `env`, а не подставляется в скрипт.
- Шаг получения репозитория — `actions/checkout@v7` с `ssh-key: ${{ secrets.RELEASE_DEPLOY_KEY }}`.
  Учётные данные сохраняются (умолчание `persist-credentials`), и последующие `git push` идут по SSH
  с этим ключом.
- `gh release create` остаётся на `GITHUB_TOKEN`. Ruleset на ветку релизы не затрагивает, и права
  `contents: write` у job'а `release` хватает.

**Заведение ключа без следов на диске.** Ключ генерируется (`ssh-keygen -t ed25519 -N ""`) в каталоге,
который затем удаляется. Открытая часть уходит в `gh repo deploy-key add --allow-write --title release`,
закрытая — в `gh secret set RELEASE_DEPLOY_KEY`. После этого оба файла стираются. Те же команды в
`CONTRIBUTING.md` служат порядком замены ключа: удалить старый deploy key и завести новый.

**Применение ruleset'а — идемпотентным скриптом `tools/github/apply-ruleset.sh`.** Скрипт ищет ruleset
с именем из файла. Если его нет — создаёт (`POST`), если есть — обновляет (`PUT /rulesets/{id}`).
Повторный запуск ничего не меняет. Коды возврата: `0` — применено, `1` — ошибка API, `2` — ошибка вызова.
Их таблица по DGN-012 будет в `CONTRIBUTING.md`.

**Тесты в `tests/release/test_main_ruleset.py`:**

- контекст обязательной проверки равен `jobs.checks.name` из `checks.yml`;
- обход только у `DeployKey`;
- правила `pull_request` (0 одобрений), `non_fast_forward` и `deletion` присутствуют;
- в `release.yml` гейт ключа стоит до получения репозитория, а `checkout` берёт `ssh-key` из секрета.

Скрипт применения проверяется заглушкой `gh`, как гейт задач выпуска.

## Risks / Trade-offs

- [Ruleset включён, а в `main` ещё старый `release.yml` без ключа] → Выпуск из такой `main` упадёт на push
  до тега и релиза. В 0.3.0 PR выпуска сливается раньше запуска `release`, и в `main` уже новый сценарий.
- [Имя check run'а не совпадёт с контекстом, и PR станет невозможно слить] → Тест сверяет контекст с `checks.yml`.
  Перед слиянием PR выпуска владелец видит в PR обязательную проверку зелёной.
- [Утечка закрытого ключа] → Ключ действует только в этом репозитории. Отзыв — удаление deploy key
  на GitHub, замена — командами из `CONTRIBUTING.md`. На диске ключ не остаётся.
- [GitHub Actions сломан, PR не слить, а обхода у администраторов нет] → Владелец временно переводит ruleset
  в `disabled` через настройки или API и возвращает тем же скриптом. Это осознанная цена отказа от обхода.
- [Обход `always` у ключа позволяет и force-push в `main`] → Ключ использует только релизный сценарий,
  а его `git push` — без `--force`, это сторожат тесты релизного сценария.

## Migration Plan

1. Реализация в ветке `release/v0.3.0`:
   - файл ruleset'а;
   - скрипт применения;
   - гейт ключа и `ssh-key` в `release.yml`;
   - тесты;
   - `CONTRIBUTING.md`.
1. Коммит `LBFR-020`.
1. По команде владельца, до слияния PR выпуска:
   - завести deploy key и секрет;
   - применить ruleset;
   - убедиться, что `GET /repos/.../rules/branches/main` показывает правила.
1. По команде владельца — проверка критерия на одноразовом PR с намеренно красным тестом. `gh pr merge`
   отклоняется. После этого PR закрывается, ветка удаляется.
1. Слияние PR выпуска 0.3.0 через защиту и запуск `release` с `minor`: проверка, что ключ проходит защиту.

Откат: ruleset переводится в `disabled` или удаляется, из `release.yml` убираются гейт и `ssh-key`, deploy key
удаляется. Тогда сценарий снова публикует через `GITHUB_TOKEN`.

## Open Questions

- Точная форма `bypass_actors` для `DeployKey` в REST API (`actor_id: null` или поле опущено) уточняется
  первым применением скрипта. На подход и задачи это не влияет.
