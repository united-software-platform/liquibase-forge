# Design

## Context

Мотивация — в proposal.md, требования — в дельтах спецификаций. Изменение опирается на
`add-drop-operations`: после него diff моделей — `ModelDiff`, `SchemaChange` содержит удаления,
рендер пишет блоки `rollback`, `ChangelogSummary` знает удалённые объекты, а `forge generate`
проверяет `allow_drop`. Текущее устройство вне этого изменения:

- Модель собирается в два уровня: `yaml_reader` строит черновик (`DataModelDraft`, `TableDraft`)
  и структурные нарушения, `DataModelFactory` превращает черновик в `DataModel` и собирает
  смысловые нарушения по таблицам. Межтабличных правил сейчас нет.
- Сверка: `PsycopgSchemaIntrospector` читает таблицы, колонки и первичные ключи в `ActualSchema`,
  `SchemaComparison` сравнивает их с моделью по таблицам.
- Проверка возврата `forge rollback` идёт через `SchemaProbeInterface` с проверками наличия
  таблицы и колонки.

## Goals / Non-Goals

**Goals:**

- Связи и уникальность — часть модели с тем же циклом, что таблицы и колонки: проверка, diff,
  накат, сверка, откат.
- Имена ограничений вычисляются из модели без хранения состояния.

**Non-Goals:**

- `ON DELETE`/`ON UPDATE`, `CHECK`, индексы, отложенные ограничения (`DEFERRABLE`).
- Проверка данных перед добавлением ограничения: нарушение данных — ошибка наката и неуспешная
  попытка.

## Decisions

### Объекты-значения модели

В домене моделирования появляются `UniqueSet` (кортеж `ColumnName`) и `ForeignKey` (колонки,
`TableName` цели, колонки цели), оба неизменяемы. `Table` получает `unique` и `foreign_keys`.
Тождество — по содержимому: `UniqueSet` сравнивается как множество колонок, `ForeignKey` —
как множество пар «колонка FK → колонка цели» вместе с целевой таблицей. Так перестановка
пар и наборов не даёт изменений ни в diff, ни в сверке.

### Проверка в два прохода

Правила одной таблицы для `unique` (неизвестная колонка, повтор, совпадение с PK, повтор набора)
проверяет фабрика при сборке таблицы, рядом с правилами PK. FK требует всех таблиц, поэтому
фабрика сначала собирает таблицы, затем вторым проходом по таблицам в порядке модели проверяет
их FK против уже собранных таблиц. Таблица, не собранная из-за нарушений, целью не служит:
FK на неё не проверяется, пока таблица не исправлена — так же, как правила таблицы ждут
исправления колонок. Порядок нарушений: сначала все нарушения таблиц в порядке модели, затем
нарушения FK по таблицам и FK в порядке модели.

Альтернатива — отдельный доменный сервис проверки связей после фабрики — отвергнута: фабрика
уже единственная точка, где невалидный объект не создаётся (DDD-014), и `DataModel` с битыми
ссылками существовать не должна.

### Имена ограничений

`fk_<таблица>_<hash8>` и `uq_<таблица>_<hash8>`, где `hash8` — первые восемь знаков SHA-256
канонической строки содержимого: для набора — отсортированные колонки, для FK — пары,
отсортированные по колонке FK, и целевая таблица. Таблица в имени обрезается до 51 символа:
`3 + 51 + 1 + 8 = 63`. Функция имени живёт в инфраструктуре миграции рядом с `primary_key_name`:
имя — знание о Liquibase и СУБД. Сверка имён не сравнивает, а откат вызывает ту же функцию.

Альтернативы: позиционный номер — ломается при перестановке и даёт удаление не того ограничения;
поле `name` в модели — лишняя обязанность агента и новый источник нарушений.

### Diff и порядок

`ModelDiff` добавляет четыре изменения: `AddUnique`, `DropUnique`, `AddForeignKey`,
`DropForeignKey`. Удаляемые ограничения — те, что есть в принятой модели и отсутствуют в модели
попытки по содержимому, включая ограничения удаляемых таблиц и колонок. Для удаляемой таблицы
`DropForeignKey` порождается для её FK и для FK других таблиц принятой модели, ссылающихся на неё;
`DropUnique` для её наборов не порождается — `dropTable` снимает их вместе с таблицей, а его откат
восстанавливает. Для удаляемой колонки ограничения, в которые она входит, обязаны исчезнуть
из модели попытки, иначе `forge validate` отклонит модель; их удаление идёт своей группой.

Порядок групп — по дельте `forge-migration`. Liquibase откатывает changeset в обратном порядке,
поэтому при откате сначала снимаются новые FK и наборы, затем восстанавливаются колонки и таблицы
и только потом — удалённые FK, когда их цели уже на месте.

### Рендер и откат changeset ограничений

- `AddUnique` → `addUniqueConstraint` (`tableName`, `columnNames`, `constraintName`); откат
  Liquibase выводит сам.
- `AddForeignKey` → `addForeignKeyConstraint` (`baseTableName`, `baseColumnNames`,
  `referencedTableName`, `referencedColumnNames`, `constraintName`); откат выводится.
- `DropUnique`/`DropForeignKey` → `dropUniqueConstraint`/`dropForeignKeyConstraint` с явным
  `rollback` из соответствующего `add…`.
- Откат `dropTable` дополняется `addUniqueConstraint` наборов таблицы после `addPrimaryKey`.

`ChangelogSummary` получает добавляемые и удаляемые ограничения: вид (`foreign_key`/`unique`),
таблицу и имя. Читатель распознаёт четыре формы.

### Проверка возврата

`SchemaProbeInterface` получает `constraint_exists(database, table, name, kind)`; реализация
читает `pg_constraint` с `contype` `f` или `u`. `RollbackAttemptUseCase._verify` добавляет
четыре проверки по сводке.

### Сверка

`ActualTable` получает `foreign_keys` и `unique` — кортежи колонок и цели, без имён. Интроспекция
читает `pg_constraint` (`contype in ('f','u')`, `conkey`, `confkey`, `confrelid`) с раскрытием
номеров колонок через `pg_attribute`. `SchemaComparison` после первичного ключа сравнивает наборы
и FK как множества и выдаёт расхождения в порядке дельты `forge-reconciliation`. Поля расхождения:
`table`, `column: null`, `expected`/`actual` — текст вида `[customer_id] → customer[id]` либо
`[tenant_id, code]` против `absent`/`present`.

### Отображение в отчёте и ответах

Ответ `forge generate` называет новые виды changeset: `add_unique`, `drop_unique`,
`add_foreign_key`, `drop_foreign_key`; поле `column` у них `null`, а имя ограничения — в новом
поле `constraint`. В `destructive` отчёта удаления ограничений не входят.

## Risks / Trade-offs

- [Коллизия `hash8` у двух ограничений одной таблицы] → вероятность пренебрежима; фабрика
  отклоняет повтор содержимого, а совпадение хешей разного содержимого даст ошибку наката, а не
  тихую порчу схемы.
- [Добавление ограничения к таблице с данными падает на накате] → штатный неуспех попытки
  с диагностикой Liquibase; описано в `docs/migration.md`.
- [PostgreSQL не создаёт индекс под колонки FK] → индексы вне объёма; ограничение зафиксировано
  в `docs/model-format.md`.
- [Уникальность по колонкам, допускающим NULL, пропускает повторные NULL] → поведение PostgreSQL;
  фиксируется в `docs/model-format.md`.
- [Конфликт дельт с `add-drop-operations` при архивации] → дельты этого изменения не правят
  требований, которые меняет `add-drop-operations`, а только добавляют свои; архивация — после
  него.

## Migration Plan

Миграции данных нет: модели без `foreign_keys` и `unique` остаются корректными, принятые
changelog не меняются. Порядок: реализовать и архивировать `add-drop-operations`, затем это
изменение в той же ветке `release/v0.2.0`.
