# Design

## Context

В репозитории две workflow, и действия из GitHub подключены в трёх местах:

| Workflow | Действие | Сейчас | Среда |
|----------|----------|--------|-------|
| `checks.yml` | `actions/checkout` | `@v4` | node20 |
| `checks.yml` | `astral-sh/setup-uv` | `@v6` | node20 |
| `release.yml` | `actions/checkout` | `@v4` | node20 |

`release.yml` вызывает `checks.yml` через `workflow_call`, поэтому версии из `checks.yml` срабатывают и при выпуске.
Других `uses:` с внешними действиями нет.

Что выяснено по `action.yml` на тегах и по релизам (2026-10-23):

- `actions/checkout`: `v5`, `v6` и `v7` объявляют `using: node24`. Плавающий тег `v7` есть, последний релиз — `v7.0.1`.
  С v5 по v7 менялись среда исполнения, место хранения учётных данных и запрет checkout форка
  на `pull_request_target`/`workflow_run`. Ни одна из этих правок наш сценарий не затрагивает.
- `astral-sh/setup-uv`: `v7` — последний плавающий мажорный тег, тоже node24. Начиная с `v8.0.0` релизы
  неизменяемые, а теги `vN` и `vN.M` не публикуются. Последний релиз — `v10.3.2`, `using: "node24"`.
  Входы `version` и `python-version` на месте, контрольная сумма `x86_64-unknown-linux-gnu-0.12.7` известна.

## Goals / Non-Goals

**Goals:**

- Все действия обеих workflow исполняются на Node.js 24, и предупреждение о Node.js 20 из прогонов уходит.
- Способ закрепления каждого действия записан в комментарии рядом и охраняется тестом.

**Non-Goals:**

- Закрепление действий хэшем коммита.
- Смена `runs-on`. Метка `ubuntu-latest` остаётся, переход на Ubuntu 26.04 проверит прогон PR.
- Обновление uv и Python. `0.12.7` совпадает с контейнером агента, `3.12` — с проектом.
- Dependabot и другая автоматизация обновления действий.

## Decisions

**`actions/checkout@v7`, плавающий мажорный тег.** Плавающий тег — штатная схема публикации GitHub
для собственных действий: внутри мажорной версии приходят исправления, и обновлять мажорную версию
приходится только при снятии среды исполнения. Рассматривались два варианта. `@v5` — минимальный
переход на node24, но это уже две устаревшие мажорные версии, и следующее обновление придёт раньше.
Хэш коммита отклонён владельцем вместе с хэшем для `setup-uv`.

**`astral-sh/setup-uv@v10.3.2`, точный неизменяемый релиз (решение владельца).** Плавающих тегов у новых
версий нет, а последний плавающий `@v7` — ветка, которая дальше не развивается. Держаться за неё значит
сохранить ту подвижность тега, от которой Astral отказались из-за атак на цепочку поставок. Точный
релиз неизменяем: его содержимое нельзя подменить переносом тега. Цена — обновлять версию вручную.
В комментарии к шагу записано, почему версия точная.

Breaking changes v8–v10 нас не задевают:

| Версия | Изменение | Почему не задевает |
|--------|-----------|--------------------|
| v8.0.0 | Удалён старый формат `manifest-file`; не публикуются теги `vN`/`vN.M` | `manifest-file` не используется; версия закрепляется точно |
| v9.0.0 | `prune-cache` по умолчанию `false` | Меняет только объём кэша Actions |
| v10.0.0 | `enable-cache: auto` выключает кэш на `pull_request_target`, `workflow_run`, `release` | Наши события — `pull_request`, `push`, `workflow_call` |

**`ubuntu-latest` остаётся (решение владельца).** Сценарии не опираются на программы образа раннера,
кроме `sh`, `git` и `gh`. Python ставит `setup-uv`. Закрепление `ubuntu-24.04` лишь отложило бы тот же
переход до снятия метки 24.04 и потребовало бы ещё одной задачи.

**Тест на версии действий в `tests/release/test_checks_workflow.py`.** Тест проверяет два свойства,
а не конкретные номера:

- `checks.yml` и `release.yml` закрепляют одинаковую версию `actions/checkout`. Иначе обновление
  одного файла молча оставит второй на старой среде.
- версия `astral-sh/setup-uv` записана полностью, `X.Y.Z`. Укороченный `@v10` у этого действия
  не существует, и прогон упал бы уже на GitHub.

Номера в тесте не повторяются, поэтому следующее обновление действий не потребует правки теста.

## Risks / Trade-offs

- [На Ubuntu 26.04 сломается шаг, завязанный на образ] → Такой шаг увидит первый же прогон `checks`
  на PR. Откат — одна строка `runs-on: ubuntu-24.04`, она возможна до снятия метки 24.04.
- [`setup-uv@v10.3.2` не получит исправлений без ручного обновления] → Это принятая цена неизменяемости.
  Устаревание действия GitHub снова покажет предупреждением в прогоне.
- [Предупреждение о Node.js 20 проверяется только на GitHub] → Пробный запуск `release` из ветки
  `release/v0.3.0` вызывает `checks` с новыми версиями. На шаге «Гейт ветки main» job `release`
  останавливается до получения репозитория и до любой записи. `checkout@v7` в `release.yml`
  до него не доходит: его версию проверяет тест равенства с `checks.yml`.
- [Пробному запуску нужна ветка на GitHub] → Push ветки `release/v0.3.0` — только по команде владельца
  (GIT-015). Без него критерий проверяется прогоном PR в конце выпуска.

## Migration Plan

1. Правка `uses:` в обеих workflow и комментарий о закреплении `setup-uv`.
1. Тест на версии действий, затем полный локальный прогон проверок.
1. Коммит `LBFR-023`. Push ветки и пробный запуск `gh workflow run release.yml --ref release/v0.3.0 -f bump=patch` — по команде владельца.
1. В логе пробного прогона: job `Проверки` зелёный и без предупреждения о Node.js 20, job `release` остановлен гейтом ветки.

Откат — вернуть прежние строки `uses:`. Состояние репозитория и GitHub от версий действий не зависит.
