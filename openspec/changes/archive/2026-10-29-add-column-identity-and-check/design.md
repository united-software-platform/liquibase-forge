# Design

## Context

Мотивация — в [proposal.md](./proposal.md#why), требования — в delta-specs изменения.

Текущее состояние кода, на которое опирается решение:

- `Column` (`src/forge/modeling/domain/column.py`) хранит `name`, `type` и `nullable` с тремя
  состояниями. Итоговую допустимость NULL вычисляет `Table.is_nullable`, и на неё опираются
  `ModelDiff`, запись changelog, сверка и проверка seed.
- Читатель YAML (`src/forge/modeling/infrastructure/yaml_reader.py`) проверяет только вид
  значений и состав полей (`_COLUMN_OPTIONAL`). Смысл проверяет `DataModelFactory`.
- `ModelDiff` отождествляет ограничения по содержимому, изменение ограничения выражает удалением
  и добавлением, а неподдерживаемые изменения собирает в `UnsupportedChangeError`.
- Changelog пишет `liquibase_changelog.py`. Имена ограничений `uq_` и `fk_` вычисляются хешем
  содержимого. Сводка changelog (`ChangelogSummary.constraints`) знает виды `unique`
  и `foreign_key`. На неё опирается проверка отката (`<вид>_absent`, `<вид>_present`) через
  `constraint_exists(…, kind)`.
- Интроспекция сверки (`postgres_introspection.py`) читает из `pg_constraint` только `p`, `u`
  и `f`, а из `pg_attribute` — тип и NOT NULL.
- Конфликты seed (`SeedConflictCheckerInterface`) находятся проверкой принятого seed по модели
  попытки. Коды нарушений seed отображаются в виды конфликта.
- Целевая СУБД — PostgreSQL 17 (`LBFR_POSTGRES_IMAGE=postgres:17.11`), Liquibase берётся
  из образа kit'а.

> **Примечание:** в тикете #26 пути кода указаны с префиксом `tools/forge/`, а код лежит
> в `src/forge/`. Комментарий о решении в тикете называет фактические пути.

## Goals / Non-Goals

**Goals:**

- Модель выражает identity-колонку и перечень значений колонки. Оба свойства проходят весь путь
  forge: проверку, changelog, накат, сверку, откат и проверку seed.
- Принятые модели, changelog и seed прежних версий остаются корректными без правок.
- Расхождения и проверки отката называют новые ограничения так же, как действующие: по содержимому,
  с устойчивым порядком.

**Non-Goals:**

- Режим `GENERATED ALWAYS`, параметры последовательности (`START WITH`, `INCREMENT BY`)
  и `serial`.
- Произвольные выражения `CHECK`, ограничения над несколькими колонками, `CHECK` у типов вне
  `string`, `text`, `integer` и `bigint`.
- Включение и выключение генерации у существующей колонки: это перенос данных, а не изменение
  схемы.
- Сдвиг последовательности identity после вставок seed.

## Decisions

### Р1. Номер выпуска — 0.5.0

Изменение добавляет в формат новые необязательные поля. По semver это минорная версия: патч
зарезервирован за исправлениями. Задача #26 кладётся в milestone `v0.5.0`, а релизный сценарий
запускается с разрядом `minor`.

Отвергнутые варианты: `0.4.2` — патч не отражал бы новую возможность; `0.4.3` — номер не следует
за `0.4.1`, и релизный сценарий его не выдаёт.

### Р2. Генерация значения — `generated: identity` в режиме BY DEFAULT

Поле `generated` принимает единственное значение `identity`. Оно отображается
в `GENERATED BY DEFAULT AS IDENTITY`. В домене это перечисление `Generation` с одним значением.
Новое значение добавляется без смены формата.

Почему `BY DEFAULT`, а не `ALWAYS`: seed вставляет строки справочников с явными значениями
ключа, а `ALWAYS` такую вставку запрещает без `OVERRIDING SYSTEM VALUE`. К тому же Liquibase
с `autoIncrement` на PostgreSQL строит именно `BY DEFAULT`.

Отвергнутые варианты: `generated: true` — не оставляет места для другого способа генерации;
два значения `identity_always` и `identity_by_default` — второй режим сейчас не нужен.

### Р3. Колонка с генерацией — целая и NOT NULL, одна на таблицу

- Тип — `integer` или `bigint`.
- Явное `nullable: true` запрещено, а без `nullable` колонка считается NOT NULL.
  `Table.is_nullable` возвращает `False` для колонки с `generated`.
- Колонок с генерацией в таблице не больше одной.

Первое и третье правила повторяют ограничения PostgreSQL, второе — семантику identity-колонки.
Итоговое NOT NULL в одном месте автоматически распространяется на changelog, сверку NULL,
проверку seed (`null_value`) и конфликт `not_null_column_added`.

Проверки распределены по слоям так:

| Где | Что проверяется |
|-----|-----------------|
| Читатель YAML | Вид значения: строка у `generated`, список скаляров у `check` |
| `Column` | Совместимость с типом и с `nullable`: `generated_requires_integer`, `generated_nullable`, `check_with_generated` |
| `Table.violations_of` | Повтор генерации в таблице: `duplicate_generated` |

### Р4. Перечень — колоночное поле `check`, без выражений

`check` — непустой список значений без повторов. В домене это объект-значение `ValueList`
с кортежем значений и сравнением по множеству значений. Пустой список и повтор проверяются
в объекте-значении, совместимость значений с типом — при сборке `Column`.

Типы значений сохраняются из YAML. Строка для `string` и `text` проверяется по `length`, целое
для `integer` и `bigint` — по пределам типа. Пределы целых берутся из того же источника, что
у проверки seed. Логическое значение YAML целым не считается, хотя в Python `bool` — подкласс `int`:
проверка явно отличает `bool` от `int`.

Отвергнутые варианты:

- Табличное поле `checks: [{name, expression}]`. Выражение не проверить в домене, а при сверке
  пришлось бы сравнивать текст, нормализованный PostgreSQL.
- Поле с другим именем, например `allowed` или `values`. Владелец принял имя из тикета.

### Р5. Версия формата не меняется

`FORMAT_VERSION` остаётся `1`. Поля необязательны, поэтому прежние модели читаются как раньше.

### Р6. Identity в changelog — `autoIncrement` и явный `generationType`

У колонки с генерацией определение в changelog получает `autoIncrement: true`
и `generationType: BY DEFAULT`. Режим задаётся явно, чтобы не зависеть от умолчания версии
Liquibase. Определение колонки строит одна функция `_column`, поэтому атрибуты появляются во всех
местах сразу: `createTable`, `addColumn` и откаты `DropTable` и `DropColumn`.

Фактический DDL закрепляется интеграционным тестом на Liquibase из образа kit'а.

### Р7. CHECK в changelog — `sql` с явным откатом и именем `ck_<таблица>_<hash8>`

Открытый Liquibase не умеет сделать CHECK отдельным именованным изменением. Варианты:

| Вариант | Почему отвергнут или принят |
|---------|-----------------------------|
| `checkConstraint` у колонки в `createTable` | Работает только при создании таблицы, у ограничения нет имени, отдельно его не удалить |
| `addCheckConstraint` | Есть только в Liquibase Pro |
| `sql` с явным `rollback` | **Принят**: отдельный changeset на ограничение, как у `unique`, имя вычисляется из содержимого |

Вид changeset:

```yaml
- changeSet:
    id: 20261029-120000-03
    author: forge
    logicalFilePath: db/changelog/20261029-120000.yaml
    changes:
      - sql:
          sql: "ALTER TABLE event ADD CONSTRAINT ck_event_1a2b3c4d CHECK (source IN ('collector', 'manual'))"
    rollback:
      - sql:
          sql: "ALTER TABLE event DROP CONSTRAINT ck_event_1a2b3c4d"
```

Детали:

- Хеш строится по таблице, колонке и отсортированным значениям в каноническом виде, например
  JSON отсортированного списка. Поэтому порядок значений на имя не влияет, а смена перечня даёт
  новое имя.
- Строковые значения пишутся литералами SQL с удвоенными кавычками, целые — числами.
- Удаление перечня — тот же `sql` с `DROP CONSTRAINT` и откатом `ADD CONSTRAINT` по принятой модели.
- В разнице моделей появляются изменения `AddCheck` и `DropCheck`. Группы стоят так:
  `DropCheck` — после `DropUnique`, `AddCheck` — после `AddUnique`.
- Откат `DropTable` восстанавливает перечни таблицы так же, как её наборы уникальности.
- Ответ `forge generate` называет новые виды `add_check` и `drop_check` с именем ограничения
  в `constraint`. В отличие от других видов ограничений, у них заполнено и поле `column`:
  перечень принадлежит одной колонке. Это допущение изменения; оно отражается
  в `docs/migration.md`.

### Р8. Сводка changelog распознаёт только собственную форму `sql`

Сводка читает таблицу и имя ограничения из `sql`-изменения строгим разбором двух форм, которые
пишет сам forge: `ALTER TABLE <т> ADD CONSTRAINT ck_… CHECK (…)` и `ALTER TABLE <т> DROP CONSTRAINT
ck_…`. Любой другой `sql` даёт `ChangelogUnreadableError`: changelog forge вручную не правится.

`ConstraintRef` получает вид `check`. Реализация `constraint_exists` отображает вид `check` на тип
ограничения `c`. Так проверки `check_absent` и `check_present` появляются в откате без отдельного
механизма.

Changelog данных `sql` не использует, поэтому разбор строк seed (`_rows`) не затрагивается.

### Р9. Эволюция модели

| Изменение | Решение |
|-----------|---------|
| Добавить, убрать, изменить `check` | `DropCheck` и `AddCheck` по содержимому |
| Новая колонка с `check` в существующей таблице | `AddColumn`, затем `AddCheck` |
| Новая колонка с `generated` в существующей таблице | `AddColumn` с identity: PostgreSQL заполнит существующие строки |
| Включить или выключить `generated` у существующей колонки | `UnsupportedChange` `column_generated_changed` |
| Новая таблица с `generated` и `check` | `CreateTable` с identity, затем `AddCheck` |

При включении генерации у колонки, которая допускала NULL, меняется и итоговая допустимость NULL.
В перечень неподдерживаемых изменений попадает только `column_generated_changed`, без
`column_nullable_changed`: смена NULL здесь — следствие генерации, а не отдельное намерение.

Отвергнутый вариант: поддержать включение генерации через `addAutoIncrement` и сдвиг
последовательности за максимум значений. Это перенос данных, его откат не восстанавливает
прежнее состояние последовательности.

### Р10. Сверка identity по `attidentity`

Запрос колонок интроспекции получает `a.attidentity`. `ActualColumn` получает признак генерации:

| `attidentity` | Значение признака | В расхождении |
|---------------|-------------------|---------------|
| `d` | `identity` | `identity` |
| `a` | `identity_always` | `identity_always` |
| пусто | нет | `absent` |

`column_generated_mismatch` идёт после `column_nullable_mismatch` той же колонки.

### Р11. Сверка CHECK — переводчик определения в колонку и множество значений

Интроспекция читает ограничения `c` вместе с `conkey` и `pg_get_constraintdef`. Переводчик
в слое инфраструктуры (ACL) превращает определение в пару «колонка, множество значений», если
оно имеет одну из канонических форм PostgreSQL для `IN (…)` над типами формата:

```text
CHECK ((source = ANY (ARRAY['collector'::text, 'manual'::text])))
CHECK (((source)::text = ANY ((ARRAY['collector'::character varying, 'manual'::character varying])::text[])))
CHECK ((priority = ANY (ARRAY[1, 2, 3])))
CHECK (((source)::text = 'collector'::text))
```

Последняя форма — перечень из одного значения: PostgreSQL сворачивает `IN ('a')` в `= 'a'`.
Точные формы для `bigint` и для значений с кавычками внутри закрепляются интеграционными тестами
на PostgreSQL 17.

Сравнение идёт по содержимому: перечень модели без пары в БД даёт `check_missing`, пара в БД без
перечня в модели — `check_unexpected`. Нераспознанное определение тоже даёт `check_unexpected`,
а в фактическом значении стоит исходный текст.

Отвергнутый вариант: сверка по имени `ck_…_<hash8>`. Хеш уже несёт содержимое, но такая сверка
нарушает действующий принцип «имена ограничений не сравниваются» и не замечает правку значений
в БД с сохранением имени.

### Р12. Seed

- `forge validate-seed` проверяет значение колонки с `check` по перечню. Значение вне перечня —
  нарушение `check_violated`, и проверяется только значение, уже прошедшее проверку типа.
- Конфликты seed получают вид `check_violated_by_seed`. Код `check_violated` отображается в этот
  вид по той же схеме, что `duplicate_unique` в `unique_violated_by_seed`.
- Колонка с `generated` в seed — обычная колонка NOT NULL: значение задаётся явно (Р3).
- Сдвиг последовательности после вставок seed в изменение не входит, см. риски.

## Risks / Trade-offs

- **[Риск] Формы `pg_get_constraintdef` различаются по типам и версиям PostgreSQL.**
  → Переводчик принимает только перечисленные формы. На каждый тип формата и на перечень из
  одного значения есть интеграционный тест на PostgreSQL 17. Нераспознанная форма даёт
  расхождение, а не ошибку окружения, поэтому вердикт `failure` видно, а не тихо пропускается.
- **[Риск] Атрибуты `autoIncrement` и `generationType` ведут себя иначе в версии Liquibase образа
  kit'а.** → Интеграционный тест наката сверяет `attidentity = 'd'`. Если поведение расходится,
  это выявит тест, и решение пересматривается до слияния.
- **[Допущение] Последовательность identity-колонки таблицы seed не сдвигается после вставок
  seed.** Таблица seed принадлежит seed целиком (`forge-seed-data`), и вставки приложения в неё
  не предусмотрены. → Допущение записывается в `docs/model-format.md` в разделе «Ограничения
  и допущения».
- **[Допущение] CHECK пропускает NULL.** Колонка с `check` без `nullable: false` допускает NULL,
  как в PostgreSQL. → Это записывается в `docs/model-format.md`.
- **[Компромисс] `sql` в changelog вместо структурного изменения Liquibase.** Liquibase не может
  проверить текст, а сводка разбирает строку. → Строку пишет и читает только forge, а разбор
  строгий: неизвестная форма — ошибка чтения changelog.
- **[Компромисс] `bool` — подкласс `int` в Python.** Без явной проверки `true` прошёл бы
  в перечень `integer`. → Читатель и проверка значений отличают `bool` от `int`, и на это есть
  модульный тест.

## Migration Plan

1. Изменение аддитивно: принятые модели, changelog и seed прежних версий не требуют правок,
   а `version: 1` сохраняется.
1. Выпуск — `0.5.0` релизным сценарием с разрядом `minor` после слияния PR в `main`,
   milestone `v0.5.0`.
1. Откат выпуска — возврат к `0.4.1`. Модели с `generated` и `check` прежняя версия отклонит
   нарушением `unknown_field`, что видно до наката.
