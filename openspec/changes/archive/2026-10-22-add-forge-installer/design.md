# Design

## Context

Мотивация — в proposal.md, требования — в `specs/forge-delivery/spec.md`. Текущее устройство:

- Шаг 1 `README.md` перечисляет пути для копирования, а раздел «Отличия от поставки kit'а»
  `CONTRIBUTING.md` — правки четырёх файлов kit'а. Сейчас эти правки вписаны в файлы без маркеров.
- `tools/host-runner/runner.py` держит белый список в литерале
  `ALLOWED_TARGETS = frozenset({ ... })` и выполняет только `make <target>` без аргументов.
  Сервер однопоточный.
- CLI `forge` работает в контейнере агента. Навык и `docs/operation.md` вызывают его как
  `uv run forge …`, а Liquibase он запускает через раннер (`runner_gateway.py`).
- Установщик kit'а перезаписывает свои файлы целиком и хранит суммы в `.sdd-kit-manifest.json`.
- На хосте уже нужен `python3` из stdlib: на нём работают раннер и шлюз.

## Goals / Non-Goals

**Goals:**

- Один источник истины для состава поставки и текстов блоков: `README.md` и `CONTRIBUTING.md`
  их не повторяют, а репозиторий forge сам несёт те же блоки, что ставит в проект.
- Установщик проверяется тестами без сети.

**Non-Goals:**

- Запуск CLI через раннер. Он отвергнут: раннер не передаёт аргументы, а вложенный вызов раннера
  из `forge apply` и `forge rollback` упирался бы в однопоточный сервер.
- Слияние правок владельца внутри блока. Блок заменяется целиком, правка внутри него только
  выявляется и подтверждается.
- Windows без POSIX-оболочки.

## Decisions

### Установщик — POSIX sh с узким набором утилит

`install.sh` использует `sh`, `curl`, `tar`, `mktemp`, `sed`, `awk` и `sha256sum` либо
`shasum -a 256`. JSON двух манифестов читается и пишется построчно: формат манифеста forge
задаёт сам установщик (одна запись на строку, как в манифесте kit'а), а из манифеста kit'а нужно
только поле `kit_version`. Так установщику не нужны `jq` и Python, и его можно запустить
через `curl … | sh`.

Альтернатива — Python-скрипт: проще работать с JSON, но потеряна форма `curl | sh` по образцу
kit'а. Отвергнута.

### Источник и версия

Архив берётся как `https://codeload.github.com/<owner>/<repo>/tar.gz/<ref>` и распаковывается
во временный каталог, который удаляется при выходе (`trap`). Без `--ref` тег берётся из
`https://api.github.com/repos/<owner>/<repo>/releases/latest` — это последний опубликованный
релиз, сортировать теги в sh не нужно. `--source` указывает на распакованное дерево
напрямую. Остальная логика от источника не зависит: дальше установщик работает с каталогом
поставки.

### Перечень `delivery.txt`

Строки — `источник` или `источник -> цель`; пустые строки и строки с `#` пропускаются. Каталог
копируется рекурсивно. Файлы, которых нет в новой версии, но которые записаны в манифесте прежней
установки, установщик не удаляет: удаление вне объёма. План перечисляет их как «больше не
поставляются». Тест в `tests/` проверяет, что каждый источник существует и что цели не
пересекаются.

### Фрагменты блоков и места вставки

Тексты блоков лежат в `install/blocks/`: `Makefile`, `env.example`, `docker-compose.yml`,
`runner.py`, `gitignore`. Каталог `install/` в поставку не входит, его читает только установщик.
Место вставки отсутствующего блока задано для каждого файла:

| Файл | Место вставки |
|------|---------------|
| `Makefile`, `.env.example`, `.gitignore` | Конец файла |
| `docker-compose.yml` | Если вне маркеров есть корневой ключ `include:`, блок с одним элементом списка ставится сразу после него. Иначе блок вместе со строкой `include:` ставится перед корневым `services:` |
| `tools/host-runner/runner.py` | Перед закрывающей `}` литерала множества, который открывает строка `ALLOWED_TARGETS = frozenset(` |

Не найден якорь, например `services:` или `ALLOWED_TARGETS = frozenset(`, — это код `1`.
Отступ блока в `runner.py` и `docker-compose.yml` задан самим фрагментом.

В репозитории forge отличия в этих файлах обрамляются теми же маркерами. Тест сравнивает текст
между маркерами с фрагментами из `install/blocks/`, поэтому расхождение ловится в CI, а не
в проекте пользователя. Блок `.gitignore` проекта отличается от `.gitignore` репозитория
разработки: в него входят только `.forge/` и `tools/forge/.venv/`. Принятое состояние `db/`
и след `backlog/` в проекте коммитятся.

### Манифест и выявление правок

`.forge-manifest.json`:

```json
{
  "forge_version": "0.2.0",
  "forge_ref": "v0.2.0",
  "installed_at": "2026-10-22T10:00:00Z",
  "files": [
    {"path": "tools/forge/pyproject.toml", "sha256": "…"}
  ],
  "blocks": [
    {"path": "Makefile", "sha256": "…"}
  ]
}
```

`forge_version` берётся из `project.version` поставляемого `pyproject.toml`; при `--source` вместо
`forge_ref` записывается `"local"`. Сумма блока считается по строкам между маркерами без самих
маркеров. Правка владельца — это расхождение текущей суммы с манифестом. При первой установке
манифеста нет, и существующий файл по пути поставки тоже считается правкой: он требует
подтверждения. Манифест коммитится владельцем вместе с поставкой.

### Порядок работы и атомарность

Сначала выполняются все проверки и строится план, без записи. Затем, если нужно, запрашивается
подтверждение. Только после этого идёт запись: файлы поставки, затем блоки, затем манифест.
Подтверждение читается из `/dev/tty`, поэтому `curl | sh` не забирает ответ из stdin. Без
терминала и без `--yes` правка владельца считается отказом и даёт код `1`.

Если блок в каком-то файле не вставляется, это выясняется на шаге плана, и тогда не пишется
ничего. Частичной установки из-за неузнанного файла нет.

### Обёртка запуска CLI

`tools/forge-env/forge.sh`:

```sh
if [ -f tools/forge/pyproject.toml ]; then
  exec uv run --project tools/forge --frozen --no-dev forge "$@"
fi
exec uv run forge "$@"
```

`exec` сохраняет stdout и код возврата. `--project` оставляет рабочий каталог корнем проекта,
поэтому `backlog/`, `.forge/` и `FORGE_ACCEPTED_DIR` разрешаются как прежде. Навык `forge`
и `docs/operation.md` переходят на `sh tools/forge-env/forge.sh …`. Шаблоны беклогов
по-прежнему называют команды `forge …`, а правило навыка переводит их в вызов обёртки.

### Тесты

Тесты установщика — pytest, вызывающий `sh install.sh --source <корень репозитория>` во временном
каталоге с поддельным `.sdd-kit-manifest.json` и минимальными копиями пяти файлов kit'а.
Проверяются сценарии спецификации, кроме сетевых. Сетевой путь (`--ref`, `releases/latest`)
проверяется ручным прогоном при релизе `v0.2.0`.

## Risks / Trade-offs

- [Владелец переписал литерал `ALLOWED_TARGETS` иначе] → код `1` с печатью блока; ручная вставка
  описана в шаге 1 `README.md`.
- [Нет `releases/latest`, а есть только тег] → установщик сообщает об этом кодом `2`
  и предлагает `--ref`; релизный сценарий публикует релиз.
- [Лимит анонимных запросов GitHub API] → нужен один запрос за установку; с `--ref` API
  не вызывается.
- [Правки forge внутри блока при переустановке kit'а] → установщик kit'а затирает файл,
  установщик forge восстанавливает блок; правки владельца вне маркеров теряет установщик kit'а,
  а не forge. Это поведение kit'а, вне объёма.
- [Разный `sha256` в Linux и macOS] → установщик выбирает `sha256sum` или `shasum -a 256`;
  если нет ни того, ни другого, это код `2`.

## Migration Plan

Ручных проектов с forge, кроме проекта разработки, нет. Владелец такого проекта запускает
установщик `v0.2.0`. Существующие файлы поставки и неотмеченные правки forge в файлах kit'а
попадают в план: файлы перезаписываются после подтверждения, а правки forge без маркеров
владелец удаляет вручную по подсказке плана. Шаг 1 `README.md` называет это явно. Откат —
вернуть файлы из git.

## Open Questions

- Нужен ли `install.sh` в релизных артефактах GitHub помимо исходников тега. Это решается
  при публикации `v0.2.0`, спецификации не меняет.
