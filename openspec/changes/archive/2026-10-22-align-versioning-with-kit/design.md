# Design

## Context

Мотивация — в proposal.md, требования — в `specs/forge-release/spec.md` и
`specs/forge-delivery/spec.md`. Текущее устройство:

- Номер `0.1.0` записан в `[project].version` файла `pyproject.toml` и повторён в `uv.lock`
  у пакета `liquibase-forge`. Сборку выполняет hatchling.
- Установщик `install.sh` читает `forge_version` регулярным выражением из `pyproject.toml`
  источника. `delivery.txt` поставляет в `tools/forge/` файлы `src/forge`, `pyproject.toml`
  и `uv.lock`.
- Бейдж версии `README.md` читает `$.project.version` из `pyproject.toml` ветки `main`
  через `shields.io` `dynamic/toml`.
- Каталога `.github/` в репозитории нет, релизного сценария тоже нет.
- Правило GIT-021 уже есть в `rules/git-rules.md`, поставке kit'а: машинный релизный коммит
  меняет один файл версии и озаглавлен `Релиз vX.Y.Z`.

Образец — `.github/workflows/release.yml`, `VERSION` и бейдж версии репозитория
`united-software-platform/sdd-developer-kit`.

## Goals / Non-Goals

**Goals:**

- Устройство релизного сценария и носителя номера совпадает с kit'ом. Отличия перечислены явно
  и обоснованы.
- Логика повышения номера проверяется тестами без GitHub.

**Non-Goals:**

- Запуск тестов и линтеров в релизном сценарии: в kit'е их нет, и CI проверок — отдельная задача.
- Изменение установщика сверх источника номера. Поиск последней версии через `releases/latest`
  остаётся прежним.
- Changelog выпуска в репозитории. Описание релиза GitHub собирает из коммитов сам.

## Decisions

### Номер — в `VERSION`, `pyproject.toml` читает его через hatchling

В `pyproject.toml` поле `version` заменяется на `dynamic = ["version"]`, а секция
`[tool.hatch.version]` указывает `path = "VERSION"` и шаблон `(?P<version>\d+\.\d+\.\d+)`.
Шаблон нужен потому, что по умолчанию hatchling ищет в файле присваивание `__version__`.

Пробный прогон на копии проекта подтвердил поведение uv:

- `uv lock` пишет `Updated liquibase-forge v0.1.0 -> (dynamic)`, и запись пакета в `uv.lock`
  остаётся без поля `version`;
- после смены `VERSION` команда `uv lock --check` проходит;
- `uv run --frozen` собирает пакет с новым номером.

Значит, релизный коммит меняет один файл, как требует GIT-021.

Альтернатива — оставить номер в `pyproject.toml` и править его в сценарии. Тогда сценарий должен
ещё и перегенерировать `uv.lock`, а коммит менял бы два файла и выпадал из GIT-021. Отвергнута.

### `VERSION` поставляется в `tools/forge/VERSION`

hatchling ищет `path` относительно `pyproject.toml`. В целевом проекте `pyproject.toml` лежит
в `tools/forge/`, поэтому `delivery.txt` получает строку `VERSION -> tools/forge/VERSION`.
Без неё обёртка `tools/forge-env/forge.sh` в установленном проекте не соберёт CLI.

### Установщик читает номер из `VERSION`

`forge_version` берётся из первой строки `$src/VERSION` и сверяется с шаблоном
`МАЖОР.МИНОР.ПАТЧ`. Если файла нет или номер неразборчив, установщик завершается кодом `1`,
как при повреждённой поставке. Проверка стоит после проверки `delivery.txt`, поэтому версия
без установщика по-прежнему даёт сообщение о `delivery.txt`.

### Релизный сценарий повторяет kit'овский

`.github/workflows/release.yml` переносится из kit'а с тем же составом шагов:

1. `workflow_dispatch` с вводом `bump` из `patch`, `minor`, `major`.
1. Разбор `VERSION` строго как `МАЖОР.МИНОР.ПАТЧ`. Ввод передаётся через `env`,
   а не подстановкой `${{ }}` в текст скрипта.
1. Гейт GIT-020 по `VERSION`.
1. Запись номера, коммит `Релиз vX.Y.Z` от `github-actions[bot]` с телом
   `Версия повышена: X -> Y.`, аннотированный тег, `git push origin HEAD` и push тега.

Комментарии сценария объясняют основание каждого шага так же, как в kit'е.

### Отличия от kit'а

- **Нет шага сборки образа.** Образа у forge нет, а значит, не нужно и право `actions: write`.
  У сценария остаётся только `contents: write`.
- **Добавлен шаг `gh release create "v$NEXT" --verify-tag --title "v$NEXT" --generate-notes`.**
  Установщик forge без `--ref` ищет версию через `releases/latest`. Kit этого шага не делает:
  его установщик по умолчанию берёт `main`.
- **Добавлен первый шаг-гейт: сценарий выпускает только из `main`.** Ручной запуск позволяет
  выбрать любую ветку, и `git push origin HEAD` опубликовал бы релизный коммит в неё.
  Спецификация требует коммит в `main`. Гейт завершает прогон ошибкой, а не пропускает задание
  молча: так запуск не из той ветки виден в статусе.

### Логика повышения проверяется на тексте сценария

Тест читает `release.yml`, берёт скрипт шага разбора версии и исполняет его через `sh`
с временными `VERSION` и `GITHUB_OUTPUT` и с разными значениями `BUMP`. Так проверяется ровно тот
код, что работает в GitHub, без выноса его в отдельный файл, которого нет у kit'а. Структура
сценария — только ручной запуск, варианты разряда, права — проверяется разбором YAML.

### Бейдж версии — как у kit'а

URL бейджа меняется на `img.shields.io/badge/dynamic/regex` с адресом
`raw.githubusercontent.com/.../main/VERSION`, `search=([\d.]+)` и `replace=v$1`.
Цель ссылки — `./VERSION`. В карте бейджей `CONTRIBUTING.md` источник значения становится
«`VERSION` в ветке `main`», режим — `dynamic/regex`.

## Risks / Trade-offs

- [Защита ветки `main` запрещает push от `github-actions[bot]`] → в разделе «Выпуск версии»
  `CONTRIBUTING.md` указано, что боту нужно право push в `main`. Если защита включится позже,
  сценарий упадёт на push до создания релиза, и тег не повиснет без коммита: тег публикуется
  после коммита.
- [Сценарий запущен до слияния в `main`] → GitHub не показывает ручной запуск, пока файла
  сценария нет в ветке по умолчанию. Это задаёт порядок выпуска `v0.2.0`.
- [Release создан, а тег — нет, или наоборот] → `--verify-tag` не даёт создать релиз без тега.
  Если шаг релиза упал после push тега, релиз доводится повторным
  `gh release create vX.Y.Z --verify-tag` вручную. Повторный запуск сценария выпустил бы
  следующую версию, и это сказано в `CONTRIBUTING.md`.
- [Выпуск без проверок] → как и у kit'а, релиз опирается на локальные проверки перед слиянием
  в `main`.

## Migration Plan

1. Реализовать изменение в ветке `release/v0.2.0`. `VERSION` создаётся со значением `0.1.0`:
   номер повышает только сценарий.
1. Слить `release/v0.2.0` в `main`.
1. Запустить сценарий `release` с разрядом `minor`: коммит `Релиз v0.2.0`, тег `v0.2.0`, Release.
1. Вручную проверить сетевую установку из `add-forge-installer`:
   `curl … | sh -s -- --ref v0.2.0` и запуск без `--ref`.

Откат: удалить Release и тег `v0.2.0` и откатить релизный коммит в `main`. Файлы изменения
откатываются обычным revert.
