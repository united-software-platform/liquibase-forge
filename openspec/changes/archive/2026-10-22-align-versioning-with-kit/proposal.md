# Proposal

## Why

Номер версии forge записан в двух местах: в `pyproject.toml` и в `uv.lock`. Меняется он вручную,
и тег с GitHub Release никак с ним не связаны. Ветка `release/v0.2.0` уже существует, а номер
по-прежнему `0.1.0`. Установщик forge без `--ref` ищет последнюю версию через `releases/latest`,
но ни одного релиза нет, поэтому установка без ключей заканчивается кодом `2`. Задача GitHub #5
(LBFR-017) просит выпускать версии так же, как SDD Developer Kit: из одного носителя и одним
ручным запуском GitHub Action.

## What Changes

- Единственный носитель номера — файл `VERSION` в корне репозитория. `pyproject.toml` берёт версию
  динамически из `VERSION` через hatchling, и `uv.lock` перестаёт хранить номер проекта.
- Новый GitHub Action `.github/workflows/release.yml` повторяет устройство релизного сценария kit'а.
  Он запускается только вручную, и его единственный ввод — разряд `patch`, `minor` или `major`.
  Сценарий разбирает `VERSION` как `МАЖОР.МИНОР.ПАТЧ`, записывает новый номер, создаёт машинный
  коммит `Релиз vX.Y.Z` по GIT-021, ставит аннотированный тег `vX.Y.Z` и публикует коммит и тег.
- От kit'а сценарий отличается двумя шагами. Сборки образа в нём нет. Есть публикация
  GitHub Release по новому тегу: без неё установщик forge без `--ref` не найдёт версию.
- Установщик берёт `forge_version` из `VERSION` источника. `delivery.txt` поставляет `VERSION`
  в `tools/forge/VERSION`: без этого файла `tools/forge/pyproject.toml` в целевом проекте
  не соберётся.
- Бейдж версии в `README.md` читает `VERSION` через `shields.io` `dynamic/regex`, как бейдж kit'а.
  Карта бейджей в `CONTRIBUTING.md` обновляется той же правкой.
- В `CONTRIBUTING.md` появляется раздел «Выпуск версии»: запуск сценария `release` и выбор разряда.
- Первый выпуск `v0.2.0` делается запуском сценария с разрядом `minor` после слияния
  `release/v0.2.0` в `main`, без ручной правки номера.
- Вне объёма: прогон тестов в релизном сценарии и отдельный CI проверок. В kit'е их тоже нет,
  выпуск по-прежнему опирается на локальные проверки по `CONTRIBUTING.md`.

## Capabilities

### New Capabilities

- `forge-release`: выпуск версии Liquibase Forge — носитель номера, ручной релизный сценарий
  с вводом разряда, релизный коммит, тег и GitHub Release, согласованность номера во всех местах,
  где он читается.

### Modified Capabilities

- `forge-delivery`: состав кода CLI в поставке дополняется файлом `VERSION`, а номер версии
  в манифесте установки берётся из `VERSION` источника.

## Impact

- Новые файлы: `VERSION`, `.github/workflows/release.yml`, тесты носителя номера.
- Правки: `pyproject.toml` (динамическая версия), `uv.lock` (без номера проекта), `install.sh`
  (источник номера), `delivery.txt`, `README.md` (бейдж), `CONTRIBUTING.md` (раздел «Выпуск
  версии», карта бейджей, устройство репозитория) и тесты поставки.
- Репозиторий на GitHub: сценарию `release` нужно право `contents: write`, а `main` должна принимать
  push от `github-actions[bot]`. Сценарий запускается только из `main`: GitHub показывает ручной
  запуск, только когда файл сценария лежит в ветке по умолчанию.
- Порядок выпуска `v0.2.0`: слить `release/v0.2.0` в `main`, запустить `release` с `minor`,
  затем вручную проверить сетевую установку `install.sh`.
