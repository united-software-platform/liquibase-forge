# Proposal

## Why

Формат модели данных — последнее открытое решение `BUSINESS-REQUIREMENTS.md`, и от него зависят
все следующие шаги: `forge generate` строит changelog из модели, `forge reconcile` сверяет с ней
фактическую схему. Беклог попытки уже предписывает агенту проверить модель командой
`forge validate --model <путь>`, но ни формата, ни команды пока нет. Change 1 первой поставки
(LBFR-006) фиксирует формат первого среза ядра и даёт агенту проверку модели до наката.

## What Changes

- Формат `model.yaml` версии `1`, независимый от PostgreSQL (решения интервью Q4, Q14–Q17, Q19):
  - корень — `version: 1` и список `tables`;
  - таблица — `name`, список `columns` и упорядоченный `primary_key`;
  - колонка — `name`, `type`, необязательный `nullable` (по умолчанию `true`) и параметры типа;
  - типы `integer`, `bigint`, `boolean`, `string` с `length`, `text`, `decimal` с `precision`
    и `scale`, `date`, `timestamp`, `timestamp_tz`, `uuid`;
  - таблиц сколько угодно, связей между ними нет, схема только `public`;
  - идентификаторы по шаблону `^[a-z][a-z0-9_]{0,62}$` без зарезервированных слов.
- Доменная модель контекста Моделирование: агрегат «модель данных», таблица, колонка, тип,
  первичный ключ, идентификатор. Инварианты проверяют конструкторы и фабрика (DDD-014, DDD-023).
- Разборщик YAML в инфраструктуре: строгая структура, запрет неизвестных полей и повторных
  ключей, пути нарушений вида `tables[0].columns[1].length` (Q31).
- Команда `forge validate --model <путь>`: один JSON-объект со всеми найденными нарушениями,
  код `0` для корректной модели, `1` при нарушениях, `2` если файл не прочитать.
- Документация:
  - новый `docs/model-format.md`: синтаксис, типы и их отображение в PostgreSQL, правила проверки,
    коды нарушений (Q43);
  - в `docs/domain.md` раздел «Ядро модели данных» получает резюме и ссылку вместо открытого
    решения;
  - в `BUSINESS-REQUIREMENTS.md` открытое решение о формате закрывается ссылкой.
- Уточнения сверх решений интервью вынесены в design.md: имя таблицы не длиннее 60 символов,
  чтобы имя PK `pk_<таблица>` (Q27) укладывалось в 63 символа; запрет имён служебных колонок
  PostgreSQL и таблиц журнала Liquibase.

## Capabilities

### New Capabilities

- `forge-data-model`: формат файла модели данных Liquibase Forge и его проверка командой
  `forge validate` — состав полей, типы, правила идентификаторов, первичный ключ, допустимость NULL,
  перечень нарушений и коды возврата.

### Modified Capabilities

Нет. Требования `forge-operation` и `forge-liquibase-gateway` не меняются: беклог попытки уже
вызывает `forge validate --model`, этот change только реализует команду.

## Impact

- **Код:**
  - `src/forge/modeling/` — домен, сценарий проверки, разборщик YAML;
  - `src/forge/cli/main.py` — регистрация команды `validate`.
- **Тесты:** модульные тесты домена, разборщика, сценария и команды; примеры моделей
  в `tests/fixtures/model/`. Интеграционных тестов с БД change не добавляет.
- **Зависимости:** новых нет, используется уже подключённый `PyYAML` (`safe_load` с собственным
  загрузчиком, запрещающим повторные ключи).
- **Документы:** `docs/model-format.md` (новый), `docs/domain.md`, `BUSINESS-REQUIREMENTS.md`.
- **Вне объёма:**
  - отображение типов в PostgreSQL как код — change 2 `forge-migration` и change 3
    `forge-reconciliation`, здесь оно только документируется;
  - пустая принятая модель при отсутствии `db/model.yaml` (Q38) — change 2;
  - FK и уникальность — следующая поставка.
