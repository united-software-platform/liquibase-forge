# Design

## Context

Мотивация — в proposal.md, требования — в `specs/forge-data-model/spec.md`.

Исходное состояние:

- каркас пакета `src/forge/` создан change 0: в модуле `modeling` пустые слои `domain`,
  `application`, `infrastructure`;
- общий слой `cli` даёт `ExitCode`, `emit` и `error_payload`, а `build_parser()` пока
  не регистрирует ни одной команды;
- `PyYAML` 6.0.3 уже в зависимостях, `pydantic` и `jsonschema` в проект не входят (Q31);
- беклог попытки вызывает `forge validate --model {{trail}}/model.yaml` и при нарушениях правит
  модель, пока код возврата не станет `0`.

Ограничения: CLAR-001..023, CQRS, DDD-012..014 и DDD-023, `mypy --strict`, `ruff`. Формат независим
от PostgreSQL по BR-008, но поддерживается только PostgreSQL, поэтому пределы значений берутся
у него.

## Goals / Non-Goals

**Goals:**

- Доменная модель первого среза ядра, которую нельзя построить в некорректном состоянии
  и которую change 2 и 3 используют как эталон.
- Проверка, которая за один вызов сообщает все нарушения с путями, достаточными агенту для правки.
- Детерминированный вывод: одна и та же модель даёт один и тот же JSON.

**Non-Goals:**

- Номера строк YAML у нарушений: путь вида `tables[0].columns[1].length` агенту достаточен,
  строка и столбец указываются только у синтаксической ошибки.
- Каноническая запись модели обратно в YAML: `forge close` в change 4 копирует файл попытки
  без перезаписи.
- Отображение типов в PostgreSQL как код: в этом change оно только документируется.
- Чтение модели из `db/model.yaml` при её отсутствии (Q38) — change 2.

## Decisions

### Состав модуля `modeling` по слоям

| Слой | Компонент | Роль |
|------|-----------|------|
| Домен | `Identifier` | Объект-значение имени: шаблон, длина, зарезервированные слова |
| Домен | `ColumnType` и перечисление `TypeKind` | Объект-значение типа с параметрами `length`, `precision`, `scale` |
| Домен | `Column` | Объект-значение: имя, тип, допустимость NULL |
| Домен | `PrimaryKey` | Объект-значение: упорядоченный непустой список имён колонок без повторов |
| Домен | `Table` | Сущность с идентичностью по имени: колонки, PK, инварианты таблицы |
| Домен | `DataModel` | Корень агрегата: таблицы, уникальность их имён |
| Домен | `Violation`, `ModelViolationError` | Нарушение (путь, код, сообщение) и исключение со списком нарушений |
| Домен | `DataModelDraft`, `TableDraft`, `ColumnDraft` | Черновик модели: значения нужного вида, ещё не проверенные инвариантами |
| Домен | `DataModelFactory` | Строит `DataModel` из черновика или бросает `ModelViolationError` со всеми нарушениями |
| Приложение | `ModelDraftReaderInterface`, `DraftReading` | Контракт чтения черновика из файла и его результат: черновик и структурные нарушения |
| Приложение | `ValidateModelUseCase` с `Input` и `Output` | Сценарий проверки модели |
| Инфраструктура | `YamlModelDraftReader` | Разбор YAML и проверка структуры |
| `cli` | команда `validate` | Разбор аргументов, вызов сценария, JSON и код возврата |

Контракт чтения объявлен в слое приложения, а не в домене: его реализация обращается к файловой
системе (CLAR-006). Сценарий сначала получает черновик, затем вызывает фабрику: порядок шагов
принадлежит приложению, смысл проверок — домену (CLAR-013).

Альтернатива — разборщик сам вызывает фабрику и возвращает готовую модель. Отклонена: тогда
инфраструктура решает, когда проверять инварианты, и сценарий не может объединить два вида
нарушений.

### Два уровня проверки и черновик модели

Разборщик проверяет вид значений: отображение, список, строка, целое число, логическое значение,
состав полей, повторные ключи, версию. Результат — черновик, в котором значения уже нужного вида,
но инварианты не проверены. Фабрика проверяет смысл: идентификаторы, типы и их параметры,
уникальность имён, первичный ключ, `nullable` у колонок ключа.

Черновик живёт в домене: это входные данные фабрики в терминах домена, без следов YAML. Каждый
`TableDraft` хранит позицию таблицы в файле, чтобы фабрика строила пути `tables[N]…`.
`ColumnDraft.nullable` имеет три состояния (`True`, `False`, не задано): иначе нельзя отличить
явное `nullable: true` у колонки ключа от умолчания.

Таблица с любым структурным нарушением, включая нарушения её колонок, в черновик не попадает.
Без полного состава колонок инварианты ключа проверить нельзя. Остальные таблицы проверяются
полностью, поэтому нарушения разных таблиц приходят в одном ответе. Нарушение корня (не
отображение, нет `tables`, неподдерживаемая версия) останавливает проверку на корне.

Альтернатива — проверять сначала всю структуру, а инварианты только при её отсутствии.
Отклонена: агенту понадобился бы лишний круг правки на каждую таблицу.

### Сбор всех нарушений при неизменяемых объектах-значениях

DDD-014 требует, чтобы некорректный объект не создавался, а Q31 — чтобы нарушения возвращались
все сразу. Оба требования совмещаются так:

- конструктор объекта-значения проверяет свои инварианты и при нарушении бросает
  `ModelViolationError` со всеми своими нарушениями и путями относительно себя (`length`, `scale`);
- `Table` проверяет инварианты таблицы целиком: уникальность колонок, ссылки ключа, повторы
  в ключе, `nullable: true` у колонок ключа — и тоже сообщает все сразу (`columns[2].name`,
  `primary_key[1]`);
- фабрика строит объекты снизу вверх, ловит исключения, дописывает к путям префикс уровня
  и продолжает со следующим элементом. Колонка строится, только если её имя и тип корректны;
  таблица — только если корректны все её колонки;
- уникальность имён таблиц фабрика проверяет по всем таблицам с корректным именем, даже если
  в остальном таблица некорректна, а конструктор `DataModel` повторяет эту проверку как инвариант.

Порядок нарушений: сначала структурные в порядке документа, затем нарушения инвариантов по таблицам
в порядке документа. Внутри таблицы порядок устойчивый, но не строго документный: повтор имени
таблицы, имя таблицы, колонки, первичный ключ, повторы колонок, ссылки ключа, `nullable` у колонок
ключа. Повторный прогон даёт тот же список.

### Строгий разбор YAML через дерево узлов

Стандартный `safe_load` молча берёт последнее значение повторного ключа. Разборщик поэтому
получает дерево узлов загрузчиком `SafeLoader` (`get_single_node`) и обходит его сам: у отображения
проверяет повторы ключей, а скаляры превращает в значения штатным конструктором загрузчика.
Путь нарушения строится по ходу обхода. Синтаксическая ошибка (`MarkedYAMLError`) превращается
в одно нарушение `yaml_syntax` с пустым путём (весь документ), строкой и столбцом в сообщении.

Следствия, фиксируемые в `docs/model-format.md`:

- ключ слияния `<<` не поддерживается и считается неизвестным полем;
- несколько документов в файле — синтаксическая ошибка;
- значения `yes`, `no`, `on`, `off` YAML 1.1 читает как логические. Колонка с именем `no` даёт
  нарушение вида значения, имя нужно взять в кавычки.

Альтернатива — подкласс загрузчика с переопределённым `construct_mapping`. Отклонена: он видит
повтор, но не знает логического пути `tables[0].columns[1]`.

### Коды нарушений

| Код | Уровень | Когда |
|-----|---------|-------|
| `yaml_syntax` | структура | Файл не разбирается как YAML или содержит несколько документов |
| `duplicate_key` | структура | Ключ повторён в одном отображении |
| `missing_field` | структура | Нет обязательного поля |
| `unknown_field` | структура | Поле не входит в формат |
| `wrong_kind` | структура | Значение не того вида: например, строка вместо списка или логическое вместо числа |
| `unsupported_version` | структура | `version` не равно целому `1` |
| `invalid_identifier` | домен | Имя не соответствует шаблону или длиннее предела |
| `reserved_identifier` | домен | Зарезервированное слово PostgreSQL, системная колонка или таблица журнала Liquibase |
| `duplicate_name` | домен | Повтор имени таблицы в модели или колонки в таблице |
| `empty_columns` | домен | У таблицы нет колонок |
| `unknown_type` | домен | Тип вне перечня |
| `missing_type_parameter` | домен | Нет обязательного параметра типа |
| `unexpected_type_parameter` | домен | Параметр не относится к типу |
| `type_parameter_out_of_range` | домен | Значение параметра вне допустимого диапазона |
| `empty_primary_key` | домен | `primary_key` пуст |
| `primary_key_unknown_column` | домен | Ключ ссылается на отсутствующую колонку |
| `primary_key_duplicate_column` | домен | Колонка повторена в ключе |
| `primary_key_nullable` | домен | У колонки ключа явное `nullable: true` |

Коды — часть контракта команды: агент и тесты опираются на них, сообщения могут меняться.

### Пределы, взятые у PostgreSQL

- `string.length` — от 1 до 10485760, предел `varchar(n)`.
- `decimal.precision` — от 1 до 1000, `scale` — от 0 до `precision`. Отрицательный масштаб
  PostgreSQL 15+ формат не допускает.
- Имя колонки — до 63 символов по шаблону Q19. Имя таблицы — до 60 символов: change 2 называет
  первичный ключ `pk_<таблица>` (Q27), и PostgreSQL молча усёк бы имя длиннее 63 символов, после
  чего сверка не нашла бы ограничение.

Без этих пределов `forge validate` пропустил бы модель, на которой накат падает. Это стоило бы
агенту попытки вместо одного круга правки.

### Зарезервированные имена

- **Ключевые слова.** Перечень снимается с сервера `lbfr-db-test` запросом
  `SELECT word FROM pg_get_keywords() WHERE catcode IN ('R', 'T')` и хранится константой в домене.
  Это зарезервированные слова и слова, допустимые только как имя функции или типа: без кавычек
  ни таблицу, ни колонку так не назвать.
- **Расхождение с сервером.** Интеграционный тест сравнивает константу с ответом сервера
  и падает при расхождении, например после смены `LBFR_POSTGRES_IMAGE`.
- **Системные колонки** `tableoid`, `xmin`, `cmin`, `xmax`, `cmax`, `ctid` запрещены как имена колонок.
- **Таблицы журнала Liquibase** `databasechangelog` и `databasechangeloglock` запрещены как имена
  таблиц: сверка их исключает (Q28).

Альтернатива — перечень из документации PostgreSQL вручную. Отклонена: ручной перечень молча
устаревает.

### Команда `forge validate`

- Аргумент `--model` обязателен, путь печатается в ответе так, как передан.
- Ответ — `{"model": <путь>, "valid": <bool>, "violations": [{"path", "code", "message"}]}`.
- Код `0` — нарушений нет, `1` — есть нарушения.
- Код `2` — файл не прочитать: нет файла, каталог, нет прав, не UTF-8. Ответ тогда
  `error_payload("model_unreadable", …, model=<путь>)`, а `ModelDraftReaderInterface` бросает
  для этого случая `ModelUnreadableError` слоя приложения.

Команда регистрируется модулем `forge/cli/commands/validate.py` с функциями `register(subparsers)`
и `run(args) -> int`. `main` вызывает `run` выбранной команды через `set_defaults(handler=…)`.
Так следующие change добавляют команды новым модулем, а не правкой ветвлений в `main` (CLAR-018).
Сборка зависимостей — реализация разборщика и фабрика — тоже происходит в модуле команды.

### Документация

- **`docs/model-format.md`.** Синтаксис с полным примером, перечень полей, типы с параметрами
  и отображением в PostgreSQL (таблица Q15), правила имён, первичный ключ и NULL, коды нарушений,
  ограничения YAML. Пример из документа лежит также в `tests/fixtures/model/example.yaml`,
  и тест проверяет, что пример корректен.
- **`docs/domain.md`.** Фраза об открытом решении этапа 2 в разделе «Ядро модели данных»
  заменяется ссылкой на формат; ограничение первого среза уточняется по Q17: таблиц много,
  связей нет. Версия 1.0.1.
- **`BUSINESS-REQUIREMENTS.md`.** Открытое решение переносится в закрытые со ссылкой
  на `docs/model-format.md`. Версия 0.2.1.
- **`docs/architecture.md`** не меняется: строка `forge validate` в контракте команд уже верна.

## Risks / Trade-offs

- [Структурная ошибка в таблице скрывает её нарушения инвариантов] → агенту понадобится второй
  круг правки только для этой таблицы; остальные таблицы проверены полностью.
- [Логические значения YAML 1.1 (`no`, `on`) как имена] → нарушение `wrong_kind` с подсказкой взять
  имя в кавычки; случай описан в `docs/model-format.md`.
- [Перечень ключевых слов зависит от версии PostgreSQL] → интеграционный тест сверяет константу
  с `lbfr-db-test`; без сервера тест пропускается с причиной, как остальные интеграционные.
- [Пределы PostgreSQL в формате, заявленном независимым] → пределы описаны в `docs/model-format.md`
  как ограничение первой поставки; при поддержке второй СУБД их придётся пересмотреть.
- [Имя таблицы ограничено 60 символами вместо 63 по Q19] → уточнение решения интервью, вынесенное
  в proposal.md; без него сверка change 3 расходилась бы с фактическим именем ключа.

## Migration Plan

Миграции нет: `db/model.yaml` ещё не существует, команда новая. Откат — удаление команды
и модуля, внешних потребителей у них нет.
