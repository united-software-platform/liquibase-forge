# Spec Delta

## Purpose

Состав и версия поставки SDD Developer Kit в проекте: какая версия kit'а установлена, какие файлы
она приносит, как при обновлении kit'а сохраняются проектные отличия в файлах поставки и чему
соответствует манифест установки.

## ADDED Requirements

### Requirement: Версия поставки закреплена тегом

Манифест `.sdd-kit-manifest.json` MUST фиксировать версию kit'а `1.5.0` и ссылку `v1.5.0`.
Обновление поставки SHALL выполняться установщиком kit'а с тегом или коммитом, а не с подвижной
веткой `main`: повторный запуск с той же ссылкой MUST давать тот же состав файлов.

#### Scenario: Манифест после обновления

- **WHEN** обновление поставки завершено
- **THEN** в `.sdd-kit-manifest.json` поле `kit_version` равно `1.5.0`, а поле `kit_ref` — `v1.5.0`

#### Scenario: Повторный предварительный просмотр

- **WHEN** установщик запущен с `--ref v1.5.0 --dry-run` в обновлённом проекте
- **THEN** план не содержит файлов к созданию, а в перечне перезаписи только файлы с проектными отличиями

### Requirement: Состав поставки 1.5.0 присутствует в проекте

Проект MUST содержать все файлы поставки kit'а 1.5.0, включая `rules/project-docs-rules.md`
и навык `.claude/skills/project-docs/`. `CLAUDE.md` и `AGENTS.md` SHALL подключать
`rules/project-docs-rules.md` наравне с остальными правилами набора.

#### Scenario: Новые файлы поставки

- **WHEN** обновление поставки завершено
- **THEN** в проекте есть `rules/project-docs-rules.md`, `.claude/skills/project-docs/SKILL.md` и три шаблона в `.claude/skills/project-docs/templates/`

#### Scenario: Подключение правил документов проекта

- **WHEN** агент загружает `CLAUDE.md` или `AGENTS.md`
- **THEN** перечень правил содержит ссылку на `rules/project-docs-rules.md`

### Requirement: Проектные отличия в файлах поставки сохраняются

Файл поставки с проектными отличиями MUST после обновления содержать и эти отличия, и изменения
новой версии kit'а для этого файла. Перезапись файла поставки целиком без слияния SHALL NOT
оставаться итогом обновления. Решение по каждому конфликтному файлу MUST быть зафиксировано
в артефактах изменения.

#### Scenario: Kit не менял конфликтный файл

- **WHEN** содержимое файла на стороне kit'а в версиях 1.4.3 и 1.5.0 совпадает, а проект его изменил
- **THEN** после обновления файл побайтно совпадает с проектной версией до обновления

#### Scenario: Окружение Liquibase Forge после обновления

- **WHEN** обновление поставки завершено
- **THEN** `Makefile` содержит цели `liquibase-update`, `liquibase-rollback` и `forge-env-*`, `docker-compose.yml` подключает `docker/lbfr/docker-compose.yaml`, `.env.example` содержит переменные `FORGE_*` и `LBFR_*`, а белый список `tools/host-runner/runner.py` включает цели Liquibase Forge

### Requirement: Манифест отражает содержимое kit'а, а не проекта

Контрольная сумма файла в манифесте MUST совпадать с содержимым этого файла в установленной
версии kit'а. Для файла с проектными отличиями она SHALL NOT совпадать с проектной версией:
иначе следующее обновление сочтёт файл нетронутым и перезапишет его без предупреждения.

#### Scenario: Файл с проектными отличиями

- **WHEN** контрольная сумма `Makefile` в проекте сравнивается с записью манифеста
- **THEN** они различаются, и запись манифеста равна контрольной сумме `Makefile` из kit'а 1.5.0

#### Scenario: Нетронутый файл поставки

- **WHEN** контрольная сумма `rules/git-rules.md` в проекте сравнивается с записью манифеста
- **THEN** они совпадают

### Requirement: Инструменты SDD развёрнуты после обновления

После обновления поставки skills и команды OpenSpec MUST быть развёрнуты повторно целью
`make init`. Существующие `.env`, SSH-ключ, `.ssh/config`, `openspec/config.yaml`,
`openspec/changes/` и `openspec/specs/` SHALL NOT изменяться этим шагом.

#### Scenario: Повторная подготовка проекта

- **WHEN** после обновления поставки выполнена цель `make init`
- **THEN** цель завершается с кодом `0`, а `.env`, `openspec/config.yaml` и содержимое `openspec/changes/` и `openspec/specs/` не изменены
