# Design

## Context

Мотивация — в [proposal.md](./proposal.md#why). Здесь — состояние, найденное при планировании.

Установщик kit'а (`install.sh` из репозитория `united-software-platform/sdd-developer-kit`) строит
план по манифесту: файл, чья контрольная сумма совпадает с записью манифеста, обновляется молча
(`UPDATE`), отличающийся — перезаписывается целиком после подтверждения (`CONFLICT`). Слияния
у установщика нет, это зафиксировано в «Ограничениях» его `README.md`. Манифест пишется последним
и содержит контрольные суммы файлов проекта сразу после копирования, то есть содержимого kit'а.

Сверка, выполненная при планировании: архив тега `v1.4.3` совпал с манифестом проекта по всем
18 файлам, ветка `main` kit'а несёт версию 1.5.0, тег `v1.5.0` существует. Эмуляция плана
установщика 1.5.0 на текущем проекте:

| План | Файлы |
|------|-------|
| `CREATE` | `rules/project-docs-rules.md`, `.claude/skills/project-docs/SKILL.md`, `.claude/skills/project-docs/templates/{contributing,readme,use-cases}.md` |
| `UPDATE` с изменением | `CLAUDE.md`, `AGENTS.md` — добавлено подключение `rules/project-docs-rules.md` и строка таблицы версий |
| `UPDATE` без изменения | прочие 9 файлов `rules/`, `tools/host-runner/README.md`, `tools/host-runner/call.sh`, `tools/make-lint/check.sh` |
| `CONFLICT` | `.env.example`, `Makefile`, `docker-compose.yml`, `tools/host-runner/runner.py` |

Все четыре конфликтных файла на стороне kit'а между 1.4.3 и 1.5.0 побайтно не менялись.
Проектные отличия в них — окружение Liquibase Forge:

| Файл | Проектное отличие |
|------|-------------------|
| `.env.example` | блоки переменных `FORGE_*` и `LBFR_*` |
| `Makefile` | цели `liquibase-update`, `liquibase-rollback`, `forge-env-sync`, `forge-env-check`, `forge-env-up` и их записи в `.PHONY` |
| `docker-compose.yml` | `include:` файла `docker/lbfr/docker-compose.yaml` с комментарием |
| `tools/host-runner/runner.py` | цели Liquibase Forge в `ALLOWED_TARGETS` и комментарий к ним |

В контейнере агента есть `sh`, `wget`, `tar`, `gzip`, `sha256sum` — достаточно для установщика;
`make` и `docker` есть только на хосте, цели `make` агент запускает через host-runner.

Рабочее дерево ветки `forge-operation` содержит незакоммиченные правки, не относящиеся к kit'у
(`README.md`, `docs/`, `src/`, `tests/`, `tools/liquibase/gateway.py` и другие), и незавершённое
изменение `commit-operation-trail`. Файлы, которые трогает обновление, по `git status` чисты.

## Goals / Non-Goals

**Goals:**

- Привести поставку к 1.5.0 штатным установщиком, а не ручным копированием: манифест и состав
  остаются такими, какими их ждёт следующее обновление.
- Разрешить четыре конфликта пофайловым слиянием с явно зафиксированным решением по каждому.

**Non-Goals:**

- Приведение `README.md`, `docs/` и прочих документов проекта к новым правилам `DGN-*`.
- Обновление образа окружения агента и закрепление его digest в `.env`.
- Изменение установщика kit'а, в том числе добавление в него слияния.
- Правка `docker-compose.yml` под `DOCK-004`/`DOCK-011`: файл на стороне kit'а не менялся,
  расхождение с правилами существует и до обновления.

## Decisions

### Ссылка установки — тег `v1.5.0`

Установщик запускается с `--ref v1.5.0`. Умолчание `main` установщик сам называет
невоспроизводимым во времени: ветка могла уйти вперёд между планированием и исполнением,
и сверка, на которой построено это решение, перестала бы быть верной.

Альтернатива — `main`, как в первой установке: отвергнута по той же причине.

### Источник — локальная копия архива тега, проверенная до запуска

Архив тега `v1.5.0` скачивается в scratchpad, установщик из него читается и запускается
с `--source <каталог архива> --ref v1.5.0`. `--ref` при `--source` влияет только на поле
`kit_ref` манифеста, но без него там окажется `main`.

Перед запуском контрольные суммы файлов поставки в архиве сверяются с результатом планирования:
если `v1.5.0` отличается от проверенного состава, работа останавливается до пересмотра решения.

Альтернатива — `wget -qO- …/install.sh | sh` прямо из сети: отвергнута, потому что исполнялся бы
непрочитанный скрипт, а план нельзя сверить с планированием до записи.

### Конфликт: перезапись kit'ом, затем возврат проектной версии

Установщик не умеет пропускать отдельные файлы, поэтому порядок такой:

1. Проектные версии четырёх файлов копируются в scratchpad, фиксируются их контрольные суммы.
1. Установщик запускается с `--yes` после просмотра плана `--dry-run`: файлы перезаписываются
   содержимым kit'а, манифест получает его контрольные суммы.
1. Слияние: к версии kit'а применяются проектные отличия. Поскольку kit эти файлы не менял,
   результат — проектная версия целиком; она копируется обратно из scratchpad.
1. Контрольные суммы сверяются с зафиксированными в первом шаге, `git diff` по четырём файлам пуст.

Возврат идёт копированием из scratchpad, а не `git restore` или `git checkout`: восстановление
через git запрещено без явного указания пользователя по `GIT-018`.

Альтернатива — подложить проектные версии в `--source`, чтобы установщик сам записал их: отвергнута.
Манифест получил бы контрольные суммы проектных версий, и следующее обновление сочло бы файлы
нетронутыми и перезаписало бы их без вопроса — требование «Манифест отражает содержимое kit'а»
в [спецификации](./specs/sdd-kit-delivery/spec.md) нарушилось бы.

Альтернатива — отказаться от перезаписи в ответ на вопрос установщика: отвергнута, отказ отменяет
установку целиком.

### Слияние, если kit всё же изменил конфликтный файл

Если сверка архива покажет, что какой-то из четырёх файлов в `v1.5.0` отличается от `v1.4.3`,
решение по нему принимается трёхсторонним слиянием: база — файл из архива `v1.4.3`, «их» —
из `v1.5.0`, «наше» — проектная версия. Итог и решение по каждому участку записываются в этот
раздел до продолжения работы. На момент планирования таких файлов нет.

### Развёртывание инструментов SDD — `make init` через host-runner

Установщик называет `make init` следующим шагом. В белом списке host-runner цель есть, `make`
в контейнере нет, поэтому цель вызывается через `tools/host-runner/call.sh`. Если раннер
не запущен, цель выполняет пользователь на хосте.

## Risks / Trade-offs

- [Сбой установщика посреди записи оставляет проект частично установленным] → до запуска
  сохраняются копии всех файлов поставки и манифеста в scratchpad; признак сбоя — неполный
  манифест, лечение — повторный запуск с той же ссылкой.
- [`make init` → `openspec init` образа меняет `.claude/skills/openspec-*` и `.claude/commands/opsx/`
  или трогает `CLAUDE.md`/`AGENTS.md`] → после шага просматривается `git diff`; правка файлов
  поставки утилитой фиксируется и выносится на решение пользователя, а не принимается молча.
- [Правила `DGN-*` начинают действовать, а `README.md` проекта им не соответствует] → вне рамок
  изменения; несоответствие называется в итоговом отчёте как кандидат в отдельное изменение.
- [Обновление смешается в коммите с незавершённой работой ветки `forge-operation`] → в коммит
  попадают только файлы поставки и артефакты этого изменения; ветку и код задачи выбирает
  пользователь до коммита по `GIT-010`.
- [Следующее обновление kit'а снова выдаст те же четыре конфликта] → ожидаемое поведение
  при отсутствии слияния в установщике; порядок разрешения описан в этом документе.

## Migration Plan

Откат до коммита: файлы поставки и манифест возвращаются копированием из резервной копии
в scratchpad, новые файлы `rules/project-docs-rules.md` и `.claude/skills/project-docs/`
удаляются. Откат после коммита — отдельным изменением по явному запросу пользователя.

## Open Questions

- Код и номер задачи для коммита и ветка, в которой он делается, — уточняются у пользователя
  перед коммитом по `GIT-010` и `GIT-005`; на план работ это не влияет.
