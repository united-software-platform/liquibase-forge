# Design

Технические решения первого этапа: как операция Liquibase Forge раскладывается на беклоги
`formular`, детерминированный CLI и работу агента, и почему выбрано именно так.

## Context

Мотивация — в [proposal.md](./proposal.md#why). Решения опираются на свойства плагина
`formular` 1.3.0, которые задают рамку проектирования:

- беклог порождается командой `backlog generate` из шаблона `templates/<операция>.md` и лежит
  в `backlog/<операция>/<предмет>/tasks.md`;
- состав порождённого беклога не правится (`BKL-004`): условные блоки раскрываются флагами
  при порождении, ветвления по ходу исполнения нет;
- стоп-знак — подтверждение владельца непосредственно перед задачей (`BKL-007`);
- значения исполнения и добытые значения живут во фронтматтере (`BKL-005`);
- каждая задача несёт признак «выполнено ранее», и при расхождении с отметкой верно
  состояние (`BKL-006`);
- завершённость беклога проверяется прогоном `backlog verify` (`BKL-010`); состояния
  «закрыт с ошибкой» в `formular` нет.

Лежащее изменение `core-cli-first-slice` уже описывает CLI на Python, формат модели в YAML,
команды `validate`, `generate`, `apply`, `reconcile` и тестовую среду с префиксом `lbfr`.

## Goals / Non-Goals

**Goals:**

- Один язык для документов, шаблонов и будущего кода — `docs/domain.md`.
- Читаемая сквозная схема «намерение → отчёт» — `docs/architecture.md`.
- Шаблоны беклогов, принятые прогоном `backlog check-template` до появления кода.

**Non-Goals:**

- Реализация CLI `forge` и навыка `forge`.
- Полная семантика формата модели данных: этап 1 вводит только понятия ядра.
- Поддержка СУБД кроме PostgreSQL и работа с production-БД.

## Decisions

### D1. Агент думает, CLI исполняет

Агент отвечает только за то, что требует понимания текста: толкование намерения, написание
модели данных и её правку по расхождениям. Всё остальное — проверка модели, генерация changelog,
накат, сверка, откат, принятие и отчёт — выполняет детерминированный CLI `forge`.

Альтернативы: навык с инструкциями без CLI — агент писал бы changelog сам вопреки цели поставки
и BR-009; сервис со своим LLM внутри — противоречит роли LLM как пользователя Forge.

### D2. Модель — целевое состояние схемы

Модель данных описывает полное желаемое состояние схемы. Changelog строится как добавляющая
разница между принятой моделью в `db/` и новой; модель, требующая удаления или переименования,
отклоняется. Сверка сравнивает схему целиком.

Альтернатива: модель как описание изменения — сверка и контроль добавляющих изменений
потребовали бы восстанавливать полное состояние из истории изменений.

### D3. Два шаблона: операция и попытка

- `forge-model` — беклог операции: фронтматтер-журнал, три группы «попытка и откат», группа
  «Итог» с закрытием и отчётом.
- `forge-apply` — беклог одной попытки: от создания модели до вердикта сверки.

Лимит в три попытки задаётся устройством шаблона — в нём ровно три группы, — а не счётчиком
в коде. Беклог операции хранит всю историю попыток (BR-003, BR-004), а беклог попытки остаётся
коротким и порождается со своими флагами.

Альтернативы: один беклог с тремя развёрнутыми попытками целиком — длинный и повторяющийся
шаблон; цепочка независимых беклогов под управлением CLI — теряется единый носитель операции,
а откат выпадает из контроля исполнения.

### D4. Задача — цель, развилка — в CLI

Ветвления по ходу исполнения в беклоге нет, поэтому задачи формулируются как цели, а выбор
действия по фронтматтеру делает CLI:

| Задача | Признак «выполнено ранее» и действие |
|--------|--------------------------------------|
| Группа попытки N | `forge status` называет подтверждённую модель предыдущей попытки — группа выполнена ранее |
| Откат попытки N | `forge rollback --attempt N`: после успешной сверки ничего не меняет, иначе откатывает и проверяет возврат |
| Закрытие операции | `forge close`: при успехе принимает модель и changelog в `db/`, иначе фиксирует `failure` |
| Отчёт | `forge report` собирает итог из фронтматтера |

Так признак «выполнено ранее» сохраняет смысл `BKL-006` — результат цели уже есть в состоянии, —
а развилка проверяема тестами CLI.

### D5. Журнал операции — фронтматтер беклога операции

Отдельного файла журнала нет. Фронтматтер `forge-model` несёт намерение, режим, перечень беклогов
попыток, пути к артефактам, вердикты попыток и статус операции. Артефакты лежат рядом:

```text
backlog/
├── forge-model/<штамп>/
│   ├── tasks.md                 беклог операции и журнал
│   └── attempt-N/
│       ├── model.yaml
│       ├── changelog.yaml
│       ├── apply.json
│       ├── reconcile.json
│       └── rollback.json
└── forge-apply/<штамп>-<N>/
    └── tasks.md                 беклог попытки N
db/
├── model.yaml                   принятая модель
└── changelog/                   принятые changelog
```

`backlog/` не коммитится: след нужен для разбора на тестовой БД. `db/` коммитится как состояние
проекта.

### D6. Стоп-знаки и автоматический гейт

| Место | Шаблон | Требование |
|-------|--------|------------|
| Перед созданием модели, каждая попытка | `forge-apply` | BR-005 |
| Перед накатом, каждая попытка | `forge-apply` | BR-006 |
| Перед закрытием операции | `forge-model` | BR-007 |

На откате стоп-знака нет: он возвращает схему к подтверждённому состоянию, а контроль
обеспечивают отметки и `backlog verify`. Подтверждений на операцию — не больше семи.

Флаг `auto` в обоих шаблонах заменяет стоп-знак автоматическим гейтом: агент проверяет машинно
проверяемые условия (модель прошла `validate`, адрес БД в перечне тестовых, changelog только
добавляющий) и записывает решение с обоснованием. Термин «стоп-знак» за гейтом не закрепляется:
в `formular` он означает подтверждение владельца (`TERM-007`).

Альтернатива: агент сам подтверждает стоп-знак — подтверждает тот же, кто исполняет, и смысл
`BKL-007` теряется.

### D7. Флаги шаблонов

| Шаблон | Флаг | Взведён | Снят |
|--------|------|---------|------|
| `forge-model` | `auto` | гейт перед закрытием | стоп-знак перед закрытием |
| `forge-apply` | `auto` | гейты перед моделью и накатом | стоп-знаки перед моделью и накатом |
| `forge-apply` | `first-attempt` | показ понимания намерения | показ расхождений и плана правки |

Флагов меньше восьми, и `check-template` перебирает все сочетания.

### D8. Сквозной поток

```text
LLM ─намерение─▶ навык forge
  └─▶ backlog generate --operation forge-model
       └─▶ /backlog:backlog-run  (беклог операции)
            ├─ попытка N: backlog generate --operation forge-apply
            │   └─▶ /backlog:backlog-run  (беклог попытки)
            │        стоп/гейт → model.yaml → forge validate → forge generate
            │        стоп/гейт → forge apply → forge reconcile → вердикт
            ├─ откат N: forge rollback --attempt N
            └─ итог: стоп/гейт → forge close → backlog verify → forge report ─▶ LLM
```

Подробная схема и контракт команд — в `docs/architecture.md`.

## Risks / Trade-offs

- [Беклог операции исполняет вложенный беклог попытки — `formular` описывает исполнение одного
  беклога] → задача группы попытки называет путь беклога попытки и предписывает загрузку
  `/backlog:backlog-run` по `BKL-008`; проверка вложенного исполнения — в приёмке шаблонов.
- [Команды CLI в шаблонах ещё не реализованы] → контракт команд фиксируется в
  `docs/architecture.md`, и реализация в следующих изменениях сверяется с ним.
- [До семи подтверждений на операцию утомляют владельца] → режим `auto` для тестовой БД.
- [Расхождение с `core-cli-first-slice`: модель одной таблицы, `attempts` всегда `1`] → отдельный
  шаг согласования после принятия этого изменения.
- [Откат Liquibase может не сработать для частично применённого changelog] → задача отката
  предусматривает пересоздание тестовой БД и проверяет возврат схемы.

## Migration Plan

Кода и данных нет — миграция не требуется. Правка `BUSINESS-REQUIREMENTS.md` меняет версию
документа на 0.2.0; ссылки на прежние BR-001..BR-015 сохраняют номера.
