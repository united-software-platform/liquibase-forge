# Design

## Context

Мотивация — в `proposal.md`, требование — в `specs/forge-release/spec.md`. Сценарий `release`
сейчас: job `checks` (только чтение), затем job `release` с `contents: write` — гейт ветки
`main`, checkout, «Разбор текущей версии» (выход `next`), гейт незакоммиченных правок `VERSION`,
запись версии с коммитом и тегом, публикация релиза. Тесты `tests/release/test_release_workflow.py`
читают YAML и исполняют скрипты шагов в `tmp_path`.

Задачи на GitHub закрываются ключевыми словами `Closes #N` при слиянии PR в `main`. Слияние
предшествует запуску `release`, поэтому к моменту гейта задачи выпуска уже закрыты.

## Goals / Non-Goals

**Goals:**

- Состав выпуска задаётся на GitHub и проверяется машиной, а не памятью человека.
- Гейт срабатывает до любой записи и называет, что мешает выпуску.

**Non-Goals:**

- Проверять, что задача закрыта «по существу», — гейт видит только статус.
- Автоматически создавать milestone или переносить задачи между milestone.

## Decisions

### Состав выпуска — milestone с названием нового номера

Сценарий уже вычисляет новый номер, поэтому имя milestone `vX.Y.Z` берётся без дополнительного
ввода: единственный ввод сценария — разряд, и требование «Релиз запускается вручную с выбором
разряда» остаётся в силе.

Альтернативы: метка `release-vX.Y.Z` — не даёт счётчика открытых задач и прогресса выпуска;
перечень задач во вводе сценария — второй ввод, который запрещает спека.

### Нет milestone — ошибка, а не пропуск

Пропуск при отсутствии milestone молча выключал бы гейт: достаточно забыть завести milestone.
Цена строгости — milestone нужен и для `patch`, даже если задача одна. Это осознанный выбор:
выпуск без задачи ничего не объясняет.

### Шаг стоит после разбора версии и до гейта правок

Гейту нужен выход `next` шага «Разбор текущей версии», а записи до гейта быть не должно. Шаг
идёт сразу после разбора, перед гейтом незакоммиченных правок. Job `checks` остаётся первым:
сначала дешёвый отказ проверок не нужен — оба отказа ничего не пишут.

### Чтение через gh api с GITHUB_TOKEN и правом issues: read

Скрипт шага:
1. `gh api "repos/$GITHUB_REPOSITORY/milestones?state=all" --paginate` и отбор по `title`;
   нет совпадения — ошибка с именем milestone.
1. `gh api "repos/$GITHUB_REPOSITORY/issues?milestone=<номер>&state=open" --paginate` — открытые
   задачи; непустой перечень — ошибка с `#номер заголовок` каждой задачи.

API задач возвращает и PR, привязанные к milestone: открытый PR тоже останавливает выпуск. Это
верно — незавершённая работа выпуска. Номер и имя milestone передаются через `env`, а не
подстановкой `${{ }}` в текст скрипта, как во входе разряда.

Job `release` получает `issues: read` рядом с `contents: write`; верхний уровень и job `checks`
не меняются. Требование «Право записи есть только у шага выпуска» сохраняется: новое право —
только чтение.

### Тест исполняет гейт с заглушкой gh

Заглушка `gh` в `PATH` отвечает фиксированным JSON по аргументам. Тесты: milestone с открытой
задачей, отсутствующий milestone, все задачи закрыты, PR в milestone. Плюс статические проверки
порядка шагов и прав job'а. Сетевых обращений тесты не делают.

### Код задачи этого change — отдельная задача на GitHub

Коммиты change получают код LBFR-024 «подготовить выпуск 0.3.0» по GIT-009; задача заводится
на GitHub и входит в milestone `v0.3.0`, чтобы гейт проверил и её. Код подтверждается владельцем
перед первым коммитом (GIT-010).

## Risks / Trade-offs

- [Задачу выпуска не успели сделать] → выпуск стоит, пока её не закроют или явно не перенесут
  в другой milestone; перенос — видимое решение владельца, а не молчаливое отложение.
- [Задачу закрыли вручную без работы] → гейт видит только статус; защищает порядок «change
  заархивирован, коммит с `Closes`».
- [`GITHUB_TOKEN` без `issues: read`] → `gh api` отвечает 403, шаг падает до записи и это видно
  в логе; тест прав job'а не даёт убрать право незаметно.
- [Задача закрыта в milestone 0.3.0, но её PR не слит] → `Closes` закрывает задачу только при
  слиянии в `main`, поэтому такое состояние возможно лишь при ручном закрытии.

## Migration Plan

1. Завести на GitHub задачу LBFR-024 и milestone `v0.3.0`, привязать к нему #7, #8, #9, #10,
   #12 и LBFR-024.
1. Внести гейт в `release.yml` первым change ветки `release/v0.3.0`, до задач выпуска.
1. Откат — удалить шаг и право `issues: read`; milestone на GitHub не мешает.
